## Detailed decision records

아래 기록은 결정 당시의 배경·대안·절충·적용 범위와 재검토 조건을 보존한다. 결정표는 ID와 상태의 색인이다. 외부 자료는 판단 맥락일 뿐 ATLAS 정책·성능·capacity를 대신 입증하지 않는다.

### ADR-0001 — 초기 아키텍처 방향 (D-001, D-037~D-042)

**상태:** 구조·기술 방향 승인; 구현·배포·운영은 별도 승인. D-001은 초기 가설(Proposed)이며 Gate 3의 승인된 구체 구조는 D-037 이하에 기록한다.

주문·재고·결제·정산의 정합성과 장애 복구를 검증해야 하지만 팀 규모, 트래픽, 배포 제약이 정해지지 않아 독립 서비스 운영 근거가 없었다. 선택 기준은 module data ownership과 transaction boundary 검증, 낮은 운영 부담, 재현 가능한 integration/failure test였다. 한 deployment 내 Modular Monolith First는 transaction·test를 단순화하고 경계를 명시하나 독립 확장·배포를 제한하며 경계 약화 위험이 있다. Microservices는 독립 배포·확장을 제공하지만 network failure, distributed transaction, 운영 부담을 앞당긴다. 경계 없는 단순 monolith는 시작이 단순하나 coupling과 변경 검증 비용이 커진다. 소유자는 첫 안을 선택했다.

승인된 stack은 JDK 25 LTS, Spring Boot 4.1.2/MVC, PostgreSQL 18.6, Gradle Wrapper 9.8.2; Testcontainers 2.0.5는 test scope, ArchUnit 1.5.1은 package dependency rule을 검사하고 Spring Modulith marker 방식은 제거됐다. Boot 4 Flyway는 `spring-boot-starter-flyway`를 쓴다. CI는 Temurin 25이며 production JDK vendor/distribution/license는 미결정이다. PostgreSQL은 durable system of record. 단일 database/schema에서 각 module이 소유 table과 write ownership을 갖고 cross-module 호출은 public API를 통한다. 필요한 invariant만 짧은 transaction으로 원자화하며 PSP network call은 transaction 밖이다. Production isolation·lock recovery·schema는 미결정이다.

현재 Buyer slice만 대상으로 Campaign(현재 campaign/SKU 및 sale-open), Admission(ticket/key/sequence/retry/re-entry), Inventory(pool/reservation/claim/release), Order/Checkout(orchestration/state), Payment(provider operation/reconciliation) 책임을 둔다. Tenant security, 확장 catalog, settlement/reconciliation은 장기 capability map일 뿐 현재 module contract가 아니다. Admission counter row 증가와 ticket insert는 같은 transaction이며 첫 eligible join에서 counter를 lazy initialize; PostgreSQL sequence의 gap 및 commit-order 불일치로 FIFO 기준에 맞지 않아 선택하지 않았다 ([PostgreSQL 18 sequence semantics](https://www.postgresql.org/docs/18/transaction-iso.html)). Module boundaries를 명시하는 modular design의 일반적 이점은 [Google Cloud guidance](https://docs.cloud.google.com/architecture/framework/performance-optimization/promote-modular-design) 및 Shopify의 대규모 Rails 사례([Deconstructing the Monolith](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity))와 맥락상 일치하나 이는 ATLAS의 경계나 성능 증거가 아니다. Packwerk 회고는 domain 명칭과 실제 dependency가 어긋날 수 있음을 지적한다 ([Shopify retrospective](https://shopify.engineering/a-packwerk-retrospective)); ATLAS ArchUnit 규칙은 작성된 allowlist만 검사하고 domain correctness/performance를 증명하지 않는다 ([ArchUnit guide](https://www.archunit.org/userguide/html/000_Index.html)).

별도 queue/cache/broker는 load test에서 bottleneck과 비교 가능한 이점을 확인한 경우에만 재검토한다. 승인된 10k sessions/60m (~2.8/s), 2×/4× synthetic stress는 report-only input이지 demand·throughput·production SLO가 아니다. Offered session arrivals, stage RPS, resolved-session TPS, concurrency, DB QPS는 서로 다른 단위로 기록한다. `L ≈ λ × W`는 steady-state 관계이며 현재 latency를 측정하지 않았으므로 수치 capacity를 산출하지 않는다 ([Little's Law](https://mathworld.wolfram.com/LittlesLaw.html)). 동일한 이유로 AWS/k6 open-loop 및 hybrid workload 안내는 측정 단위·모델을 구분하는 참고이지 도구나 target 선택이 아니다 ([AWS load-test types](https://docs.aws.amazon.com/prescriptive-guidance/latest/load-testing/test-types.html), [k6 open/closed models](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/), [Artillery hybrid models](https://www.artillery.io/blog/load-testing-workload-models)).

Local inventory baseline은 conditional guarded UPDATE와 per-order transaction lock; production lock 전략·성능은 비교 측정 전까지 미결정. PostgreSQL row-lock/deadlock 및 isolation semantics는 version-specific reference이며 capacity proof가 아니다 ([explicit locking](https://www.postgresql.org/docs/18/explicit-locking.html), [transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html)). Shopify inventory reservation 사례는 MySQL/Shopify에 한정, schema나 throughput 근거로 일반화하지 않는다 ([Shopify](https://shopify.engineering/scaling-inventory-reservations)).

재검토 조건: 독립 team/deployment 필요, module 간 변경·장애 결합 증가, 단일 deployment/PostgreSQL bottleneck 반복 측정, data ownership 변경 또는 실측이 현재 가설을 반증. Local runtime Issue #72는 Fake PSP 기반 current-flow만 승인했으며 live payment·deployment·production capacity 주장은 승인하지 않았다.

### ADR-0002 — 기술 선택과 공통 처리 재검토 (D-040, D-044~D-046)

**상태:** 검토 완료; D-040의 사용자 승인 stack 유지. Migration이나 production 승인 아님.

비교 범위는 단일 SKU Buyer flow, blocking JDBC, PostgreSQL, 한 Spring Boot deployment, Fake PSP였다. Version support는 compatibility 근거이지 성능 우위 증명이 아니다. Java 25 LTS는 사용자가 선택했고 모든 source/test가 Java였으며, Java 25 전용 feature 요구는 없었다. Java 21 LTS 및 Kotlin 2.2도 대안이었다. Kotlin의 nullability와 concise syntax 이점에는 stdlib/reflection, Spring `all-open`, Jackson module 및 mixed-language convention 비용이 따른다. Kotlin은 명확한 user/skill objective와 bounded pilot이 있을 때 신규 slice에서 재평가한다. Oracle LTS 일정은 vendor별이다 ([Java support roadmap](https://www.oracle.com/java/technologies/java-se-support-roadmap.html)); Boot Kotlin 문서는 추가 plugin/dependency 등 지원 조건을 설명할 뿐 언어 선택을 정하지 않는다 ([Spring Boot Kotlin](https://docs.spring.io/spring-boot/reference/features/kotlin.html)). Meta의 Android migration과 JetBrains/Xebia adoption 글은 각각 custom tooling 사례와 adoption guidance이지 Spring backend productivity/defect benchmark가 아니다 ([Meta](https://engineering.fb.com/2024/12/18/android/translating-java-to-kotlin-at-scale), [JetBrains/Xebia](https://blog.jetbrains.com/kotlin/2025/10/evaluating-kotlin-in-real-projects/)).

Boot 4.1.2/MVC를 유지하고 Boot 3.5.16, Quarkus, WebFlux를 대안으로 검토했다. Boot 3.5도 Java 25를 지원한다; Boot 4는 승인 시점의 stable line이었다. Quarkus는 cold-start/idle-memory objective가 생기면 비교 후보. 현재 JDBC/JPA의 blocking I/O에는 MVC가 자연스러우며 WebFlux의 non-blocking workload 이점이 보편적 속도 향상을 뜻하지 않는다. Cloud startup, memory, p99는 측정되지 않았다. 공식 requirements는 지원 호환성을 보여준다 ([Boot 4](https://docs.spring.io/spring-boot/system-requirements.html), [Boot 3.5](https://docs.spring.io/spring-boot/3.5/system-requirements.html)); Spring MVC/WebFlux 안내는 workload fit 설명이지 ATLAS benchmark가 아니다 ([Spring Framework WebFlux](https://docs.spring.io/spring-framework/reference/web/webflux/new-framework.html)). Quarkus-hosted 비교는 embedded-ML 단일 서비스의 AI-assisted 요약이므로 독립 재현 benchmark로 취급하지 않았다 ([Quarkus Insights](https://quarkus.io/blog/quarkus-insights-255-faster-leaner-predictable-quarkus/)).

PostgreSQL 18.6을 17.11, MySQL, Redis-only reservation state보다 선택했다. ATLAS는 advisory transaction lock, row lock, PostgreSQL-specific migration/index semantics를 쓴다. MySQL은 유효한 RDBMS 대안이지만 비교 실험은 없고 Redis-only는 order/ledger와 atomic boundary를 분리한다. PostgreSQL major-version support policy는 수명주기만 설명하며 capacity를 입증하지 않는다 ([versioning policy](https://www.postgresql.org/support/versioning/)). Shopify의 Redis-to-MySQL 운영 사례는 ATLAS의 PostgreSQL 비교 benchmark가 아니다 ([Shopify](https://shopify.engineering/scaling-inventory-reservations)).

Gradle Wrapper 9.8.2는 사용자 선택으로 유지; Maven Wrapper 3.9.16은 lifecycle/convention 예측성이 강점이고 Gradle은 flexible DSL/cache/parallel capability와 build-logic 복잡도 trade-off가 있다. 현재 작은 단일 `build.gradle`에서 build speed 우위는 측정하지 않았다. Boot는 두 도구 모두 지원하며 ([requirements](https://docs.spring.io/spring-boot/system-requirements.html)), release notes는 버전 사실만 뒷받침한다 ([Gradle 9.8.2](https://docs.gradle.org/9.8.2/release-notes.html), [Maven 3.9.16](https://maven.apache.org/docs/3.9.16/release-notes.html)); practitioner 비교는 controlled benchmark가 아니다 ([Maven/Gradle](https://www.thoughtfularchitect.dev/posts/maven-vs-gradle)).

초기 explicit `JdbcTemplate` persistence 판단은 일반 CRUD에서 JPA 적용으로 한정해 ADR-0004/D-048에 의해 supersede됐다. PostgreSQL 특화 locking/atomic SQL은 JDBC/native query로 남고 Flyway가 versioned DDL을 소유한다. Testcontainers PostgreSQL은 test-scope이며 H2는 PostgreSQL advisory lock/engine behavior를 대체하지 않는다. Spring JDBC/JPA locking 자료는 선택지/API 설명이지 성능 증거다 ([JDBC](https://docs.spring.io/spring-framework/reference/data-access/jdbc/choose-style.html), [JPA locking example](https://softice.dev/posts/optimistic_and_pessimistic_locking_with_spring_data_jpa/), [Testcontainers PostgreSQL 2.0.5 API](https://javadoc.io/doc/org.testcontainers/testcontainers-postgresql/2.0.5)).

공통 처리 선택도 적용 범위가 명시적이다. `application-module`의 단일 `GlobalExceptionHandler`는 RFC 9457 `ProblemDetail`와 stable `code` extension을 반환하며 unexpected 500 detail을 감춘다. 각 domain module은 typed exception과 reason enum 하나를 소유; raw `IllegalArgumentException`은 client contract가 아니다. `AdmissionService.find()`/GET은 persisted state만 읽고 expiry/FIFO promotion/DB write를 하지 않는다. Scheduler가 반영하며 sweep 전 status는 잠시 stale할 수 있다. 이는 CQS 설계 원칙 및 RFC 9110의 GET safe semantics와 부합하나 expiry는 application operation으로 별도 처리한다 ([CQS](https://martinfowler.com/bliki/CommandQuerySeparation.html), [RFC 9110 §9.2.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.1), [Spring ProblemDetail](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-rest-exceptions.html), [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)).

Transactions는 invariant 단위로 짧게 유지한다. 기본 module operation은 `@Transactional`; 명시적 Order/Inventory/Payment flow는 `TransactionTemplate`을 사용하며 같은 datasource/manager와 기본 REQUIRED propagation에서 cross-module JDBC 참여 가능. PSP 호출은 transaction 밖이고 module 분리 후 동일 atomicity를 가정하지 않는다. Clock은 root configuration 주입, tests는 controllable clock, module scheduler는 expiry 처리. 공용 root concern은 error handler와 Clock configuration뿐이므로 generic `common` module은 만들지 않는다. Authentication/tenant isolation, metrics/tracing/alerts, production backup/deployment/PSP recovery는 OPEN이다. 새 runtime dependency는 관례만으로 추가하지 않는다.

재검토: Kotlin은 명시된 목적·pilot, Quarkus/reactive는 승인된 workload의 startup/memory/tail-latency 요구와 같은-workload pilot, DB/build 변경은 승인 benchmark나 compatibility 필요가 있을 때. Current stack/support 변경은 새 ADR을 만들며 과거 기록을 소급 수정하지 않는다.

### ADR-0003 — 도메인 모듈과 계층 경계 (D-047, D-050~D-054)

**상태:** Accepted. 기존 다섯 business capability를 각각 Gradle subproject로 두고 `application-module`에서 조립한다. 이는 module 추가나 독립 배포를 뜻하지 않는다. 패키지만 나누면 compile dependency를 막지 못하고, 별도 service는 독립 배포/data ownership 근거 없이 network failure와 distributed transaction을 앞당긴다. Gradle subproject는 소유권·의존성을 build에서 드러내는 대신 설정/API 연결 비용이 든다.

`application-module`은 Boot/HTTP/root error/config/Flyway 및 다섯 domain modules 의존을 소유한다. `campaign-module`은 Seller·Seller-SKU·Campaign (inventory API 의존), `admission-module`은 ticket/sequence/idempotency/slot/expiry (campaign 의존), `inventory-module`은 shared pool/reservation/conservation, `order-module`은 checkout/order orchestration (admission/inventory/payment 의존), `payment-module`은 attempts/provider state/results를 소유한다. Seller/Seller-SKU/Campaign은 현행 동일 흐름·API·data ownership 경계가 별도로 확인되지 않아 campaign module에 유지; 독립 업무 흐름과 ownership이 생길 때 재검토한다 (D-054).

여섯 Gradle subproject의 물리 디렉터리는 root `ATLAS-application`, `ATLAS-campaign`, `ATLAS-admission`, `ATLAS-inventory`, `ATLAS-order`, `ATLAS-payment`; `settings.gradle` `projectDir` mapping은 project/task path와 dependency coordinates를 보존한다. `modules/<name>` 추가 계층은 root에서 찾기 어렵고 project path까지 바꾸는 것은 불필요한 영향이 있어 선택하지 않았다. Gradle 문서는 `projectDir` mapping을 지원하며 naming/build mechanics를 뒷받침할 뿐 directory layout의 보편적 최선은 아니다 ([Gradle Multi-Project Builds 9.8.2](https://docs.gradle.org/9.8.2/userguide/multi_project_builds.html)).

공개 contract는 `.service`, `.dto.request`, `.dto.response`, `.exception`; lifecycle enum은 필요한 경우 `.persistence.state`, entity는 `.persistence.entity`, module-private repository는 `.repository`, workflow/scheduled expiry는 `.service.impl`, provider adapter는 `.provider.*`. Cross-module entity/repository 접근 금지, 연계는 scalar ID와 public service/DTO. HTTP controller/transport DTO/config/error mapping은 application module 소유. HTTP/domain request를 나누는 것은 input shape/validation이 다를 때만. CQRS, CommandBus, handler/mediator, `internal`, `package-info.java` marker 금지; 구체 요구와 ADR 승인 없이는 추가하지 않는다. Spring Modulith marker 방식은 이전 도구 사용 경험이며 현재 boundary test는 ArchUnit 1.5.1; 명시한 package rule만 검사하고 domain correctness를 판단하지 않는다 ([ArchUnit guide](https://www.archunit.org/userguide/html/000_Index.html)).

업무 의미 기반 capability boundary는 Google Cloud guidance, Meituan DDD 사례에서 참고했지만 ATLAS의 module map·성능 증명은 아니다 ([Google Cloud modular design](https://docs.cloud.google.com/architecture/framework/performance-optimization/promote-modular-design), [Meituan DDD practice](https://tech.meituan.com/2017/12/22/ddd-in-practice.html)). Shopify의 Packwerk retrospective는 semantic labels와 runtime dependency가 불일치할 수 있다고 경고한다 ([retrospective](https://shopify.engineering/a-packwerk-retrospective)). Alibaba COLA 작성자의 직접 읽히는 흐름 선택은 author experience이지 보편 지침이 아니다 ([COLA](https://www.alibabacloud.com/blog/the-simplicity-of-cola-an-alibaba-open-source-application-architecture_597234)). Private ArchUnit design blog도 층을 복잡도에 맞출 관점일 뿐 모든 층의 근거가 아니다 ([ArchUnit practitioner article](https://shaogefenhao.com/posts/architecture/arch-unit.html)).

기본 CRUD는 JPA; schema는 application-owned Flyway, Hibernate `ddl-auto=validate`. PostgreSQL-specific locking, sequence, guarded update만 `.repository` JDBC/native SQL. Service implementation은 transaction/scheduled workflow 소유, PSP call transaction 밖. `Pool`은 책임을 드러내도록 `InventoryPool`로 rename하되 DB schema/API response field 유지. V4 migration checksum을 바꾸지 않고 V5에서 `operation` column/constraint를 `payment_phase`로 rename. Test는 consumer-visible behavior, boundary, state/error/concurrency 검증에 집중; PostgreSQL semantics는 PostgreSQL로 확인, wiring/중복 위험 테스트 금지.
Google Testing Blog's real-dependency guidance was considered only where fidelity to PostgreSQL behavior matters; it is not a blanket ban on mocks or a test-count formula ([Avoid Mocks](https://testing.googleblog.com/2024/02/increase-test-fidelity-by-avoiding-mocks.html)).

Module 경계나 모듈 수는 독립 team/release/data ownership 또는 측정된 운영/성능 요구가 생길 때 재검토한다. Issue #89/PR #90에서 근거 있는 redundant/unused package/class를 찾지 않아 삭제하지 않았다.
GitNexus provenance is limited to the repository graph examined before the changes in PR #90; no post-change graph was generated. It therefore provides no graph-based evidence that the resulting repository structure conforms to the selected module boundaries.

### ADR-0004 — JPA CRUD와 PostgreSQL 특화 SQL 경계 (D-048, D-051)

**상태:** Accepted. 초기에는 모든 CRUD와 concurrency SQL을 `JdbcTemplate`로 직접 구현했으나 단순 CRUD에서 SQL/row mapping 반복이 있었다. 다섯 domain module의 일반 CRUD는 JPA entity와 Spring Data `JpaRepository`; entity `.persistence.entity`, repository module-private `.repository`. 별도 mapper, generic base, custom ORM은 두지 않는다. Schema는 application module의 Flyway migrations 단독 소유, Hibernate `ddl-auto=validate`; ORM schema create/update 금지. Entity 간 cross-module relation 대신 ID를 저장하고 public service/DTO contract로 연동.

PostgreSQL lock, atomic update, sequence allocation 경로만 `.repository` 내부 `JdbcTemplate` 또는 JPA native query를 쓴다. CRUD SQL 재구현은 금지. Service transaction과 scheduled workflow 소유; provider network call은 transaction 밖. 이 선택은 SQL/row mapping 반복을 줄이지만 ORM dependency와 entity mapping 비용을 더하며 JPA adoption은 성능 개선 증거가 아니다. PostgreSQL 전용 동시성 SQL은 database-specific이고 transaction/lock을 바꾸는 batch optimization은 측정·별도 결정 전 추가하지 않는다.

Spring Data `JpaRepository` 문서는 typed CRUD repository contract를 정의할 뿐 performance를 입증하지 않는다 ([repository interfaces](https://docs.spring.io/spring-data/jpa/reference/repositories/definition.html)). Spring JDBC access styles, PostgreSQL 18 locking/isolation 문서는 SQL/transaction semantics의 근거이지 ATLAS capacity 결과가 아니다 ([Spring JDBC](https://docs.spring.io/spring-framework/reference/data-access/jdbc/choose-style.html), [PostgreSQL explicit locking](https://www.postgresql.org/docs/18/explicit-locking.html), [transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html)). JPA lock options에 관한 appointment 예시는 benchmark나 ATLAS advisory-lock/native SQL 권고가 아니다 ([practitioner example](https://softice.dev/posts/optimistic_and_pessimistic_locking_with_spring_data_jpa/)).

PostgreSQL/Testcontainers local integration에서 `ddl-auto=validate` 및 current JPA mapping 검증은 통과했으나 이는 production DB, isolation, operational behavior/performance를 보장하지 않는다. Layers/module boundary를 구분한 개인 설계 경험은 사례일 뿐 모든 package 층 도입 근거로 일반화하지 않는다 ([practitioner article](https://shaogefenhao.com/posts/architecture/arch-unit.html)).

### ADR-0005 — Seller-SKU 공유 재고와 전역 FIFO/K (D-049; migration 부분은 D-055로 superseded)

**상태:** Accepted. 초기 campaign마다 같은 SKU의 pool/queue를 별도 생성했으나 Seller identity가 없어 campaign 간 stock 공유·global FIFO를 나타내지 못했다. Owner choice는 Seller=Tenant, Seller-owned SKU, Campaign 간 shared stock 및 global FIFO/K. 고려 대안은 (A) Campaign별 stock+queue 유지—변경은 작지만 같은 실제 Seller-SKU 재고가 분리/중복됨; (B) Seller-SKU stock, Campaign별 queue—oversell은 방지하지만 선택된 cross-Campaign global FIFO는 아님; (C) 하나의 `(sellerId, skuId)` pool, sequence counter, lock, active K, FIFO—선택. Campaign은 sale status, ticket TTL, attribution을 유지한다.

Seller registration은 server-generated UUID를 반환하고 이후 요청은 `sellerId`를 보낸다. Seller=Tenant는 data identity일 뿐 authentication/authorization 또는 tenant security boundary가 아니다. 외부 network 노출에 auth 없이 bind하는 것은 범위 밖. Seller-SKU registration에서 `initialStock`으로 inventory pool을 한 번 생성하며 Campaign creation은 stock을 더하지 않는다. Inventory pool/reservation은 inventory module 소유. Seller-SKU registration 때 global admission의 `maxActiveCheckouts` K를 설정; 과거 campaign K를 집계/보존하지 않는다. 모든 Campaign은 같은 Seller-SKU global FIFO와 K 공유. Ticket TTL 및 `(campaignId, idempotencyKey)` replay scope는 Campaign별 유지, `campaignId`는 ticket/order attribution이다. Seller/SKU/Campaign은 기존 campaign module 소유하며 별도 Catalog/Seller module 추가 안 함.

재고 reservation/claim consistency 및 available/reservation 구분은 Shopify와 commercetools 자료에서 참고했으나 그들의 storage/scale/vendor model을 복사하지 않았다 ([Shopify inventory reservations](https://shopify.engineering/scaling-inventory-reservations), [commercetools inventory modeling](https://docs.commercetools.com/learning-model-your-product-catalog/inventory-modeling/inventory-management)). Alibaba Redis Snap-Up 사례는 pre-deduct/timeout-release trade-off만 참고, Redis architecture와 scale 수치는 적용하지 않는다 ([Alibaba Cloud](https://www.alibabacloud.com/blog/597858)). Meituan queue articles describe ordering/parallelism trade-offs, not ATLAS's fairness/K policy ([queue models](https://tech.meituan.com/2016/07/29/distributed-queue-based-programming.html), [optimization](https://tech.meituan.com/2016/08/05/distributed-queue-programming-optimization.html)). SeatGeek virtual waiting room and Queue-it online fairness are operator/vendor-specific, not general fairness proof ([SeatGeek/InfoQ](https://www.infoq.com/presentations/ticketing-system-virtual-waiting-room/), [Queue-it](https://queue-it.com/blog/online-fairness)).

Cross-Campaign orders use one Seller-SKU balance; conditional stock update protects against oversell. Admission counter/sequence/held-slot/expiry/promotion use Seller-SKU key; releasing a slot promotes the next global FIFO ticket. Global transaction lock broadens contention and serializes same Seller-SKU joins; correctness tests are required, but throughput/capacity is unmeasured. Campaign inventory capacity and campaign K are removed. Load performance, tenant isolation/security, location/channel stock, multi-quantity purchase, replenishment/adjustment, refund/post-claim stock policy remain unproven or out of scope; measured bottleneck/operational environment, authentication need, or expanded inventory policy triggers review.

Legacy migration method in this original decision was superseded by D-055: V6 clean-start only, preserving all domain choices here.

### ADR-0006 — V6 clean-start migration (D-055)

**상태:** Accepted; supersedes only ADR-0005's legacy migration method, not Seller-SKU ownership/shared stock/global FIFO/K. Converting V1–V5 Campaign data would require owner-verified mapping and merging stock, K, and queue. A wrong complete mapping can merge unrelated inventory/K/queue; silently resetting loses existing data. Owner therefore chose no conversion or automatic merge.

If any V1–V5 application table contains a row, V6 fails before DDL and leaves existing data/schema unchanged. Only when old application tables are empty may V6 remove old schema and create current Seller-SKU schema. No legacy mapping, aggregate, backfill, or preservation. If local data is needed, archive/reset it explicitly outside the app before empty-start; application must not silently delete/reset it. Consequence: nonempty database blocks V6 until operator action; only empty V1–V5 DB can fresh-start. Legacy transformation/recovery is not part of this migration.

### ADR-0007 — UUIDv7 identifiers (D-056; EXP-014)

**상태:** Accepted, owner decision 2026-11-03. EXP-014 is the only ATLAS measurement considered: UUIDv7 showed a smaller parent PK index, insert results near UUIDv4, and no material measured advantage for a BIGINT/public-UUID hybrid. Raw figures and workload are in [EXP-014](../08-experiments/EXP-014-id-strategy-comparison.md); these local results are not production evidence.

Seller, Campaign, Admission Ticket, and PurchaseOrder primary IDs use Hibernate UUIDv7. PaymentAttempt primary key is the Order UUIDv7 (`order_id`); its unique non-PK `attempt_id` remains UUIDv4. UUID column/API/FK formats stay; no BIGINT internal ID, separate public ID, external generator, or handwritten generator. PostgreSQL 18 documents UUIDv7; Hibernate ORM 7.4 marks `VERSION_7` `@Incubating`. Testcontainers integration verified version 7 for entity primary IDs. Source limits are below.

EXP-014 excludes ID-generation and commit costs; it is a five-run single-session synthetic PostgreSQL 18.6 test with raw timing variance and possible host contention. It does not measure concurrent load, larger working sets, sustained WAL/checkpoint, ORM generation cost, or point-lookup latency. External measurements use different workloads; no production performance/capacity claim follows.
