# EXP-123: 상품 검색 후보를 가장 드문 n-gram으로 좁혀 결과는 그대로 두고, 겹치지 않는 카탈로그 30만 개에서 지연을 다시 잰다

- 상태: ✓ 완료. 결정은 [ADR-0109](../02-decisions/adr/ADR-0109-shopping-assistant-and-ctype-independent-search.md) "결정 2"와 D-195에 반영했다.
- 날짜: 2026-11-29
- 관련: [#759](https://github.com/Neo1228/ATLAS/issues/759), [EXP-120](EXP-120-shopping-assistant-search-and-tool-safety.md)

## 문제 한 문장

`searchPublic`은 검색어 n-gram 하나만 겹쳐도 상품을 후보로 읽고 행마다 겹침 수를 세는데, EXP-120이 잰 지연(상품 200,040개에서 1.5~4.3초)은 고정 입력 120개를 1,667번 복제한 카탈로그에서 측정 잠금 없이 호스트 load1 25~31일 때 잰 값이라 규모 판단 근거가 되지 못했다.

## 방법

### 카탈로그

출처는 합성이다. 실제 쇼핑몰 데이터는 쓰지 않았다. 생성기는 `load-tests/catalog-search/product-search-scale.sql`이고 같은 `n`이면 같은 카탈로그를 만든다(md5 기반 결정적 난수, 1만 개를 두 번 만들어 이름·설명 md5가 같음을 확인했다).

- 카테고리 12개(신발, 의류, 가방, 전자, 주방, 뷰티, 캠핑, 운동, 가구, 침구, 문구, 반려동물). 카테고리마다 한글·영문 상품 명사 8~15개, 브랜드 8~14개, 특징어 6~8개를 둔다. 색·대상·소재·용도 어휘는 공통이다.
- 분포: 카테고리는 `u^1.6`, 브랜드·명사는 `u^2`로 골라 앞쪽 어휘가 많이 나온다(머리가 무거운 분포). 상품 15%는 영문 이름·설명, 50%는 모델 번호(`AB-123`), 4%는 `INACTIVE`, 5%는 `ONLINE_STORE` 미노출.
- 이름은 `브랜드 특징 명사 색 [모델]`, 설명은 `대상용 색 명사. 소재 소재, 특징. 용도에 잘 어울려요.`이다. 설명의 명사는 이름과 같고 색·대상·소재·용도는 따로 고른다.
- 라벨 고정 입력 120개(EXP-120)를 시험과 같은 UUID로 함께 넣는다.

| 규모 | 상품 | 서로 다른 이름 | 서로 다른 이름+설명 | 상품당 n-gram 평균 | 서로 다른 n-gram | `product` 크기 | GIN 크기 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 1만 | 10,120 | 9,932 | 10,120 | 50.4 | 4,128 | 9.4 MB | 1.9 MB |
| 10만 | 100,120 | 88,941 | 100,120 | 50.7 | 4,130 | 93 MB | 15 MB |
| 30만 | 300,120 | 237,315 | 300,118 | 50.7 | 4,130 | 279 MB | 41 MB |

어휘가 고정이라 서로 다른 n-gram 수가 4,130에서 멈춘다. 실제 카탈로그는 어휘가 더 넓어 드문 n-gram이 더 많고, 그만큼 아래 가지치기가 더 잘 듣는 쪽이다(측정하지 않음).

### 측정

- `postgres:18.6` 컨테이너 하나(`shared_buffers=512MB`, `work_mem=16MB`), V1~V16 적용, 규모마다 데이터베이스 하나, `VACUUM ANALYZE` 뒤.
- 호스트 측정 잠금(`measure-lock`)을 쥐고 잰 값이다. 잠금 동안 load1은 처음 72에서 끝 3까지 내려갔다(다른 작업의 빌드). 그래서 표는 부하가 4~12로 내려간 뒤 A0와 A2를 A0, A2, A0, A2 순서로 번갈아 3회씩 다시 잰 값이다(질의 64건 × 6회 = 384 표본). 처음 순차 측정(부하 72→14)에서도 순위와 배율은 같았다.
- 각 질의는 상위 5건을 한 번 뽑아 저장(예열 겸 결과 비교)한 뒤 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`의 `Execution Time`과 최상위 노드의 shared hit+read, `product`를 읽은 노드가 힙에서 가져온 행 수(남긴 행 + 필터·재검사로 버린 행)를 기록한다.
- 지연은 데이터베이스 실행 시간만이다. 애플리케이션·네트워크 시간은 없다.

### 비교한 방식

| 기호 | 방식 |
|---|---|
| A0 | 현행. `search_grams && q.grams`(모든 n-gram) |
| A2 (출시안) | 비둘기집 probe. 겹침이 `min_hits = ⌈2n/5⌉` 이상인 상품은 아무 `n − min_hits + 1`개 n-gram 중 하나를 반드시 가진다. `pg_stats.most_common_elems` 빈도가 낮은 순(목록에 없으면 가장 드묾)으로 그만큼 골라 `search_grams && probe`로 찾는다. 나머지 식은 A0와 같다 |
| A1F | A2와 같되 빈도를 정확한 n-gram 빈도 테이블(`unnest(search_grams)` 집계)에서 읽음. V17 스키마가 필요한 방식의 상한 |
| B1000 | 후보 상한. A0 후보를 1,000행에서 자름(정렬 없음. 점수로 정렬하려면 후보 전부의 점수를 계산해야 해 줄이는 비용이 없다) |

## 결과

### 관련도

| 규모 | A2 상위 5건 = A0 | A1F = A0 | B1000 = A0 |
|---|---:|---:|---:|
| 고정 입력 120개(시험, 두 ctype) | 64/64, recall@5 0.956, nDCG@5 0.771 | - | - |
| 1만 | 64/64 | 64/64 | 35/64 |
| 10만 | 64/64 | 64/64 | 7/64 |
| 30만 | 64/64 | 64/64 | 2/64 |

비둘기집 조건은 빈도와 무관하게 성립하므로 A2의 결과 집합은 A0와 같다(위 표는 그 확인이다). 규모 카탈로그에는 라벨이 없는 합성 상품도 정답일 수 있어 recall 값 자체는 비교하지 않고 A0와 같은지만 본다.

### 지연과 읽은 양 (부하 4~12, 번갈아 측정, 384 표본)

| 규모 | 방식 | p50 ms | p95 ms | 버퍼 평균 | 힙에서 읽은 행 평균 / 최대 |
|---|---|---:|---:|---:|---:|
| 1만 | A0 | 6.4 | 26.2 | 1,579 | 1,524 / 8,547 |
| 1만 | A2 | 2.1 | 12.3 | 1,241 | 486 / 2,483 |
| 10만 | A0 | 64.2 | 271.0 | 18,346 | 15,114 / 85,148 |
| 10만 | A2 | 20.5 | 131.2 | 14,699 | 4,826 / 24,821 |
| 30만 | A0 | 201.3 | 851.0 | 54,903 | 45,311 / 255,218 |
| 30만 | A2 | 64.8 | 475.1 | 43,836 | 14,371 / 74,745 |

순차 측정(부하 72→14, 320 표본)의 30만 값: A0 p50 232.9 / p95 1,249.8, A2 77.8 / 652.9, A1F 64.0 / 429.2, B1000 14.0 / 26.7. 계획 시간은 A2가 0.4~0.8 ms로 A0보다 0.2~0.5 ms 길다(`pg_stats` 조회).

- 힙에서 읽는 행이 약 3.1배 줄고 p50이 약 3.1배 줄었다. 시간은 후보마다 겹침 수를 세는 CPU가 대부분이고, 버퍼는 20%만 준다(후보가 줄어도 30만 행이 힙 전체에 흩어져 있어 읽는 페이지는 덜 준다).
- A1F(정확 빈도)는 A2와 읽은 행이 거의 같다(30만 평균 14,335 대 14,371). `pg_stats` 목록(기본 통계 목표에서 1,000개)만으로도 정확 빈도와 거의 같은 probe가 나왔다. 빈도 테이블과 쓰기마다의 유지 비용(V17)을 둘 이유가 없다.
- B1000은 가장 빠르지만 30만에서 상위 5건이 62/64 질의에서 달라진다. 기각.

### 남는 느린 질의 (30만, p50 ms, 읽은 행)

| 질의 | A0 | A2 |
|---|---|---|
| 검은색 운동화 | 1,047.6 / 152,296 | 697.2 / 61,530 |
| 사무용 의자 | 1,273.8 / 255,218 | 405.1 / 33,580 |
| 나이키 운동화 | 730.3 / 113,645 | 592.3 / 74,745 |
| 블루투스 키보드 | 862.4 / 167,224 | 281.3 / 41,135 |

두 단어 질의에서 두 단어가 모두 흔하면 probe도 흔한 n-gram만 남는다. "검은색 운동화"는 n-gram 8개, `min_hits` 4라 "검은색"만 가진 상품도 조건을 채운다. 이 행들은 실제로 조건을 만족하므로 가지치기로는 더 줄지 않고, 줄이려면 관련도 규칙(40% 문턱)이나 상위 K 조기 종료를 바꿔야 한다. 이번 범위 밖이고 ADR-0109 재검토 조건에 적었다.

## 변이 점검

`ProductSearchRelevanceIntegrationTest`는 `ANALYZE` 뒤(probe가 통계로 고르는 상태) 두 ctype에서 (1) recall@5 0.956·nDCG@5 0.771 고정, (2) 질의마다 전체 결과(최대 1,000행)를 `&& probe.grams`를 `&& q.grams`로 바꾼 원래 식과 대조, (3) probe 크기가 `n − min_hits + 1`, (4) probe가 고른 n-gram의 빈도가 고르지 않은 n-gram의 최소 빈도 이하인지 본다.

| 변이 | 결과 |
|---|---|
| M0 main의 SQL(probe 없음) | ✓ 실패: probe 식이 없음 |
| M1 probe 하나 적게(`n − min_hits`) | ✓ 실패: "운동화" probe 크기 3 기대, 2 |
| M2 가장 흔한 n-gram부터 고름 | ✓ 실패: "운동화" probe의 `화 `가 고르지 않은 n-gram보다 흔함 |
| M3 probe = 모든 n-gram(가지치기 없음) | ✓ 실패: "운동화" probe 크기 3 기대, 4 |
| M5 후보 30행 상한 | ✓ 실패: "검은색 운동화" 전체 결과가 원래 식과 다름 |

수정 코드로는 통과한다(두 ctype에서 probe n-gram 303/446개, recall@5 0.956, nDCG@5 0.771).

## 한계

- 합성 카탈로그다. 어휘가 고정이라 서로 다른 n-gram이 4,130개에서 멈추고, 실제 상품명의 고유명사·오탈자·긴 설명은 없다.
- 한 호스트의 컨테이너 하나에서 잰 값이다. 잠금 동안에도 다른 작업 부하가 있어(load1 3~72) 절대값보다 같은 조건에서 번갈아 잰 배율을 근거로 쓴다.
- 가격 필터를 준 질의는 재지 않았다(후보 조건 뒤의 EXISTS라 후보 수가 줄면 같은 비율로 준다고 보지만 확인하지 않음).
- `pg_stats`가 없으면(ANALYZE 전) probe는 이름순으로 골라 덜 줄인다. 결과는 같다. 이 경우의 지연은 재지 않았다.

## 재현

1. V1~ 마이그레이션을 적용한 데이터베이스에서 `psql -v n=300000 -f atlas-application/src/test/resources/search/product-search-relevance.sql -f load-tests/catalog-search/product-search-scale.sql`(한 세션).
2. `VACUUM ANALYZE product; VACUUM ANALYZE product_channel_availability;`
3. `ProductRepository.searchPublic`의 SQL 문자열을 변형별로 `INSERT INTO bench_variant VALUES ('A2', '<SQL>')`. A0는 main(e2d5217e)의 같은 문자열이다.
4. 측정 잠금을 쥐고 `SELECT bench_run('t', 'A0', 3); SELECT bench_run('t', 'A2', 3);`를 두 번 번갈아 실행한 뒤 `SELECT * FROM bench_report('t', 'A0');`
