# EXP-078: relay lease를 쥔 application이 죽으면 회복이 lease 길이에 비례하는가

- 질문: Kafka가 멈춰 있는 동안 relay lease를 쥔 application이 죽으면, 이벤트 전달이 재개되기까지의 시간이 `lease-duration`에 달려 있는가? [EXP-072](EXP-072-kafka-outage-relay.md)는 이를 "lease 만료를 기다린 것"으로 해석했을 뿐 보유자를 확인하지 못했고 길이를 바꿔 보지 않았다.
- 상태: 탐색 실험. lease 길이당 n=2, 로컬 단일 호스트. **하네스는 저장소에 올리지 않았다**([EXP-071](EXP-071-production-like-fault-injection.md)과 같은 스택과 이유).
- 날짜: 2026-11-25
- 관련: [EXP-072](EXP-072-kafka-outage-relay.md), [ADR-0067](../02-decisions/adr/ADR-0067-event-log-kafka-relay.md)

## 방법

- 스택은 EXP-072와 같다(nginx, application 2대, Kafka 1대, 풀 10). 두 application의 `lease-duration`을 15초, 30초, 60초로 바꿔 각각 새로 띄우고 설정이 반영됐는지 컨테이너 환경 변수로 확인했다.
- EXP-072에서는 한 application만 죽여 보유자가 누구인지 몰랐다. 이번에는 **두 application을 모두 죽여** 보유자가 반드시 죽도록 했다. 순서: 부하 시작 15초 뒤 Kafka `pause` → 2초 뒤 두 application `kill` → 죽이는 순간 DB에서 lease 남은 시간을 읽음 → 3초 뒤 두 application `start`, 건강해질 때까지 대기 → 시작 45초에 Kafka `unpause`.
- 부하는 초당 30건 신규 예약 70초. 회복 시간은 `unpause`부터 relay lag(이벤트 로그 최대 seq에서 cursor를 뺀 값)이 50 이하가 될 때까지이고 2초 간격 표본이다.

## 결과

| lease | 죽이는 순간 lease 남은 시간 | 계산한 만료 시각 | unpause | unpause 뒤 lag ≤ 50까지 | 중복 | 누락 |
| --- | --- | --- | --- | --- | --- | --- |
| 15초 | 12.7, 12.7초 | 29.7, 29.7초 | 45.6, 45.4초 | 0.2, 0.4초 | 7, 4 | 0, 0 |
| 30초 | 27.6, 27.7초 | 44.6, 44.8초 | 45.5, 45.5초 | 0.2, 0.3초 | 10, 12 | 0, 0 |
| 60초 | 57.6, 57.6초 | 74.7, 74.7초 | 45.5, 45.1초 | **33.6, 33.9초** | 7, 5 | 0, 0 |

- 계산한 만료 시각 = 죽인 시각(타임라인 기록 17.0~17.1초) + 죽이는 순간의 lease 남은 시간. 시작을 기준으로 한 초 단위다.
- **60초 lease에서만 만료가 `unpause`보다 늦어 회복이 지연됐다.** 만료(74.7초)와 lag ≤ 50이 된 첫 표본(79.1초, 79.0초)의 차이가 4.3~4.4초이고 표본 간격이 약 4초이므로 만료 직후 첫 표본에서 회복을 본 것과 일치한다. 15초와 30초에서는 만료(29.7초, 44.6~44.8초)가 `unpause`(45.1~45.6초)보다 앞서 회복이 즉시였다.
- 죽이는 순간 lease 남은 시간이 lease 길이보다 약 2.3초 적다(15에서 12.7, 30에서 27.6, 60에서 57.6). Kafka를 멈춘 지 2초 뒤라서, relay가 `pause` 직후 시작한 전송에서 lease를 쥐고 막혀 있었다는 해석과 맞는다.
- 모든 실행에서 이벤트 누락 0이었다. 중복 4~12건은 `pause` 때문이다([EXP-072](EXP-072-kafka-outage-relay.md)).
- 클라이언트 응답은 이 실험의 관찰 대상이 아니다. 두 application이 13.2~16.4초 동안 모두 내려가 있어 `502`가 460~496건(22~24%)이었고 lease 길이와 관계가 없다.

## 이 결과가 증명하는 것과 아닌 것

- 증명한 것: 보유자가 죽고 Kafka가 멈춰 있는 이 조건에서, 전달 재개 시각은 `max(Kafka 복구 시각, lease 만료 시각)`로 설명된다. lease가 길수록 재개가 늦어질 수 있고, 60초에서는 약 34초 지연됐다.
- 증명하지 못한 것:
  - lease가 실제로 만료에 의해 풀렸다는 것은 DB에서 직접 확인하지 않았다. 만료 시각의 계산과 회복 시각의 일치라는 정황이다.
  - lease가 binding이 되는 점은 60초 하나뿐이다. "비례"라고 쓸 수 있는 근거는 한 점과 두 점(15, 30)의 부재이며, 선형 관계를 증명하지 않는다.
  - 설정 문서가 요구하는 "lease는 전송 제한(10초)보다 5초 이상 길게"의 경계(15초)는 시험했지만, 그보다 짧은 lease에서 두 replica가 동시에 전송해 중복이 늘어나는지는 시험하지 않았다(설정 검증이 막는다고 가정했다).
  - 죽인 시점을 lease 획득 직후로 맞춘 최악 조건이다. Kafka가 정상일 때는 lease를 쥐는 시간이 짧아([EXP-072](EXP-072-kafka-outage-relay.md)) 이 지연이 나타나지 않는다.
  - n=2, 단일 호스트이고 표본 간격이 4초라 4초보다 작은 차이는 구별할 수 없다.

## 후속 제안(적용하지 않음)

- 기본값 30초가 맞는지 판단하려면 Kafka 장애 중 application 사망이 얼마나 자주 겹치는지 운영 데이터가 필요하다. 지금 근거만으로 값을 바꾸지 않는다.
- 만료 지연을 줄이는 방안 후보: 전송 제한과 lease를 함께 줄이는 것(제약 `lease >= 전송 제한 + 5초`). 효과와 중복 증가는 측정하지 않았다.
