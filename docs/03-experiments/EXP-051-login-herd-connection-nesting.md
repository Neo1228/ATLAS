# EXP-051: 로그인 폭주에서 먼저 무너지는 것과 필요한 대응

**추적 이슈:** [#464](https://github.com/Neo1228/ATLAS/issues/464)
**상태:** 로컬 단일 노드 실측 완료 · 운영 capacity 주장 아님

## 목적

한정 판매가 열리는 순간 구매자가 한꺼번에 몰리면 ATLAS에서 무엇이 먼저 무너지는지 실제 앱과 실제 PostgreSQL로 확인한다. Redis나 Kafka 같은 추가 저장소·로그가 정말 필요한지는 결론을 정해 두지 않고 이 측정으로 판단한다.

## 배경 사례에서 가져온 가설

- 인도 철도 예약(IRCTC Tatkal)처럼 정해진 시각에 모두가 로그인부터 동시에 시도하는 구조는 예약 로직이 아니라 인증 진입점이 먼저 포화된다.
- 알리바바의 핫 행 업데이트 사례처럼, 저장소를 바꾸기 전에 대기가 어디서 쌓이는지(행 락, 연결, CPU)를 먼저 확인해야 한다.

ATLAS에 대입한 가설: 판매 시작 직후 로그인이 비밀번호 해시(PBKDF2)의 CPU 때문에 먼저 포화될 것이다.

## 방법

- 앱: 현재 main의 jar(JDK 25). PostgreSQL 18.6은 별도 일회용 컨테이너, 앱·k6·DB가 같은 호스트(Apple M3 Pro 11코어, 18 GiB)에서 실행됐다. 호스트는 Docker VM 등 다른 부하가 있어 완전히 비어 있지 않았다.
- 부하: k6 open-loop constant-arrival-rate, 단계당 20초, 인증된 400개 구매자 계정으로 올바른 비밀번호 로그인. 별도로 초당 5건의 `GET /api/products?limit=20`을 함께 보내 무관한 읽기가 받는 영향을 봤다. 모든 단계에서 `dropped_iterations`가 0이어서 생성기가 느려진 구간은 없다.
- 한도 회피: 요청마다 다른 `X-Forwarded-For`를 보내 출처 한도(`origin-limit`)가 아니라 로그인 경로 자체를 측정했다.
- 오염 제외: 같은 호스트에서 Gradle 빌드가 겹친 구간의 단계는 모두 제외하고 깨끗한 재실행만 사용했다.
- 재계산: 아래 표의 로그인 성공 수와 지연은 k6 원시 점(point) 스트림에서 다시 집계해 보고서의 수치와 일치함을 확인했다.

## 결과: 기본 설정 (Hikari 풀 10, Tomcat 40 스레드)

| 초당 요청 | 전송 | 성공(HTTP 200) | 실패 | 성공 p50 / p95 |
|---:|---:|---:|---|---:|
| 25 | 501 | 501 | 0 | 117 / 163 ms |
| 40 | 801 | 801 | 0 | 101 / 141 ms |
| 50 (첫 실행) | 1,001 | 1,001 | 0 | 81 / 100 ms |
| 50 (반복 3회) | 약 1,000 | 22 / 37 / 259 | 500과 timeout | 보고서 집계 |
| 100 | 2,001 | 83 | 500 1,462 · timeout 456 | 4,993 / 9,417 ms |
| 200 | 4,000 · 4,001 | 36 · 39 | 500 828~861 · timeout 3,101~3,136 | 3.5~5.8 s |

- 초당 40건까지는 전부 성공하다가, 50건 부근에서 한 번 붕괴하면 성공이 초당 2~6건으로 떨어져 구간 내내 이어진다. 점진적 저하가 아니라 **이중 안정(bistable) 붕괴**다. 50건/초는 같은 조건에서 전부 성공한 실행과 1,000건 중 22건만 성공한 실행이 모두 나와, 이 지점의 결과는 확률이다.
- 붕괴 상태에서 실패는 HTTP **500**이다(503이 아님). 같은 풀을 쓰는 `GET /api/products`도 50~81%가 500이었다. 무관한 읽기까지 번지는 폭발 반경이다.
- PostgreSQL은 한가했다. 풀 10에서 `active`는 0~1이었고 연결 10개가 모두 `idle in transaction`이었다.

## 결과: 풀을 50으로 키움 (Tomcat 40 스레드는 그대로)

| 초당 요청 | 전송 | 성공 | 성공 p50 / p95 |
|---:|---:|---:|---:|
| 50 | 1,000 | 1,000 | 92 / 128 ms |
| 100 | 2,001 | 2,001 | 2,694 / 4,934 ms |
| 150 | 3,001 | 1,615 | 5,198 / 9,572 ms |
| 200 | 4,001 | 1,250 · 1,337 | 약 4.8~5.2 s |
| 300 | 6,001 | 977 | 5,270 / 9,525 ms |

붕괴가 사라지고 한계는 CPU로 옮겨 초당 약 75~80건(호스트 CPU 포화, 앱 약 750%)이다. 부하가 늘수록 처리량은 오히려 줄었다(150에서 약 81, 300에서 약 49). 클라이언트가 포기한 요청도 해시를 계속 계산하는 것으로 추정되지만 직접 계측하지는 않았다.

## 원인

기본 설정에서 먼저 무너지는 것은 CPU가 아니라 **연결 풀 고갈**이었다.

1. `AccountService.login`이 `@Transactional`이라 요청 전체에서 연결 1개를 쥔다.
2. 그 안에서 `AuthAttemptLimiter.tryAcquire`가 `REQUIRES_NEW` 독립 transaction으로 두 번째 연결을 요구한다.
3. 동시 로그인이 풀 크기(10)를 넘으면 모든 연결이 바깥 transaction에 잡힌 채 두 번째 연결을 기다려, `connection-timeout`(500ms)이 지날 때까지 서로를 막는다.
4. 스레드 덤프에서 36개 스레드가 `HikariPool.getConnection`에 막혀 있었고 PBKDF2 안에는 없었다. 로그에는 `Connection is not available, request timed out after 505ms (total=10, active=10, idle=0, waiting=41)`가 남았다.

인과의 근거는 풀을 50으로 키웠을 때 붕괴가 사라지는 절제(ablation)이며, 중첩 획득 경로만 따로 격리한 실험은 이 문서의 측정에는 없다. 대신 수정 PR의 회귀 테스트가 같은 가설을 직접 검증한다. 풀 크기를 1로 줄인 상태에서 로그인이 성공해야 하고, 수정 전 코드에서는 `CannotCreateTransactionException`으로 실패한다.

로그인 1건은 PBKDF2를 두 번 계산하고(약 40ms씩, 로그인 1건당 CPU 약 70~80ms) 그동안 연결을 쥐고 있었다. 같은 중첩 구조가 `registerBuyer`, `requestPasswordReset`, `requestEmailVerification`, `completeMfaLogin`에도 있다.

## Redis·Kafka·admission 상한이 해결하는 것

| 수단 | 이 붕괴에 대한 판단 | 근거 |
|---|---|---|
| Redis (한도 카운터 이전) | 필요하지 않다 | 연결 하나가 줄어 붕괴는 피하지만 transaction 범위 수정으로 같은 효과를 얻는다. PostgreSQL은 병목이 아니었고, CPU 한계(초당 약 75~80건)는 그대로다. 저장소가 둘로 나뉘면 정합성 경계와 장애 모드가 늘어난다. |
| Kafka | 해당 없음 | 로그인은 동기 요청·응답이라 큐를 앞에 두어도 같은 CPU 뒤에서 대기만 한다. |
| 동시 해시 수 상한(admission) | CPU 한계 구간에서 의미가 있다 | 상한이 없으면 클라이언트가 포기한 요청까지 해시를 계산해 처리량이 줄고 무관한 읽기가 느려진다. 별도 PR에서 측정과 함께 다룬다. |

즉 이번 측정이 가리킨 첫 번째 병목은 인프라 부족이 아니라 코드의 연결 중첩이었다. 공유 저장소나 로그가 필요해지는 조건은 여러 노드가 한도 카운터나 세션을 공유해야 할 때이며, 이 측정은 그 조건에 대한 증거를 갖고 있지 않다.

## 부수 발견

- 붕괴 상태에서 실패 요청마다 전체 스택 트레이스를 로그에 남겨, 한 번의 측정에서 로그가 555 MB(`GlobalExceptionHandler` ERROR 22,296건, 약 546 MB)까지 늘었다. 이미 실패 중인 앱에 디스크와 CPU 부하를 더한다.
- 풀 고갈이 `application.yml`의 주석(503으로 응답한다고 설명)과 달리 HTTP 500으로 노출된다.

## 한계 (정직하게)

- 로그인 엔드포인트 하나만 측정했다. 체크아웃, 주문, 재고 같은 실제 한정 판매의 쓰기 경로는 포함하지 않았다.
- 단일 노드다. 다중 replica, 같은 출처(NAT)에서 몰리는 경우의 `origin-limit` 거절과 `auth_origin_bucket` 행 경합은 측정하지 않았다.
- 기본 풀 단계는 1~3회 반복이어서 50건/초 같은 경계 지점은 점이 아니라 확률이다.
- 카탈로그 edge cache를 앞에 두지 않았다. 풀 50 구간에서 무관한 읽기가 느려진 정도(예: 100건/초에서 p50 약 2.2초)는 Tomcat 40 스레드가 해시에 점유된 결과다.
- 수정 후 같은 부하에서 붕괴가 사라지는지는 이 문서에 포함되지 않았고 별도로 재측정해야 한다.
