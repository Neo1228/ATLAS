# EXP-076: shard 가중치는 얼마나 예측하고, 어떤 균형 방식과 shard 개수가 나은가

- 질문: [EXP-069](EXP-069-ci-shard-imbalance.md)는 같은 클래스의 시간이 실행마다 흔들린다는 것까지 좁혔다. 그렇다면 한 번의 실측으로 만든 가중치는 얼마나 틀리고, 다회 실측과 다른 균형 방식으로 최대 shard 시간을 줄일 수 있는가? shard 개수는 지금(4개)이 맞는가?
- 상태: 조사와 시뮬레이션. 실제 CI에서의 효과는 마지막 절에 따로 적었다. **확정한 것, 모형으로 추정한 것, 확인하지 못한 것을 구분해 적었다.**
- 날짜: 2026-11-24
- 관련: [ADR-0070](../02-decisions/adr/ADR-0070-parallel-backend-ci.md), [ADR-0074](../02-decisions/adr/ADR-0074-shard-weights-from-recent-runs.md), [EXP-030](EXP-030-ci-build-duration.md), [EXP-069](EXP-069-ci-shard-imbalance.md), Issue #599

## 문제

앱 테스트 shard 4개 중 가장 느린 shard가 전체 CI 시간을 정하는데, 그 shard의 클래스 시간 합이 실행마다 126~241초로 흔들리고 가중치는 한 번의 실측으로 만들어 사람이 기억해서 갱신한다.

## 데이터와 조건

- 대상: 2026-11-23 11:39 ~ 2026-11-24 11:37(UTC) Backend CI 성공 실행 중 application 테스트 4개 shard가 모두 성공하고 `CLASSTIME` 줄이 있는 실행. 스크립트 기준 112회(shard job 448개), 별도 시뮬레이션 하네스 기준 111회다(수집 시각이 달라 실행 하나가 더 들어왔다). 브랜치 48개, PR 실행 64회와 push 실행 47회(하네스 기준). runner는 `ubuntu-latest`다.
- 수집: `gh api .../actions/runs/<id>/jobs`의 job 시간과 `.../jobs/<id>/logs`의 `CLASSTIME <클래스> <초>` 줄. 중첩 클래스는 바깥 클래스에 합쳤다.
- **한계**: 24시간 동안의 표본이다. 같은 PR의 재실행과 같은 커밋 주변의 실행이 섞여 실행끼리 독립이 아니다. 아래 표준편차와 차이는 실행을 독립으로 본 값이라 실제 불확실성은 더 크다. 하루 사이에 코드가 계속 바뀌어(사실 3) 한 시점의 결론이 아니라 이 24시간의 결론이다.
- "최대 shard 시간"은 **그 shard에 배정된 클래스 시간의 합**이다. 두 fork로 겹쳐 실행되므로 이 합은 실제 소요 시간이 아니다(EXP-069 사실 4). 합과 실제 시간의 관계는 사실 4에서 쟀다.

## 측정한 사실

### 1. 현재 가중치 파일은 균형을 예측하지만 실제는 균형이 아니다

수정 전 main의 가중치 파일(클래스 110개, 합 840초)로 LPT 배정을 하면 4개 shard 모두 **210초**다. 같은 배정을 실측 111회에 적용하면 다음과 같다.

| shard | 1 | 2 | 3 | 4 |
| --- | ---: | ---: | ---: | ---: |
| 파일이 예측한 클래스 시간 합(초) | 210 | 210 | 210 | 210 |
| 실측 평균(초) | 221 | 165 | 203 | 158 |
| 가장 느린 shard였던 실행 수 | 57 | 7 | 34 | 13 |

- 최대/평균은 1.238, 최대 shard 평균 231초다(실행 당시 배정으로 잰 값도 230.8초로 같다. 파일의 배정과 실제 배정이 같은지는 사실 5에서 확인했다).
- 실행마다 파일에 없는 클래스가 평균 12.8개(시간 69초, 합의 9%)이고 이름 해시로 배정된다.
- 파일 값과 실측 평균(클래스가 나온 실행 비율을 곱함)의 차이를 shard별로 더하면 shard 2는 -45초, shard 4는 -51초, shard 1은 +11초, shard 3은 -7초다. shard 2와 4가 가벼운 것은 파일이 **한 번의 실행에서 비싸게 나온 클래스를 크게 잡았기** 때문이다(`CheckoutAmountOverflowIntegrationTest` 31초에서 평균 3초, `RemoteReservationCheckoutIntegrationTest` 39초에서 13초, `InventoryLockWaitIntegrationTest` 22초에서 5초). shard 3이 무거운 것은 파일에 없는 `LocationFaultConvergenceIntegrationTest`(평균 44초)가 해시로 이 shard에 배정됐기 때문이다(+42초). 한 번 실측 가중치가 일회성 비싼 구간을 클래스의 성질로 기록한다는 뜻이다.
- 가장 느린 shard job(큐 대기 포함)은 평균 189초, 중앙값 189초, 표준편차 18초, p90 208초다.

### 2. 클래스 시간은 두 종류로 나뉘고 흔들림은 일부 클래스에 몰려 있다

실행 111회에서 클래스 142개를 쟀다(평균 기준 큰 순).

| 클래스 | 평균(초) | 표준편차(초) | 최소~최대(초) |
| --- | ---: | ---: | ---: |
| `SplitAllocationCheckoutIntegrationTest` | 53.6 | 10.9 | 46.0~80.4 |
| `LocationFaultConvergenceIntegrationTest` | 43.6 | 3.1 | 37.4~50.3 |
| `BuyerFlowIntegrationTest` | 42.1 | 4.7 | 32.3~51.6 |
| `SellerCouponRedemptionIntegrationTest` | 33.2 | 3.6 | 25.5~44.4 |
| `FxRateCallCostIntegrationTest` | 14.8 | 13.3 | 2.0~33.0 |
| `InventoryFlashSaleContentionIntegrationTest` | 18.1 | 11.5 | 3.6~36.8 |
| `CatalogIntegrationTest` | 15.6 | 10.3 | 3.1~34.0 |

- 큰 클래스 대부분(`LocationFault...`, `BuyerFlow...`, `SellerCoupon...`)은 표준편차가 평균의 10% 안팎으로 안정적이다. 위 표 아래쪽 클래스는 평균과 표준편차가 비슷한 **2~4초 또는 20~35초** 모양이다(EXP-069 사실 5와 같은 현상).
- 클래스별 분산의 합 중 상위 12개 클래스가 65%를 차지한다. 클래스가 서로 독립이라고 보고 분산을 더하면 shard 합의 표준편차는 25.7초이고(전체 합은 51.5초), 실측한 shard 합 예측 오차(RMSE)는 26.8초(아래 표, 평균 가중치)로 비슷하다. **흔들림은 클래스마다 독립으로 흔들리는 성격이고, 어느 가중치를 쓰든 그만큼은 남는다.**

### 3. 흔들리는 시간은 클래스가 아니라 시점을 따라 옮겨 다닌다

시간순으로 앞 55회와 뒤 56회의 클래스별 평균을 비교했다. 전체 합이 808초에서 742초로 줄었고, 가장 크게 바뀐 클래스는 다음과 같다.

| 클래스 | 앞 절반 평균(초) | 뒤 절반 평균(초) |
| --- | ---: | ---: |
| `FxRateCallCostIntegrationTest` | 3.3 | 26.1 |
| `CheckoutCancelWithoutAttemptIntegrationTest` | 19.0 | 3.9 |
| `AuthAttemptLimiterIntegrationTest` | 18.7 | 3.9 |
| `LoginConnectionPoolIntegrationTest` | 18.6 | 5.2 |
| `ProductCategoryHierarchyIntegrationTest` | 17.9 | 4.6 |
| `InventoryCapacityAdjustmentIntegrationTest` | 10.7 | 21.7 |

15~20초짜리 "비싼 구간"이 다른 클래스로 옮겨 갔다. EXP-069가 본 "앞선 클래스의 컨텍스트가 남아 있을 때 비싸다"와 맞지만, 왜 옮겨 갔는지(같은 기간에 병합된 테스트 변경인지 배정 변화인지)는 이 데이터로 가를 수 없다. 확인하지 못했다. 결과로 **가중치는 시간이 지나면 낡는다**: 오래된 실행을 많이 섞어도 나아지지 않는다(아래 시간순 분할).

### 4. 클래스 시간 합과 job 시간의 관계

shard job 448개(실행 112회)에서 최소제곱 회귀한 값이다.

| 대상 | 식 | R² | 잔차 표준편차 |
| --- | --- | ---: | ---: |
| shard job 전체 시간 | 68초 + 0.503 x 클래스 시간 합 | 0.59 | 약 15초 |
| `Run application tests` step | 47초 + 0.54 x 클래스 시간 합 | 0.66 | 14초 |

- 기울기 0.5는 `ATLAS_TEST_FORKS=2`로 두 fork가 겹치는 것과 맞다.
- shard마다 드는 고정 시간은 직접 잰 값으로 `Set up job` 2초, checkout 1초, Gradle 설정 4초, `docker info` 1초(중앙값 합 약 9초), 테스트 시작 전 Gradle 기동과 컴파일 23초(표본 268개), 합계 약 32초다. 회귀의 절편 68초와 32초의 차이 약 36초는 **테스트 단계 안의 클래스 시간으로 잡히지 않는 시간**(이미지 확보, fork 기동, 마지막 클래스를 기다리는 시간 등)으로 추정하며 원인은 확인하지 못했다.
- 실행 30회만으로 회귀하면 절편 53초, 기울기 0.567로 달랐다. 절편은 클래스 시간 0으로 외삽한 값이라 불안정하며, 표준오차는 112회 기준 약 3.8초다.

### 5. 이 스크립트의 LPT는 실제 배정과 같다

무작위로 고른 CI 실행 14회에 대해 그 실행의 커밋에 있던 가중치 파일로 파이썬 LPT(동률은 이름순, 가장 앞 shard)와 해시(`String.hashCode`의 `floorMod`)를 돌려, 로그에 남은 shard별 클래스 목록과 비교했다. **14회 모두 완전히 같았다.** 그래서 스크립트의 shard 예측은 `TestShardFilter`가 실제로 하는 배정과 같다(표본 14회).

## 가설과 검증

### H1. 한 번의 실측보다 다회 평균이 예측과 균형이 낫다

가중치를 훈련 실행으로 만들고 **다른** 검증 실행의 shard 합과 비교했다. 아래는 실행을 무작위로 반으로 나눠(훈련 55, 검증 56) 300회 반복한 결과다. 같은 PR의 재실행이 양쪽에 섞여 낙관적이다.

| 가중치 | 최대/평균 | 최대 shard 합 평균(초) | shard 합 예측 오차 RMSE(초) | 예측 편향(초) | 클래스 하나의 예측 오차 RMSE(초) |
| --- | ---: | ---: | ---: | ---: | ---: |
| 이름 해시(ADR-0070 이전) | 1.632 | 304.4 | - | - | - |
| 한 번 실측(지금 방식) | 1.184 | 221.0 | 36.2 | -5.1 | 6.98 |
| 중앙값 5회 | 1.174 | 219.2 | 34.0 | -13.1 | 6.08 |
| 중앙값 20회 | 1.168 | 218.1 | 35.3 | -20.1 | 5.60 |
| 평균 5회 | 1.158 | 216.1 | 28.9 | -0.8 | 5.35 |
| 평균 20회 | 1.151 | 214.9 | 26.8 | 0.5 | 5.00 |
| 평균 훈련 전체(55회) | 1.144 | 213.6 | 25.6 | 0.2 | 4.92 |
| 검증 실행 자신의 시간(상한) | 1.000 | 186.6 | - | - | - |

- **평균이 중앙값보다 낫다.** 중앙값은 shard 합을 13~20초 낮게 잡는다(편향). 2~4초와 20~35초를 오가는 클래스의 중앙값은 낮은 쪽이라 기대 시간을 과소평가하고, shard 합은 기대값의 합이기 때문이다. 과제가 제안한 "중앙값 가중치"는 이 데이터에서 기각했다.
- 평균 20회는 한 번 실측보다 shard 합 예측 오차를 36.2초에서 26.8초(26% 감소)로 줄였다. 그러나 그 오차는 사실 2의 독립 잡음 25.7초와 같은 크기라 평균을 더 늘려도 거의 줄지 않는다(5회 28.9, 55회 25.6).

### H2. 균형 효과가 방식에 따라 유의미하게 다르다

실행을 브랜치 단위로 반으로 나눠(훈련 약 76, 검증 약 35) 60회 반복했다(같은 PR이 양쪽에 섞이지 않는다).

| 방식 | 최대/평균 | 최대 shard 합 평균(초) | 검증 안에서의 표준편차(초) |
| --- | ---: | ---: | ---: |
| 이름 해시 | 1.628 | 304.1 | 29.8 |
| 한 번 실측 + LPT(지금) | 1.179 | 220.4 | 22.5 |
| 중앙값(전체) + LPT | 1.167 | 218.2 | 23.4 |
| 평균 3회 + LPT | 1.165 | 217.9 | 21.6 |
| 평균 10회 + LPT | 1.156 | 216.1 | 21.6 |
| 평균(전체) + LPT | 1.143 | 213.7 | 21.6 |
| 훈련 실행에 직접 최적화(아래) | 1.104 | 206.3 | 18.5 |
| 검증 실행 자신의 시간으로 LPT(상한) | 1.000 | 187.0 | 14.1 |

- 해시와 LPT 계열의 차이(약 85초)는 크다. **LPT 계열끼리의 차이는 작다**: 한 번 실측에서 평균 전체까지 6.7초(3%)이고 표준편차 22초에 비해 작다.
- 상한과의 차이 약 27초는 가중치로 줄일 수 없는 클래스별 잡음(사실 2)이다.

실행을 시간순으로 앞 절반에서 만들고 뒤 절반으로 검증하면(1회 분할이라 표본이 작다) 결과가 다르다.

| 방식 | 최대/평균 | 최대 shard 합 평균(초) |
| --- | ---: | ---: |
| 한 번 실측 + LPT(훈련에서 무작위 1회, 30회 반복) | 1.195 | 220.3 |
| 중앙값(훈련 전체) + LPT | 1.263 | 233.7 |
| 평균 3회 + LPT | 1.174 | 216.4 |
| 평균 10회 + LPT | 1.173 | 216.3 |
| 평균(훈련 전체) + LPT | 1.205 | 222.4 |

오래된 실행을 전부 섞은 평균이 최근 몇 회만 쓴 평균보다 나쁘고, 중앙값은 가장 나쁘다. 사실 3의 이동 때문이다. 실제 사용 방식(오래된 것으로 만들고 이후 실행에 쓴다)에 더 가까운 **앞으로 걷는 검증**을 했다. 실행을 시간순으로 놓고 시점 12곳에서, 그 시점 이전 실행 N회로 가중치를 만들어 이후 20회에 적용했다(검증 구간이 겹쳐 독립이 아니다).

| 방식 | 최대/평균 | 최대 shard 합 평균(초) |
| --- | ---: | ---: |
| 직전 1회 + LPT(지금) | 1.145 | 210.6 |
| 평균 3회 | 1.151 | 211.4 |
| 평균 10회 | 1.122 | 206.2 |
| 평균 20회 | 1.133 | 208.5 |
| 평균 30회 | 1.128 | 207.2 |
| 평균 40회 | 1.147 | 210.8 |
| 중앙값 10회 | 1.129 | 207.6 |
| 중앙값 30회 | 1.160 | 213.4 |
| 평균 이전 전체 | 1.140 | 209.7 |
| 검증 실행 자신의 시간(상한) | 1.000 | 184.0 |

**방식을 가르는 데이터는 부족하다.** 10~30회 평균이 가장 낮지만 직전 1회와의 차이는 3~4초로 표준편차(16~24초)보다 작고, 표본이 24시간이다. 위 세 가지 검증이 서로 다른 순위를 보였다(예: 스크립트의 112회 검증에서는 직전 1회 209초가 평균 214초와 중앙값 220초보다 낮았고, 최근 30회 검증에서는 평균 202초가 직전 1회 206초보다 낮았다). 확실한 것은 다음 두 가지다.

1. **낡은 가중치는 분명히 나쁘다.** 수정 전 main의 파일은 가장 새 37회에서 최대 shard 합 225.6초(최대/평균 1.208), 111회 전체에서 230.7초(1.238)였고, 최근 실행으로 만든 가중치는 같은 구간에서 209~214초다(스크립트 출력, 직전 1회와 평균).
2. 최근 10~30회 평균은 단일 실행이나 중앙값보다 같거나 낫고 한 번도 크게 나쁘지 않았으며, 중앙값은 두 검증에서 가장 나빴다.

### H3. 더 복잡한 방식(국소 탐색, 훈련 실행에 직접 최적화)은 유의미하게 낫다

훈련 실행 전체에 대해 "최대 shard 합의 평균"을 직접 줄이도록 클래스를 하나씩 옮기거나 둘씩 바꿨다(6000회 시도, 파이썬 약 30줄). 평균 LPT 대비 검증 구간의 최대 shard 합은 브랜치 분할 -7.4초(213.7에서 206.3), 앞으로 걷는 검증 -4.5초(207.3에서 202.7, 시점 12곳 중 10곳에서 개선)다. 순수 LPT 위의 단순 국소 탐색(평균 가중치 20회, 시간순 분할 1회)은 -1.6초로 더 작았다.

**채택하지 않았다.** 이유는 세 가지다. (1) 개선이 4~7초(클래스 시간 합 기준)이고 job 시간으로는 기울기 0.5를 곱해 2~4초다. 실행 간 표준편차 18~25초에 묻힌다. (2) 결과가 클래스별 가중치가 아니라 클래스별 shard 번호 목록이라 `TestShardFilter`의 형식과 shard 개수 고정이 바뀐다. (3) 사실 3의 이동 때문에 한 시점의 시간 상관 구조에 맞춘 배정은 쉽게 낡는다(시간순 분할에서 이득이 하네스 구현에 따라 -3.8초와 -12.1초로 달랐다).

## shard 개수

사실 4의 모델(job = 68초 + 0.503 x 클래스 시간 합)과 평균 가중치 LPT의 검증 구간 최대 shard 합으로 계산했다. `--shard-counts 3,4,5,6`으로 재현한다. **큐 대기, 변경 감지, 판정 job을 뺀 shard job만의 값이고, 실제 CI에서 재지 않은 모형 추정이다.**

| shard 수 | 최대 shard 클래스 시간 합(초) | 가장 느린 job(초) | shard job 합계(분) | 직전 개수 대비 |
| ---: | ---: | ---: | ---: | --- |
| 3 | 280 | 209 | 9.7 | |
| 4 | 214 | 176 | 10.8 | 33초 단축, 1.1분 증가 |
| 5 | 175 | 157 | 12.0 | 19초 단축, 1.2분 증가 |
| 6 | 153 | 145 | 13.1 | 12초 단축, 1.1분 증가 |

- shard를 하나 늘릴 때마다 job 합계가 약 1.1분 늘고(고정 시간 68초), 줄어드는 시간은 33초, 19초, 12초로 빠르게 작아진다. 실측한 가장 느린 job(큐 포함 평균 189초)과 4개의 모형 값(176초 + 큐 2초 = 178초)은 11초 차이다. 현재 파일이 낡은 탓(사실 1)으로 해석하지만 이 차이를 검증하지는 않았다.
- 모형이 못 담는 것: shard job은 클래스 시간 합과 별개로 잔차 표준편차 15초의 잡음이 있어, shard가 늘수록 가장 느린 것의 기대값이 올라간다(정규 분포로 가정한 추정으로 4개에서 5개 때 약 2초). 5번째 shard가 줄이는 19초는 이 잡음 안에 있다.
- 클래스 시간 합이 줄면(비싼 구간 수정) 절편 68초는 그대로라 최적 개수는 **줄어든다**. 지금 늘려도 그 수정 뒤에는 되돌려야 할 수 있다.
- **제안: 4개 유지.** 5개로 늘리는 이득은 모형으로 약 19초(전체 중앙값 204초의 약 9%)이고 비용은 job 합계 11% 증가다. 늘릴 때의 기준은 "다음 shard가 줄이는 시간이 한 실행의 잡음 표준편차(약 15~18초)보다 클 때"다. 4에서 5는 겨우 넘고 5에서 6은 넘지 않는다. 비싼 구간 수정이 병합되고 가중치를 다시 만든 뒤 `--shard-counts`로 다시 계산하면 된다. 매트릭스 변경은 요청하지 않았다.

## 확인하지 못한 것과 한계

- 24시간 표본이고 실행끼리 독립이 아니다. 가중치가 며칠에 걸쳐 얼마나 낡는지는 재지 못했다.
- 사실 3의 이동 원인은 확인하지 못했다. SlowTestForensics가 비싼 구간을 고치면 클래스 시간 분포가 바뀌므로 이 문서의 가중치 값과 shard 개수 모형은 그때 다시 만들어야 한다. 방식(평균, LPT)은 분포가 바뀌어도 유지되는지 같은 스크립트로 다시 확인한다.
- 절편 68초 중 36초의 정체를 확인하지 못했다. shard 개수 결론은 이 절편에 가장 민감하다.
- 모든 비교는 클래스 시간 합을 대리 지표로 썼다. 두 fork 사이의 배치(큰 클래스 하나가 한 fork를 오래 차지하는 경우)는 모형에 없다.
- 시뮬레이션의 방식 순위가 검증 방법에 따라 달랐다. 방식 선택의 근거는 "낡은 가중치를 피하는 것"이고 "평균이 중앙값이나 한 번 실측보다 확실히 낫다"가 아니다.
