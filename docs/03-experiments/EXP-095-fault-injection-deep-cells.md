# EXP-095: lease 2대·`pg_wal` 단독 가득 참·같은 key 동시 요청·DNS 부정 캐시·SYN/비대칭·DB `pause`에서도 예약 불변식은 지켜지는가

- 질문: [EXP-087](EXP-087-fault-injection-network-disk-multi-app.md)이 "증명하지 못한 것"으로 남긴 다섯 칸에서도 네 불변식(응답받은 예약 유실 0, order 대 location 수 일치, 중복 예약 0, 90초 안 수렴)이 유지되는가? 그리고 EXP-070의 정확히 10초 복구 지연은 실제 application 스택에서 일어날 수 있는가, 일어난다면 어떤 조건에서인가?
- 상태: **부분 실행.** "가설"과 "시험 가동 뒤에 추가한 가설"은 본 가동 전에 별도 커밋했다(커밋 이력이 증거). 계획한 121회(21개 조건 × n=5, DNS 2칸 n=3) 중 **결과가 있는 11개 실행만 끝냈고**(조건별 n=1) 나머지는 실행하지 않았다. 따라서 가설 대부분은 **판정하지 못했다**. 이 문서는 하네스와 n=1 관측, 그것이 보여 준 것과 보여 주지 못한 것을 적는다. 이슈 [#652](https://github.com/Neo1228/ATLAS/issues/652).
- 날짜: 2026-11-25
- 관련: [EXP-085](EXP-085-fault-injection-repeated.md), [EXP-087](EXP-087-fault-injection-network-disk-multi-app.md), [EXP-070](EXP-070-real-stack-fault-injection.md), [EXP-071](EXP-071-production-like-fault-injection.md), [EXP-078](EXP-078-relay-lease-length.md), [EXP-068](EXP-068-stage-evidence-map.md)(8단계 표), D-144, D-146

## 문제 한 문장

운영자가 lease를 줄이거나(수렴 꼬리 단축 목적) application을 2대 이상으로 늘리거나 DB 볼륨을 분리했을 때(`pg_wal` 별도 디스크는 흔한 구성) 돈·재고 불변식이 어떻게 되는지, 그리고 DB가 잠깐 내려갔다 올라온 뒤 application이 정확히 10초 더 늦게 복구되는 현상이 실제로 가능한지를 지금은 측정으로 답하지 못한다(EXP-087이 명시한 빈칸). 영향을 받는 것은 예약 API(`POST /api/internal/order-inventory/reservations`) 호출자와 이를 운영하는 사람이며, 현재까지 위반 사례는 0건이므로 아직 실제 피해가 보고된 것은 아니다(가정: 빈칸이 곧 위험은 아니다. 위험의 크기는 이 실험이 재는 대상이다).

## 읽고 확인한 사실과 한계 (설계 근거, 실행 결과 아님)

- 복구 lease 코드(`LocationReservationServiceImpl`, `LocationReservationConfiguration`): workflow 처리는 `lease_until = now + lease-duration`과 `lease_token`을 잡고 시작한다. 처리 중 lease는 남은 시간이 `lease/2` 미만이면 location을 호출하기 **전에** 갱신한다(`renewLeaseIfNeeded`). 모든 상태 쓰기는 `lease_token`을 조건으로 한다(펜싱). location 호출(`POST .../reservations`)은 `Idempotency-Key` 단위로 멱등이다. 설정 검증 규칙은 `lease/2 > connect-timeout + read-timeout + 1s`(기본값에서 `lease > 6.5s`)이며 기본 PT30S다.
- 따라서 두 인스턴스가 같은 workflow의 location을 호출하려면 한쪽이 lease를 쥔 채 `lease` 이상 멈춰 있어야 한다(JVM 정지, 프로세스 `SIGSTOP`, 긴 GC, VM 정지). 호출 하나는 최대 약 2.25초라서 보통의 느린 응답만으로는 만료되지 않는다.
- EXP-087은 lease PT10S·PT15S를 application 1대로만 쟀고, 디스크 가득 참은 데이터 디렉터리 전체 tmpfs 하나였고, 같은 key 재시도는 순차였으며, DNS는 부하 시작 전 유휴 시간과 `FAULT_FOR=0`(`kill` 직후 `start`, 이름이 사라지는 창이 약 0.13초)만 조작했다.
- 이 실험을 설계하기 전에 EXP-085·087의 결과를 이미 읽었다. 그래서 아래 예측은 그 결과의 영향을 받았다(독립적이지 않다).

## 측정 도구에 대한 사전 확인 (가설을 시험한 것이 아님)

설계가 가능한지 보려고 `none` 한 번과 보조 점검을 돌렸다. 확인한 것만 적는다: 하네스가 이 worktree에서 기동되는 것(application jar는 Docker VM이 읽는 `$HOME` 아래에 두어야 한다. `/tmp` 아래 jar는 컨테이너 안에서 "Invalid or corrupt jarfile"이었다), location JVM(Tomcat)의 access log를 `docker logs`로 볼 수 있다는 것(pattern에 시작·종료 epoch ms, 메서드, 경로, 상태, `Idempotency-Key` 포함), Colima VM에서 loop 마운트한 ext4 이미지를 bind 볼륨으로 컨테이너에 줄 수 있다는 것(128MiB, `dd`로 가득 채우면 `df` 100%). 이 점검의 결과는 어떤 가설의 증거로도 쓰지 않는다.

## 가설 (실행 전에 적음)

공통 판정: 한 불변식이라도 어긋나거나 아래 "반증" 조건이 관측되면 그 가설은 틀린 것이다. 틀린 가설은 지우지 않고 결과 절에 그대로 둔다. 표본 크기는 "힘" 열에 적는다. 조건별 n=5에서 위반 0건이면 실행 단위 위반율의 95% 상한은 `1-0.05^(1/5)=45%`(rule of three는 `3/5=60%`로 더 느슨)이므로 n=5는 드문 위반을 배제하지 못한다. 그래서 가능한 곳에서는 요청·workflow·쌍 단위 분모를 함께 적고 그 분모에 대한 상한(`3/N`)을 보고한다.

### (a) lease × application 2대

설정: application 2대(같은 order DB, 클라이언트 라운드 로빈, 복구 worker 둘 다 켜짐), 첫 인스턴스에서 location 구간에 `tc netem delay 400ms`(각 방향, workflow가 lease를 쥔 채 머무는 시간을 늘려 정지 시점의 노출 수를 키움), 부하 시작 3초 뒤 첫 인스턴스를 **`docker pause` 12초**(정지 길이 S=12초). lease L은 PT30S·PT15S·PT10S·PT7S(PT7S는 검증 규칙을 통과하는 가장 짧은 값 근처: `7/2=3.5 > 3.25`). 각 n=5.

측정: location access log에서 `Idempotency-Key`별 `POST /reservations` 호출 수와 **호출 출처 IP**(application 1·2·그 밖). "교차 인스턴스 중복"(xdup)은 같은 key가 서로 다른 application IP에서 호출된 key 수, "중복 호출"은 `Σ(호출−1)`, "이중 201"은 같은 key에서 201이 두 번 나온 key 수. 노출 E는 정지 직전 order DB의 비종결·lease 유효 workflow 수. 그리고 네 불변식.

| 가설 | 예측 | 반증 | 힘 | 이 가설이 정하는 결정 |
| --- | --- | --- | --- | --- |
| A1 불변식 | 모든 (L, S) 조건에서 네 불변식 통과, 이중 201 0 | 불변식 위반 1건 또는 이중 201 1건 | 조건별 n=5, 노출 합계 E를 보고하고 E에 대한 상한 `3/E` | 위반이 있으면 결함 이슈 분리, 펜싱 지점을 찾음 |
| A2 짧은 lease는 교차 인스턴스 중복을 만든다 | L=PT7S·PT10S에서 xdup≥1인 실행이 5회 중 4회 이상 | L=PT7S에서 xdup=0인 실행이 2회 이상 | n=5 | "2대에서 짧은 lease는 안전한가"의 답. 중복이 없으면 정지 모델이 두 인스턴스를 같은 workflow에 동시에 세우지 못한 것(전제 실패) |
| A3 긴 lease는 S=12초 정지에서 중복이 없다 | L=PT30S에서 xdup=0이 5/5. L=PT15S는 경계(정지 시점 lease 잔여가 `L−나이`, 나이는 최대 약 2.5초라 12.5~15초 > 12초)라 5회 중 4회 이상 xdup=0 | L=PT30S에서 xdup≥1 | n=5 | 임계는 "lease > 최대 정지 + 여유" 한 줄로 쓸 수 있는지 |
| A4 중복은 무해하다 | xdup>0인 실행에서도 location 예약 행은 order당 location당 1개, 이중 201 0, `counts_equal` 통과 | 위 A1과 같음 | A1과 같음 | lease 기본값. 위반 없이 중복만 있으면 기본 PT30S 유지(꼬리 비용이 중복 비용보다 큼은 D-146), 단 정지 허용 길이를 문서에 적음 |

대조군: (i) 무변경 대조군: 2대, 정지 없음, netem 400ms, L=PT7S, n=5. 예측: xdup=0, 불변식 통과. (ii) 음성 대조군(탐지기가 반응해야 함): 대조군 실행에서 부하 뒤 **호스트에서 location A로 이미 있는 key를 직접 한 번 더 POST**(출처 IP가 application과 다름)한다. 감사는 이 key를 "중복 호출 ≥1, 출처 IP ≥2"로 잡아야 한다. 잡지 못하면 이 하네스의 xdup=0은 무의미하다. (iii) 정지 노출 대조: L=PT10S, S=12초, **netem 없음**, n=5(노출 E가 작아도 같은 방향인지). (iv) before/after: lease 값만 다른 같은 조건끼리 비교(같은 환경·같은 부하, 실행 순서는 아래에서 섞음).

### (b) `pg_wal`만 가득 찬 별도 볼륨

설정: order DB의 `pg_wal`을 별도 128MiB ext4 볼륨(Colima VM에서 loop 마운트한 이미지, 예약 블록 0%)에 두고(`POSTGRES_INITDB_WALDIR`) 데이터 디렉터리는 큰 볼륨에 둔다. 장애: 부하 3초 뒤 root `dd`로 그 볼륨의 남은 공간을 모두 채우고 FAULT_FOR초 뒤 채움 파일을 삭제. 부하 외에 order DB에 WAL을 더 만드는 쓰기(WAL 소각기)를 장애 구간에만 돌려 새 WAL 세그먼트가 실제로 필요해지게 한다. 노출 지표: 장애 구간 `pg_current_wal_lsn` 증가량과 넘은 세그먼트 경계 수. 조건별 n=5. 컨테이너가 종료되면 채움을 지운 뒤 `docker start`로 되살리고 그 시간을 잰다(재시작 정책을 쓰지 않음).

| 가설 | 예측 | 반증 | 힘 | 결정 |
| --- | --- | --- | --- | --- |
| B1 PANIC | 30초 장애(B2 조건) 5회 중 1회 이상 order DB 로그에 `PANIC`(WAL 쓰기 실패) | 세그먼트 경계를 3개 이상 넘었는데 5회 모두 PANIC 0 | n=5(이 칸은 "한 번이라도 나는가"를 묻기 때문에 존재 증명) | 런북에 "WAL 볼륨 가득 참은 서버 종료일 수 있다"를 쓸지 |
| B2 응답받은 예약은 잃지 않는다 | PANIC 여부와 무관하게 해제·재기동 뒤 네 불변식 통과 | 불변식 위반 | n=5 | 위반이면 결함 이슈. 통과면 런북은 "공간 확보 뒤 재기동"만 요구 |
| B3 공간 확보 뒤 자동 또는 `docker start` 한 번으로 복구 | 해제(또는 재기동) 뒤 60초 안에 첫 201, 수동 복구(`pg_resetwal` 등) 불필요 | 기동 실패(`invalid checkpoint record` 등) 또는 60초 초과 | n=5 | 런북 복구 절차 |
| B4 응용 가시 실패 | 장애 구간 쓰기는 5xx(`500`·`503`)이고 커밋되지 않은 요청이 `201`로 응답되지 않음 | 불변식 1 위반 | n=5 | 알람이 볼 신호(5xx, 로그 문구) |

대조군: (i) 무변경 대조군: 같은 별도 `pg_wal` 볼륨, 장애 없음, n=5(볼륨 구성 자체가 결과를 바꾸지 않는지). (ii) 음성 대조군: 채움이 실제로 효력이 있음을 `df`가 100%, 로그의 `No space left on device`, 그리고 WAL 소각기 쓰기가 장애 구간에 실패하는 것으로 보인다. 어느 것도 관측되지 않으면 그 실행은 "장애 미주입"으로 분류하고 집계에서 뺀다(빼는 수를 보고). (iii) 이전 결과와 비교: EXP-087 데이터 디렉터리 tmpfs 칸(ENOSPC, PANIC 0, 재시작 0)과 같은 방식으로 표를 만든다.

### (c) 같은 `Idempotency-Key` 동시 요청과 처리 중 재시도

설정: application 2대 + Toxiproxy(location B 앞). 각 쌍은 `threading.Barrier(2)`로 같이 출발하는 두 요청. 변형 4개를 한 스택 실행 안에서 순차로 돌린다(`run-id` 접두사 구분). 5회(스택 5번) × 변형당 쌍 800개.

| 변형 | 구성 |
| --- | --- |
| C1 | 같은 key·같은 본문, 요청 하나는 인스턴스 1, 하나는 인스턴스 2 |
| C2 | 같은 key·같은 본문, 둘 다 같은 인스턴스 |
| C3 | 처리 중 재시도: location B에 Toxiproxy 지연 1.5초(처리 약 1.5초), 첫 요청 뒤 0.3초에 같은 key를 **다른 인스턴스**로 |
| C-neg | 음성 대조군: 쌍이 서로 **다른 key와 다른 주문**. 예약이 쌍마다 2개 생겨야 한다 |

| 가설 | 예측 | 반증 | 힘 | 결정 |
| --- | --- | --- | --- | --- |
| C1 key당 workflow·예약 | C1·C2·C3의 모든 key에서 order workflow 1행, location A·B 예약 각 1행, 이중 201 0 | 어느 key에서든 예약 행이 1이 아니거나 이중 201 | 변형당 4000쌍, 0건이면 쌍 단위 위반율 95% 상한 `3/4000=0.075%` | 위반이면 결함 이슈(돈·재고) |
| C2 응답 일관성 | 쌍마다 `201`이 정확히 1개, 다른 하나는 `200` 또는 `202`, `409`·`5xx`·상태 0 없음, 두 응답의 workflow id 동일 | `201` 2개 또는 `409`·5xx·0 또는 id 불일치 | 같은 | 응답 계약을 문서에 적는지 |
| C3 동시성이 실제로 일어났다 | C1 쌍의 20% 이상에서 패자가 `202` 또는 재생 응답을 받음(두 요청이 겹쳤다는 증거) | 1% 미만이면 하네스가 동시 요청을 만들지 못한 것(이 칸 결과를 무효로 보고하고 설계를 고침) | 같은 | 결과 해석 가능 여부 |
| C4 처리 중 재시도 | C3 변형에서 재시도는 90% 이상 `202`이고 location 호출은 key당 location당 정확히 1회(재시도가 원격 호출을 만들지 않음) | 한 key라도 두 인스턴스에서 겹친 호출 | 같은 | 클라이언트 재시도 안내 |

음성 대조군 C-neg가 쌍마다 예약 2개를 만들지 못하면 C1~C3의 "정확히 1개"는 탐지기가 못 본 것일 수 있어 무효다. 순차 대조(한 요청이 끝난 뒤 같은 key 재전송)에서 "겹침 비율"이 약 0으로 나와야 C3 탐지가 겹침을 구별한다고 볼 수 있다.

### (d) DNS 부정 캐시

모형(읽은 사실에서 세운 가설): JVM은 성공한 이름 조회를 30초(`networkaddress.cache.ttl` 미설정 기본값), 실패를 10초(`negative.ttl`, EXP-070이 컨테이너 안 `java.security`에서 확인) 기억한다. application의 연결 풀이 안정 상태면 order DB 이름을 새로 조회하지 않아 마지막 조회(`T_last`) 뒤 30초가 지나면 캐시는 만료돼 있다. DB 컨테이너가 멈춰 있는 동안 Docker 내장 DNS는 그 이름을 풀지 못한다(`NXDOMAIN`). 따라서 **DB가 멈춰 있는 구간 안에서** 캐시가 만료돼 있고 풀이 새 연결을 시도하면 조회가 실패하고, DB가 돌아와도 마지막 실패 뒤 10초가 지나야 다시 조회한다. EXP-087의 `dns:*`는 `FAULT_FOR=0`이라 이름이 사라지는 창이 약 0.13초뿐이었다.

계측: application 컨테이너의 네트워크 네임스페이스에 붙인 사이드카(`tcpdump`, 읽기만, 실행마다 시작·`--rm`)로 UDP 53 패킷을 시각과 함께 기록해 `order-postgres` 조회·응답(`NOERROR`/`NXDOMAIN`)을 직접 본다. `T_last`는 관측한 마지막 성공 조회 시각이다. 장애 주입 시각은 `T_last + 오프셋`(실제 오프셋을 기록하고 분석은 명목이 아니라 **실제** 오프셋으로 한다). 복구 지연은 DB가 연결을 받기 시작한 시각(`pg_isready` 폴링 100ms)부터 첫 `201`까지. 부하는 장애 전후를 덮도록 길게(`DURATION`), 일정 속도. 조건별 n=5.

| 조건 | 주입 | 예측(`pg_isready` 이후 첫 `201`까지, 5회 중) | 반증 |
| --- | --- | --- | --- |
| D-fresh | `T_last+5s`에 `kill`, 6초 뒤 `start` | 2초 이하 5/5 (캐시가 장애 내내 유효) | 5초 이상이 1회라도 있으면 모형 틀림 |
| D-inside | `T_last+27s`에 `kill`, 6초 뒤 `start` (만료가 장애 구간 안) | 3초 이상 4/5 이상 | 2초 이하가 3회 이상이면 모형 틀림 |
| D-expired | `T_last+40s`에 `kill`, 6초 뒤 `start` | 5~11초 4/5 이상, pcap에 장애 구간 `NXDOMAIN` 1건 이상, 마지막 `NXDOMAIN` 뒤 다음 성공 조회까지 9초 이상 | 2초 이하가 3회 이상이면 이 스택에서는 10초 지연이 안 난다(그때는 "어떤 조건에서도 못 낸다"고 쓰려면 아래 한계를 먼저 적는다) |
| D-expired+fix | D-expired와 같고 JVM `networkaddress.cache.negative.ttl=0` | 2초 이하 5/5, 같은 `NXDOMAIN`이 pcap에 보임 | 5초 이상이 1회라도 있음 |
| D-restart | `T_last+40s`에 `docker restart` | 예측 약함: 5초 이상 3/5 이상 | 기록만 한다 |
| D-recreate | `T_last+40s`에 `docker rm -f` 뒤 같은 서비스 재생성(IP가 바뀔 수 있음) | 예측 약함 | 기록만 한다 |

무변경 대조군은 D-fresh(같은 스택·같은 부하·캐시 유효). 음성 대조군은 D-expired+fix가 겸한다(같은 장애인데 지연이 없어야 하고, 지연이 있으면 하네스가 아니라 모형이 틀린 것). 하네스를 먼저 의심하는 절차: D-expired에서 지연이 0이면 pcap으로 application이 장애 구간에 이름 조회를 **하지 않았는지**부터 본다.

결정 규칙(사전): D-expired 가설이 맞고(5초 이상 4/5 이상) D-expired+fix도 맞으면 운영 기본값 변경 후보로 삼아, 실제 적용 방식(이미지·compose·Security 속성)으로 before/after n≥5와 되돌리기 시험을 한다. D-expired가 틀리면 변경하지 않고 "이 스택에서 불가능한 조건"을 적는다.

### (e) SYN 드롭, 비대칭 분리, order DB `pause`

각 n=5, 장애는 부하 3초 뒤 6초.

| 조건 | 주입 | 예측 | 반증 |
| --- | --- | --- | --- |
| E1 location B SYN 드롭 | location B 네임스페이스 `iptables -I INPUT -p tcp --syn -j DROP`(새 연결만 무응답, 이미 연결된 것은 통과) | 네 불변식 통과, `202` 존재(5회 중 4회 이상), 장애 중 application 쪽에 `SYN-SENT` 소켓이 관측되고 드롭 카운터 > 0 | 불변식 위반, 또는 카운터 0(주입 실패) |
| E2 비대칭: 응답 드롭 | location B에서 application으로 나가는 패킷 DROP(요청은 도달해 처리되고 응답이 사라짐) | 불변식 통과. location access log에서 장애 구간에 B가 처리한 요청 > 0이고 같은 key가 나중에 재생(`200`)으로 다시 호출됨, 이중 201 0 | 위반 또는 이중 201 |
| E3 비대칭: 요청 드롭 | location B에서 application에서 오는 패킷 DROP(요청이 도달하지 않음) | 불변식 통과. 장애 구간에 B access log의 `POST /reservations` 0건 | 위반 또는 B가 요청을 받음(주입 실패) |
| E4 order DB `pause` | `docker pause`/`unpause` 6초 | 불변식 통과, 일부 요청이 정지 동안 매달림(최대 지연 5초 이상), 해제 뒤 3초 안에 첫 `201`, application 재시작 0 | 위반 또는 해제 뒤 5초 초과 복구 |

무변경 대조군: 이 하네스의 `none`(access log 켬) n=5. 음성 대조군은 각 주입의 "주입이 일어났다는 증거"(카운터·소켓·B 로그)이며 증거가 없으면 그 실행은 집계에서 빼고 수를 보고한다. E2는 "응답이 사라질 때 원격 효과는 있고 확인은 없다"는 가장 위험한 비대칭이라 이중 201과 중복 호출 수를 함께 센다.

## 실행 계획과 교란 요인

- **실행 순서는 섞는다.** 모든 칸의 (조건, 반복)을 고정 시드(20261125)로 한 번에 섞어 순차 실행한다. 시간대·호스트 부하가 조건과 섞이지 않게 하려는 것이다. 시드와 순서는 결과에 남긴다. 실행마다 `uptime`·`docker stats`를 앞뒤로 기록한다(맥락용, 결론은 개수와 불변식에 둔다).
- 같은 Docker VM을 다른 에이전트가 쓴다. 한 번에 스택 하나만 돌린다(application 1대 6개 컨테이너 + mailpit은 필요할 때만, 2대면 7, Toxiproxy를 더하면 8). 컨테이너·볼륨·네트워크는 모두 `atlasexp=h5` 라벨이며, 실행 뒤 라벨로 0개를 확인한다. loop 마운트·이미지 파일은 Docker 객체가 아니라 별도 확인한다.
- 교란 요인 기록(결과 절에 칸마다 채운다): 캐시 상태(JIT·JVM 워밍업: 모든 칸 같은 워밍업), GC(JVM 로그는 켜지 않았으므로 정지 길이를 GC와 구분하지 못함: `pause` 칸의 "정지"는 외부 `SIGSTOP`이라 GC와 같다고 가정하지 않음), 호스트 부하(앞뒤 `uptime`), 데이터 분포(요청마다 같은 모양), 첫 실행 효과(실행마다 새 스택), 하네스 버그(음성 대조군으로 시험).
- 내려가는 순서: application 로그·불변식 → 미들웨어(location access log, PostgreSQL 로그·`pg_stat_*`, 풀) → 네트워크(`tcpdump`, `ss`, `iptables` 카운터) → 런타임(스레드 덤프·GC)은 증거가 가리킬 때만 → OS·컨테이너(cgroup, OOM). 멈춘 층과 이유는 결과에 적는다.
- 원자료(로그·JSONL·pcap)는 저장소에 올리지 않고 `/tmp`에 둔다. 이 문서에 조건별 집계 표만 싣는다. 재현은 `load-tests/fault-injection/run-expansion-matrix.sh`의 EXP-095 모드 한 명령이다.

## 시험 가동 뒤에 추가한 가설 (DNS (d)만, 본 가동 전에 기록)

본 가동을 시작하기 전에 각 칸을 한 번씩(n=1) 돌려 하네스가 도는지만 보았다. 그 시험에서 본 것은 가설의 증거로 쓰지 않지만 설계를 바꾸게 했으므로 숨기지 않고 적는다.

- (d) 시험: `kill` 뒤 6초 정지·캐시 만료 상태(D-expired 조건)에서 DB가 열린 뒤 첫 `201`까지 0.18초였다(사전 등록 예측 "5~11초"와 어긋남, n=1). 같은 시험의 장애를 30초 넘게 끌면 8초대 지연이 나왔다(n=1). 두 시험 모두 tcpdump 사이드카와 같은 네임스페이스에서 해석기 탐침을 돌려 탐침의 조회가 캡처에 섞였으므로, 탐침을 **별도 컨테이너**로 옮겼다(하네스 수정). 섞인 캡처는 쓰지 않는다.
- 시험에서 해석기 탐침(`getent hosts`, 0.1초 간격)은 `kill` 직후 약 0.08초부터 컨테이너가 다시 뜰 때까지 내내 실패했고 `start` 직후 곧 성공했다. 즉 6초 정지 중에는 JVM의 조회가 캐시(30초)에 막혀 이름 조회 자체가 없을 수 있고, 조회가 일어나더라도 실패는 컨테이너가 정지해 있는 동안 계속되며 짧은 "창"만 문제가 아니다.

위를 바탕으로 한 모형(사전 등록): JVM은 접속을 시도할 때만 이름을 조회한다. 마지막 성공 조회 `T0` 이후 `T0+30`에 캐시가 만료된다. DB 정지(길이 S) 중 만료 이후의 조회는 해석기가 실패를 돌려주고 그 실패는 10초 동안 기억된다(부정 캐시). 이후 10초마다 조회가 반복되고 해석기가 다시 답하는 시점(컨테이너 시작) 이후 첫 조회에서 성공한다. 따라서 정지 중 조회 시각은 `T0+30+10k`(k=0,1,…, 컨테이너가 시작돼 해석기가 답하기 전까지)이고 DB가 연결을 받는 시각 `R`(`pg_isready`) 이후의 지연은 `max(0, (시작 후 첫 조회 시각) − R)`이다.

| 조건 | 장애 | 예측(각 실행에서 `R` 이후 첫 `201`까지, 실제 pcap의 `T0`와 조회 시각으로 계산한 모형값) | 반증 |
| --- | --- | --- | --- |
| D-s15 | `T0+5`에 `kill`, 15초 뒤 `start`(캐시가 만료되기 전에 복구) | 모형값 0, 관측 1초 이하 5/5 | 3초 이상이 1회라도 |
| D-s27 | S=27(만료가 정지 중, 다음 조회가 시작 뒤) | 관측과 모형값의 차이가 5회 모두 ±1.5초 안, 평균 지연 3초 이상 | 5회 중 2회 이상 ±2초 밖이면 모형이 틀림 |
| D-s36 | S=36 | 같은 | 같은 |
| D-s36-fix | S=36 + `networkaddress.cache.negative.ttl=0` | 1초 이하 5/5(`R` 직후 첫 조회가 곧 성공) | 3초 이상이 1회라도 |

이 모형이 맞으면 "정확히 10초"는 필연이 아니다. 지연은 `[0, 10)`초 균등 분포에 가깝고 EXP-070의 두 값(10.0, 9.8)은 정지 길이와 조회 위상이 만든 값으로 설명된다. 그 반대(관측이 모형을 따르지 않음)가 나오면 원인은 모른다고 쓴다. 표본 n=5는 모형의 정량 예측을 시험할 뿐 지연이 날 확률을 추정하지 않는다.

## 2차 가동 사전 등록 (가동 전에 별도 커밋으로 기록)

1차 가동은 11개 실행(조건별 n=1)에서 멈췄다. 2차 가동은 위 가설 표(A1~A4, B1~B4, C1~C4, DNS 모형, E1~E4)와 그 반증 조건을 **한 글자도 바꾸지 않고** 계획한 칸 전부에서 판정한다. 조건별 n=5(DNS의 `d-restart`·`d-recreate`만 n=3)이며, 모든 (조건, 반복)을 고정 시드 20261125로 한 번에 섞어 순차 실행한다(블록 무작위화: 시간대와 호스트 부하가 조건과 섞이지 않게 한다). 1차와 같은 시드를 쓰지만 목록이 달라 순서는 다르다. 실행 순서·시드·앞뒤 `uptime`은 결과에 남긴다. 아래는 1차 데이터를 본 뒤 추가하는 가설이므로 독립적이지 않다.

## 실제로 한 것

- 하네스를 확장했다(`load-tests/fault-injection/`, 새 파일은 `compose.wal.yaml` 하나뿐이고 나머지는 기존 스크립트의 옵션이다). `run-fault-injection.sh`: 결함 `app-pause`, `order-db-pause`, `order-db-wal-full`, `location-b-syn-drop`, `location-b-resp-drop`, `location-b-req-drop`, `dns-kill`, `dns-restart`, `dns-recreate`, `race`와 옵션 `LOCATION_ACCESSLOG`, `PLANT_DUP`, `APP1_DELAY`, `LEASE_AUDIT`, `DNS_TRACE`, `DNS_OFFSET`, `DNS_REFRESH`, `MAILPIT=0`, `WAL_*`. `reservation_load.py race`: 같은 key 동시 쌍. `audit_invariants.py calls|dns|deep|selftest`: location access log의 key별 중복 호출, DNS 패킷 디코딩, 조건별 표, 탐지기 자체 시험. `run-expansion-matrix.sh SET=deep`: 고정 시드로 섞은 매트릭스.
- 탐지기 자체 시험(음성 대조군 성격): `python3 load-tests/fault-injection/audit_invariants.py selftest`가 알려진 답이 있는 합성 입력을 판정한다. 규칙 7곳(교차 인스턴스, 이중 201, 겹침, 외부 출처, DNS rcode·qr·qtype 판독)을 하나씩 깨뜨려 시험이 실패함을 확인하고 `cmp`로 복원을 확인했다(7/7 실패, 복원 7/7).
- 호스트 부하: 실행 직전 1분 load average는 12~42였다(공유 Docker VM). 시간 값은 맥락으로만 쓴다.
- 실행 순서는 시드 20261125로 섞었다. 섞은 목록 앞의 9개만 돌렸고(c-race 1, a-pause12-L7 1, a-pause12-L10 1, a-ctl-L7 1, a-pause12-L10-nodelay 1, b-ctl-burn 1, d-fresh 1, d-recreate 1, d-s36-fix 1, e-ctl-none 1, e-syn-drop 1) 매트릭스는 호스트 사정과 요청 예산 때문에 중단했다. 중단 시 컨테이너·볼륨·네트워크는 `atlasexp=h5` 라벨로 0개다.

## 사전 부검과 되돌리기

- 이번에 production 코드·설정을 바꾸지 않았다(ADR 없음). 따라서 되돌리기 시험은 해당 없다. 바꿀 것이 생기는 후보(DNS `negative.ttl=0` 적용)는 이번 데이터로 근거가 서지 않아 적용하지 않았다.
- 이 하네스 변경이 실패할 수 있는 방식과 감지: ① 탐지기가 0을 거짓으로 낼 수 있다 → `selftest`와 PLANT_DUP·`neg` 음성 대조군. ② 호스트 부하가 시간 값을 흔든다 → 개수와 불변식으로만 결론, load average 기록. ③ 조건이 섞인다 → 시드 고정 섞기. ④ 공유 Docker를 오염시킨다 → 모든 객체 `atlasexp=h5` 라벨, 종료 시 0개 확인, `pg_wal` 이미지는 VM 안 임시 마운트(종료 때 해제, 이번에 남은 빈 디렉터리 하나를 삭제).
