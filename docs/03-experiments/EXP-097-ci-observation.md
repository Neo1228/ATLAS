# EXP-097: 최근 CI 변경 네 건은 실제 GitHub Actions에서 무엇을 했는가

- 질문: [EXP-074](EXP-074-slow-test-forensics.md)·[EXP-075](EXP-075-ci-pipeline-reliability.md)·[EXP-076](EXP-076-shard-balance.md)가 로컬 측정이나 작은 표본으로만 말한 네 가지를 병합 뒤 실제 CI 데이터로 확인한다. (1) `LocationFaultConvergenceIntegrationTest` 간헐 실패(#609 전 4건)가 이후 재발하는가. (2) 끝난 클래스의 Spring 컨텍스트를 닫는 리스너(#609)가 실제 CI의 앱 테스트 시간을 줄였는가(로컬 390초 → 225초). (3) `DOWNLOADED_JARS`가 0으로 유지되고 Maven 429가 재발하지 않는가(#604). (4) main push의 앱 테스트 생략(#613)의 전제(보호 규칙 strict + squash만 허용)가 지금도 성립하고 push와 PR의 job 분 비용이 실제로 어떻게 달라졌는가.
- 상태: **사전 등록 단계.** 이 절은 데이터를 수집하기 전에 커밋한다(git 이력이 증거). 새 실험은 하지 않고 `Neo1228/ATLAS`의 GitHub Actions 실행 데이터를 읽기 전용으로 분석한다.
- 날짜: 2026-11-25
- 관련: [ADR-0073](../02-decisions/adr/ADR-0073-ci-dependency-cache-warming.md), [ADR-0074](../02-decisions/adr/ADR-0074-shard-weights-from-recent-runs.md), [ADR-0070](../02-decisions/adr/ADR-0070-parallel-backend-ci.md), [EXP-069](EXP-069-ci-shard-imbalance.md), [Issue #647](https://github.com/Neo1228/ATLAS/issues/647), 결정 로그 D-137, D-138, D-163

## 문제 한 문장

작업 기록에는 "간헐 실패를 고쳤다", "shard 시간이 줄었다", "다운로드가 0이다", "push 실행은 중복이다"가 적혀 있지만 앞의 둘은 로컬 재현값이고 뒤의 둘은 병합 직전의 작은 표본(재실행 3회, 단일 시점 설정)이어서, 앞으로 CI를 믿고 병합하는 사람(1인 운영자와 에이전트 6명)이 이 네 주장이 실제 CI에서 성립하는지 모른다(영향 범위: 병합 판단 전부, 수치는 아래 측정 전까지 "가정").

## 데이터 출처와 수집 규칙(수집 전에 정함)

- 출처: GitHub REST API(`gh api`, GET만)로 `Neo1228/ATLAS`의 워크플로 파일 `.github/workflows/backend-ci.yml`(표시 이름 `CI`) 실행 목록, 실행별 job·step 시각, 실행 로그 압축 파일(`.../runs/<id>/attempts/<n>/logs`). 저장소와 Actions 설정은 바꾸지 않는다. 보호 규칙은 읽기 요청만 한다.
- 창: `run_started_at`이 2026-11-23T12:11:38Z(#502, 샤딩과 `CLASSTIME` 출력이 들어온 병합 시각) 이상이고 수집 시작 시각(`T_cut`, 수집 스크립트가 파일에 기록) 이전인 모든 실행. 목록은 페이지를 끝까지 넘겨 받는다(`--limit 500`에 걸리면 그것도 기록한다).
- 변경 시각(`gh pr view`로 확인한 실제 병합 시각, UTC):

| 경계 | PR | 병합 시각 | 하는 일 |
| --- | --- | --- | --- |
| B604 | #604 | 2026-11-24T12:36:49Z | `verify`가 shard 의존성을 캐시에 넣음, `DOWNLOADED_JARS` 출력 |
| B609 | #609 | 2026-11-24T13:44:00Z | 끝난 클래스의 컨텍스트 닫기 리스너, `LocationFault...` 테스트의 호출자 재시도 |
| B613 | #613 | 2026-11-24T15:04:43Z | main push에서 `app-tests` 생략 |

- 기간: S0 = [#502, B604), S1 = [B604, B609), S2 = [B609, B613), S3 = [B613, `T_cut`). 어느 기간인지는 **시도(attempt)의 `run_started_at`**으로 정한다. PR 실행은 병합 ref의 워크플로를 쓰므로 경계 직후 시작한 실행은 이전 버전일 수 있다. 그래서 모든 전후 비교에 경계 뒤 30분을 뺀 민감도 분석을 함께 낸다.
- 관측 단위: **시도 하나 = (run id, run_attempt)**. 같은 head를 다시 돌린 재실행은 **별도 관측으로 센다**(간헐 실패는 재실행에서 통과하므로 마지막 시도만 보면 실패를 지운다). 같은 head의 시도는 독립이 아니므로 구간 추정은 PR 번호(push는 SHA) 단위 군집 부트스트랩으로 낸다. 군집 수도 함께 적는다.
- 제외: 완료하지 않은 시도, 시도 전체가 `cancelled`인 것(동시성 규칙이 새 push로 취소한 것), job 결론이 `cancelled`·`skipped`인 job, 코드 변경이 없어 `verify`가 건너뛰어진 문서 전용 시도. 제외한 시도 수는 기간마다 적는다.
- "전체 검사 시도" = `verify`와 `Application tests (k/4)`가 모두 실행된 시도. S3부터 push 시도는 `verify`만 돈다(검증 전용 시도로 따로 센다).
- 로그에서만 얻는 값: `CLASSTIME <클래스> <초>`, `DOWNLOADED_JARS <n>`, 429·HTTP 오류 문자열, Gradle 실패 줄. 만료돼 받을 수 없는 로그는 "로그 없음"으로 세고 분모에서 뺀다.

통계는 양쪽 정확(Clopper-Pearson) 95% 구간, 분포는 중앙값·사분위 범위(IQR)·p90(선형 보간)·최소·최대, 두 분포의 차이는 Hodges-Lehmann 이동량과 군집 부트스트랩 95% 구간(2,000회, 시드 고정), 순위 검정은 Mann-Whitney(양측)와 Wilcoxon 부호 순위로 낸다. 평균은 대표값으로 쓰지 않는다. 주 가설(H1, H2, H5, H7, H8)에만 판정을 붙이고 나머지는 기술 통계로 둔다. 다중 비교 보정은 하지 않으므로 p값은 참고용이다.

## 대조(통제)

- **무변경 대조**: 변경이 영향을 줄 수 없는 지표를 같은 방법으로 잰다. #613은 PR 시도에 영향이 없으므로 S2 대 S3의 PR 시도 job 분과 shard 시간이 같아야 한다(H8의 영 대조).
- **음성 대조(탐지기가 반드시 반응해야 하는 사례)**: (a) 이미 알려진 429 실행 `45231283583`, `45330809510`, `45344744453`을 429 탐지기가 잡아야 한다. (b) 이미 알려진 LocationFault 실패 실행 `45181797918`, `45231697943`, `45342680146`을 LocationFault 탐지기가 잡아야 한다(EXP-074가 `Application tests (3/4)`에서 확인한 값). (c) 캐시 없는 첫 실행 같은 `DOWNLOADED_JARS` 5가 B604 직후 시도에서 보여야 한다(EXP-075 값 5). (d) #613 전후 main push job 분은 반드시 다르다. 하나라도 반응하지 않으면 그 지표의 "0건"은 쓰지 않는다. 발견한 실행 id는 결과에 적는다.
- **짝지은 비교의 위약 대조와 양성 대조**: S0를 `run_id` 짝홀로 둘로 나눠 같은 비교를 하면 중앙값이 0에 가깝고 구간이 0을 포함해야 한다(위약). 후 기간 클래스 시간에 합성 0.85배를 곱하면 구간이 0을 제외하고 -10%를 넘는 이동을 탐지해야 한다(양성). 둘 중 하나가 어긋나면 H2 결과를 쓰지 않는다.
- **하네스 재현**: [EXP-075](EXP-075-ci-pipeline-reliability.md)가 `gh run list --limit 300`으로 센 값(샤딩 뒤 전체 검사 118건 중 429 3건, 같은 창에서 main push 103회 중 8회 실패)을 같은 창으로 다시 세어 자릿수가 맞는지 본다. 규칙이 달라(120초 기준 대 이 문서의 job 규칙) 정확한 일치는 기대하지 않고 차이를 적는다.

## 표본 크기와 한계(수집 전에 적음)

- 후 기간은 `T_cut`까지 길어야 하루 남짓(S2+S3)이고 PR 병합이 이어지는 속도에 달려 있다. 후 기간 표본(클래스 실행, 전체 검사 시도)은 수집 뒤에야 알 수 있다. 0건이 나오면 "규칙 3": 95% 상한 ≈ 3/n을 적고 "없다"로 쓰지 않는다. 구간이 겹치면 구별하지 못한다고 쓴다.
- 같은 head의 재실행은 독립이 아니다. 군집 수를 같이 적고 구간은 군집 단위로 낸다.
- 러너는 공유 호스티드 VM이고 PR마다 변경한 테스트 클래스가 달라 시간 분포의 구성이 다르다. 그래서 같은 클래스끼리 짝지은 비교를 주로 쓰고 shard job 시간은 참고로 둔다. 단 클래스 내용이 바뀐 경우(예: `LocationFault...` 자체 수정)는 짝지은 비교에서 따로 표시한다.
- 로컬 Mac의 시간은 이 연구에 쓰지 않는다. 결론은 개수와 불변식(경계 전후 설정, 합성 대조)으로 내린다.

| --- | --- | --- |
| PR마다 다른 클래스 구성 | shard 시간, 클래스 시간 | 같은 클래스끼리 짝지은 비교, 위약 대조 |
| 러너 공유와 시간대 | 모든 시간 | 중앙값·IQR·p90, 시간대를 해석에 쓰지 않음, 결론은 개수 기준 |
| 캐시 상태(첫 실행) | `DOWNLOADED_JARS`, 시간 | `W` 이전 시도를 따뜻한 집합에서 뺌, 음성 대조 (c) |
| PR이 의존성을 바꿔 정당하게 받는 jar | `DOWNLOADED_JARS` | 0이 아닌 시도의 PR이 빌드 파일을 바꿨는지 확인해 분리 |
| 재실행이 실패를 지움 | 실패율 | 모든 시도를 센다 |
| 경계 직후 시작한 PR 실행이 옛 워크플로 | 모든 전후 비교 | 경계 뒤 30분 제외 민감도 분석 |
| 로그 형식, 정규식 오류(하네스) | 모든 로그 지표 | 음성 대조 (a)~(c), 놀라운 결과는 하네스부터 의심 |
| 분모 정의(job 대 시도) | 실패율 | 두 분모를 모두 표기 |
| 다른 PR이 같은 시간에 병합한 테스트 변경 | 클래스 시간 | 클래스 내용이 바뀐 것을 표시, 변경된 클래스는 민감도 분석에서 제외 |

## 한 겹씩 내려가기

CI 실행 목록 → job·step 시각 → 로그 줄 순서로만 내려간다. 원인을 묻는 새 질문(왜 429인가, 왜 느린가)은 이 연구에서 다루지 않는다. LocationFault가 재발하면 로그의 DB 상태 줄(`dangling`, `in flight after recovery`)을 EXP-074의 서명과 비교하는 데서 멈춘다. 그 아래(아티팩트의 요청 이력, 스레드 덤프)는 재현된 경우에만 내려간다.

## 대안 비교(수집 전)

| 대안 | 비용 | 위험 | 근거 |
| --- | --- | --- | --- |
| 아무것도 안 함 | 0 | 네 주장이 측정 없이 남아 틀려도 모름. #613은 되돌리기 조건(strict 해제)을 아무도 점검하지 않음 | 로컬 값과 3회 재실행만 있음 |
| 같은 head를 일정 횟수 재실행하는 새 CI 실험(가장 강한 반론) | 러너 분, 한 회에 약 11분 × n | 표본을 통제할 수 있고 구성 차이가 없다는 장점이 있으나 비용이 들고, 이미 쌓인 실행 수백 건이 같은 질문에 답할 수 있는지 먼저 모름. 공유 러너 소음은 줄지 않음 | EXP-075의 재실행 3회가 이 방식이었고 표본이 작았음 |
| 기존 실행 데이터의 읽기 전용 분석(채택) | API 호출, 로그 수백 건 | 구성 차이와 재실행 비독립이 있어 일부는 "데이터 부족"으로 끝남. 위 대조로 보완 | 이미 쌓인 표본과 사전 등록 규칙 |

## 사전 부검(pre-mortem)

| 틀릴 수 있는 방식 | 탐지 |
| --- | --- |
| 로그 만료나 압축 파일 누락으로 분모가 줄어듦 | "로그 없음" 개수를 기간별로 적고 분모에서 뺀 수를 함께 표기 |
| 정규식이 로그 형식과 달라 0건을 잘못 만듦 | 음성 대조 (a)~(c)와 로그 줄 예시를 직접 열어 확인 |
| 마지막 시도만 봐서 실패를 지움 | 재실행 시도(`run_attempt > 1`)를 모두 받고 시도 수를 적음 |
| 경계 직후 PR이 옛 버전이라 전후가 섞임 | 30분 제외 민감도 분석, 결과가 뒤집히는지 표시 |
| 클래스 구성 차이를 효과로 오인 | 짝지은 비교와 위약 대조 |
| 설정(strict)은 지금 값만 보이고 과거는 모름 | 설정은 시점 값으로만 쓰고 이력은 병합 PR의 `behind_by` 간접 증거로만 보완. 둘을 구분해 적음 |

## 되돌리기 시연

이 변경은 문서만 바꾼다(코드·워크플로·설정 변경 없음). 되돌리기는 PR 되돌리기(`git revert`)이고, 마지막에 로컬 worktree에서 한 번 실행해 결과를 적는다.
