# EXP-037: 아주 작은 단일 노드에서 시작해 한계를 찾고 스케일 아웃으로 해결

**추적 이슈:** [#346](https://github.com/Neo1228/ATLAS/issues/346)

**상태:** 진행 중 · 측정값은 실제 실행 결과만 기록

## 왜 다시 시작하는가

EXP-035는 앱·DB 각 2 vCPU로 시작했습니다. 그 조건에서 10 it/s(60 HTTP RPS)는 드롭 0.1%로 통과했고, 20 it/s에서야 PostgreSQL이 2코어를 다 썼습니다. 즉 **출발점이 이미 넉넉했습니다.** "작은 서버에서 시작해 무엇이 먼저 무너지는지"를 보려면 더 작아야 합니다.

이 실험은 의도적으로 **AWS 최소 인스턴스보다도 작은** 스펙에서 시작합니다.

| 항목 | EXP-035 | **EXP-037 (이번)** | AWS 참조 |
| --- | --- | --- | --- |
| 앱 CPU | 2.0 | **1.0** | t4g.small baseline 0.24 vCPU / t4g.medium 2 vCPU |
| 앱 메모리 | 2 GiB | **1 GiB** | t4g.small 2 GiB |
| PG CPU | 2.0 | **1.0** | db.r7g.large 2 vCPU |
| PG 메모리 | 2 GiB | **1 GiB** | db.r7g.large 16 GiB |
| `max_connections` | 60 | **40** | RDS 기본은 메모리 기반 |
| `shared_buffers` | 256MB | **96MB** | RDS 기본 |
| Tomcat 스레드 | 64 | **32** | — |

AWS `t4g.small`은 **2 GiB / baseline 24%**(2 CPU credits/h, 최대 576)입니다. 즉 지속 가능한 연산은 0.24 vCPU 수준입니다. 이번 앱 컨테이너는 1.0 vCPU로 그보다 4배 넉넉하지만, 2 vCPU보다는 확실히 작아 **한계가 먼저 나타납니다**.

## 실험 순서

이 실험은 다음 순서를 고정합니다. 각 단계는 이전 단계의 실패를 근거로만 진행합니다.

```text
1. Tiny single node  → 어디서 먼저 무너지는가 (지표로 특정)
2. 같은 스펙 유지 + 병목만 제거 → 정말 그것이 원인인가
3. 수직 확장(scale up) → 한계가 얼마나 올라가는가
4. 수평 확장(scale out) → 어디서 다시 무너지는가
5. 추가 인프라(pooler, cache, replica) → 남은 병목을 무엇으로 해결하는가
```

## 측정 환경

| 항목 | 값 |
| --- | --- |
| 호스트 | Apple Silicon, Docker VM 8 CPU / 13.5 GiB |
| 데이터셋 | 아래 "데이터 규모" 참조 |
| 시나리오 | `load-tests/catalog-read-capacity.js` — 1 iteration = 6 공개 GET |
| 관측 | Prometheus 5 s, 인스턴스별 target, Grafana 패널 캡처(창·크기·SHA-256) |

### 데이터 규모

| 항목 | 값 |
| --- | ---: |
| seller | 2,000 |
| product | 2,000,000 |
| seller_sku | 4,000,000 |
| ONLINE_STORE availability | 2,000,000 |
| 선택도 높은 keyword(`needle`) | 20건 (1/100,000) |

시드는 `load-tests/seed-catalog-scale.sql`로 수행합니다. 각 단계를 `batch_rows` 청크로 나눠 청크마다 별도 트랜잭션으로 커밋하므로, 한 트랜잭션이 수백만 인덱스 항목을 붙잡지 않고 실패해도 이미 커밋된 청크는 남아 멱등 재시도가 가능합니다.

실측(이 환경, 컨테이너 기본값):

| 규모 | products | SKUs | 테이블+인덱스 | 소요 |
| --- | ---: | ---: | ---: | ---: |
| 2,000 × 1,000 | 2,000,000 | 4,000,000 | 3,133 MB | 351 s |
| 2,000 × 2,000 | 4,000,000 | 8,000,000 | 6,247 MB | 971 s |

`needle` 선택도는 1/100,000으로 유지되어 2M 상품에서 정확히 20건이며, 해당 라우트는 trigram index로 **0.3 ms, heap block 20개**만 읽습니다.

## 결과

원자료: [`results/exp-037/exp-037-summary.json`](results/exp-037/exp-037-summary.json).

### 단계 1 — tiny 단일 노드 (앱 1 vCPU/1 GiB, PG 1 vCPU/1 GiB) · 측정 완료

2M 상품 / 4M SKU, 120초, 여정 시나리오(읽기 다수 + 장바구니 6% + checkout).

| Offered it/s | 완료/계획 | 드롭 | p95 (ms) | 측정 실패 | App CPU mean | PG CPU mean |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 1201/1201 | 0 (0.0%) | 14 | 0.0% | 39% | 9% |
| 20 | 2350/2401 | 51 (2.1%) | 791 | 0.0% | 57% | 12% |
| 40 | 4309/4801 | **492 (10.2%)** | **1706** | 0.0% | 92% | 19% |

**첫 번째 벽:** 10 → 20 it/s에서 p95가 14 ms에서 **791 ms(56배)**로 무너지고 드롭이 발생합니다. 40 it/s에서는 드롭 10.2%, p95 1,706 ms입니다. 이때 PostgreSQL CPU는 19%로 거의 유휴이고 **애플리케이션 CPU가 92%** 입니다.

즉 첫 병목은 DB가 아니라 **1 vCPU 애플리케이션**입니다. 40 it/s에서 k6 VU가 48 → 192까지 확장된 것도 같은 원인입니다. 고정 VU 예산으로 도착률을 맞추지 못했다는 뜻입니다.

### 단계 2 — 같은 데이터, 앱만 2 vCPU로 scale up

단계 1이 지목한 병목만 제거합니다. **PostgreSQL은 tiny(1 vCPU) 그대로** 두고 앱만 2 vCPU/2 GiB로 올렸습니다.

| 구성 | Offered it/s | 완료/계획 | 드롭 | p95 (ms) | App CPU | PG CPU |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| tiny (1 vCPU) | 20 | 2350/2401 | 51 (2.1%) | 791 | 57% | 12% |
| **scale up (2 vCPU)** | 20 | 2401/2401 | **0 (0.0%)** | **7** | 58% | 13% |
| tiny (1 vCPU) | 40 | 4309/4801 | 492 (10.2%) | 1706 | 92% | 19% |
| **scale up (2 vCPU)** | 40 | 4778/4801 | **23 (0.5%)** | **76** | 75% | 18% |

**원인 검증:** 앱 코어만 1 → 2로 늘렸더니 20 it/s에서 드롭이 2.1% → **0%**, p95가 791 ms → **7 ms(113배 개선)**가 됐습니다. 40 it/s에서는 드롭 10.2% → 0.5%, p95 1,706 → 76 ms입니다. PostgreSQL CPU는 12–19%로 변하지 않았습니다.

개선이 DB가 아니라 앱에서 나왔으므로, 단계 1의 진단이 **실제 원인이었음**이 확인됩니다. 병목을 잘못 짚었다면 같은 부하에서 이런 변화가 나타나지 않았을 것입니다.

### 단계 3~5 — scale out / pooler / 남은 병목

앱 2 vCPU에서 40 it/s가 거의 해결되었으므로, 다음 한계는 더 높은 부하에서 나타납니다. 이어서 측정할 항목:

| 단계 | 변경 | 확인할 것 |
| --- | --- | --- |
| scale out | 동일 스펙 replica 3개 + nginx | 앱이 병목일 때 수평 확장이 처리량을 늘리는가 |
| pooler | PgBouncer transaction mode | DB 연결 압박이 실제로 병목이 되는 지점 |
| 상한 탐색 | 80/160 it/s | 앱 이후에 무엇이 먼저 무너지는가 |

## 해석 규칙

- 드롭이 0이 아닌 지점을 "용량"이라 부르지 않습니다.
- 각 단계는 **이전 단계에서 확인된 병목**을 근거로만 진행합니다. 근거 없이 스펙을 올리지 않습니다.
- 컨테이너 CPU는 5초 샘플이며 순간 최대가 아닙니다. 100%는 1코어 상한입니다.

## 한계

- 로컬 단일 호스트 비교이며 프로덕션 SLA가 아닙니다.
- AWS 스펙은 **참조점**이며, 실제 클라우드에서 같은 수치가 나온다고 주장하지 않습니다.
- 2M 상품 시드는 합성 데이터이며 실제 상품 분포와 다릅니다.
