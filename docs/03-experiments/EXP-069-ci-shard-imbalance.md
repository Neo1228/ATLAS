# EXP-069: CI application shard의 시간 편차는 어디서 오는가

- 질문: [ADR-0070](../02-decisions/adr/ADR-0070-parallel-backend-ci.md)은 가중치를 runner 실측값으로 바꿔도 shard 편차가 사라지지 않았고 원인은 검증하지 못했다고 적었다. 원인의 후보와 그 근거는 무엇인가?
- 상태: 조사와 로컬 측정. 코드를 바꾸지 않았다. **확정한 것, 로컬에서 확인한 것, 확인하지 못한 것을 구분해 적었다.** 로컬 측정(사실 5)은 하네스를 저장소 밖에 두었다.
- 날짜: 2026-11-24
- 관련: [ADR-0070](../02-decisions/adr/ADR-0070-parallel-backend-ci.md), [EXP-030](EXP-030-ci-build-duration.md)

## 측정한 사실

### 1. 클래스마다 컨테이너와 Spring 컨텍스트를 새로 띄우는 구조다

테스트 소스를 직접 세었다(2026-11-24, main `fd4cc8a`).

| 항목 | 값 |
| --- | --- |
| application 모듈 테스트 클래스 | 120개 |
| `@SpringBootTest` 클래스 | 52개. 모두 자기 PostgreSQL 컨테이너와 자기 `@DynamicPropertySource`를 가진다 |
| Spring 없이 PostgreSQL 컨테이너를 띄우는 클래스 | 21개 |
| 컨테이너를 자기가 띄우는 클래스 합계 | 73개(52 + 21) |
| `@DynamicPropertySource`가 설정하는 키 집합이 서로 다른 종류 | 14개 |

컨테이너 주소가 클래스마다 다르므로 Spring 테스트 컨텍스트 캐시는 클래스 사이에서 재사용되기 어렵다. 이것은 주소 문자열이 달라 캐시 키가 달라진다는 구조에서 추론한 것이며 컨텍스트 생성 횟수를 로그로 센 것은 아니다. 키 집합 14종은 컨텍스트 종류 수의 하한일 뿐이다.

### 2. PostgreSQL 컨테이너 하나의 기동 비용

Colima Docker VM(Apple 실리콘)에서 `postgres:18.6`을 Testcontainers와 같은 기준(로그의 "ready to accept connections"가 2회)으로 3번 쟀다: **1.49초, 1.51초, 1.65초**. 컨테이너만으로는 73 × 1.5초 ≈ 110초이고, `test-shard-weights.properties`의 클래스별 시간 합 859초(CI runner 실측으로 만든 가중치 112개 클래스)의 약 13%다. 단, 859초는 CI runner 값이고 1.5초는 로컬 값이라 둘을 섞은 비율은 거친 추정이다. Spring 컨텍스트 기동과 Flyway 마이그레이션(75개 테이블)의 비용은 측정하지 않았다.

### 3. 같은 클래스의 시간이 실행마다 크게 흔들린다

두 CI 실행(2026-11-24, PR 브랜치 #518과 #516, 둘 다 같은 구성)의 클래스별 시간을 비교했다. 두 실행 모두에서 5초 이상인 클래스 36개의 (큰 값 / 작은 값) 중앙값은 1.33, 최댓값은 10.65였다. 가장 크게 흔들린 클래스는 다음과 같다.

| 클래스 | 실행 A | 실행 B |
| --- | --- | --- |
| `OrderShipmentIntegrationTest` | 4초 | 35초 |
| `ConcurrentPaymentPreparationIntegrationTest` | 33초 | 3초 |
| `JdbcExpirySweepLockRepositoryTest` | 3초 | 29초 |

세 클래스 모두 흔들림 폭이 25~32초로 비슷하다. 세 클래스 모두 `@SpringBootTest`이고 자기 PostgreSQL 컨테이너를 가진다(소스 확인). 세 번째 클래스는 이름이 바뀐 것이 아니다. 파일은 `ExpirySweepLockRepositoryTest.java`이고 안의 클래스 이름이 `JdbcExpirySweepLockRepositoryTest`다. 로컬 측정(사실 5)에서 이 세 클래스가 같은 방식으로 흔들리는 것을 다시 관찰했다.

### 4. 클래스 시간의 합이 step 시간보다 크다

shard 한 개의 테스트 step 시간은 117~255초인데 그 shard의 클래스 시간 합은 134~256초이고, 두 실행의 8개 shard **모두**에서 합이 step 시간을 넘는다. 이는 `ATLAS_TEST_FORKS=2`로 클래스가 두 JVM에서 겹쳐 실행되기 때문이다. 따라서 "클래스 시간의 합"은 shard의 실제 소요 시간이 아니고, 가중치를 합으로 균형 잡는 방식은 두 fork에 걸친 겹침을 반영하지 못한다.

### 5. 로컬에서 같은 현상을 재현하고 위치를 좁혔다

측정 조건: Apple 실리콘 Mac(Colima Docker VM 8 vCPU, 12.6GiB), main `e4982cda` 기준 별도 worktree, `:application-module:test` 전체(타임라인에 잡힌 클래스 110개), 실행마다 `cleanTest`와 `--no-build-cache`. Gradle 테스트 리스너로 클래스별 시작·종료 시각을 기록했다(init script, 저장소 밖). fork 번호는 로그에 없어서 겹치지 않는 구간을 두 트랙에 나누는 방식으로 추론했고 위반은 0건이었다. 실행 중 외부 Gradle 프로세스 수와 load를 15초마다 기록해 오염 여부를 가렸다.

| 실행 | fork | 클래스 시간 합 | 클래스 구간 폭(wall) | 오염 |
| --- | --- | --- | --- | --- |
| f1 | 1 | 412초 | 412초 | 외부 Gradle 0, load 최대 7.4 |
| f2b | 2 | 417초 | 226초 | 외부 Gradle 0, load 최대 5.5 |
| f2a | 2 | 551초 | 279초 | 외부 Gradle이 일부 겹침, load 중앙값 7.3, 최대 10.1 |

제외한 실행: 처음 돌린 f2b와 f1은 빌드 캐시에서 복원돼 5초에 끝나 테스트가 실행되지 않았다. 다시 돌린 f2b는 다른 세션의 Gradle이 샘플 48개 중 31개에서 겹쳤고(load 최대 21) DB 연결 오류로 테스트 3개가 실패해 버렸다. f2a는 같은 문제를 완전히 배제하지 못했으므로 참고로만 쓴다.

- **같은 클래스의 시간이 2~4초와 22~35초 사이를 오간다.** 110개 중 중앙값은 1.9초(p90 4.9초)인데, 15초 이상인 클래스가 실행마다 7~11개이고 중앙값 24~28초, 클래스 시간 합의 47~54%를 차지한다. 어느 한 실행에서 15초 이상이었던 클래스 15개 중 세 실행 모두 15초 이상인 것은 3개뿐이고, 9개는 한 실행에서 15초 이상, 다른 실행에서 6초 이하였다. 예(f1 / f2a / f2b): `OrderShipmentIntegrationTest` 34.9 / 5.0 / 3.6초, `JdbcExpirySweepLockRepositoryTest` 32.4 / 2.6 / 2.1초, `PaidOrderCancelContractIntegrationTest` 2.4 / 4.6 / 32.1초, `SellerOrderDiscoveryIntegrationTest` 23.1 / 31.5 / 2.4초. CI에서 본 흔들림(사실 3)과 같은 클래스에서 같은 크기로 나타난다.
- **비싼 시간은 테스트 메서드 안이 아니다.** f2b에서 15초 이상이던 8개 중 5개는 테스트 메서드 합이 0.3~12초인데 클래스 시간이 23~38초였다(메서드 밖 22.6~31.6초). 저렴한 클래스(102개)는 메서드 밖 시간 중앙값이 0.9초다.
- **Spring 컨텍스트 기동 자체도 아니다.** Spring Boot가 보고한 기동 시간은 58개 클래스에서 60회, 합 68초(클래스 시간 합의 약 16%)이고 비싼 클래스의 기동 시간은 0.9~5.4초(대부분 1초 안팎)다.
- **컨텍스트가 클래스 사이에서 재사용되지 않는다는 사실 1의 추론은 맞았다.** 58개 클래스가 기동 로그를 남겼고 총 60회 기동했다(한 클래스만 3회). 다만 클래스마다 컨텍스트를 새로 띄우는 비용은 합의 16%이므로 H3의 "큰 부분"을 이것으로 설명할 수 없다.
- **클래스 자체의 비용이 아니다.** `PaidOrderCancelContractIntegrationTest`와 `SellerOrderDiscoveryIntegrationTest`만 골라 JVM 하나에서 2회씩 돌리면 6.2~6.5초와 2.0초였다. 전체 실행에서는 각각 2.4~32.1초, 2.4~31.5초였다. 같은 JVM에서 앞서 실행된 것이 비용을 좌우한다.
- **비싼 구간의 로그에 앞선 클래스의 컨텍스트가 남아 있다.** 로그 시각 공백을 본 4개 클래스 중 3개에서 가장 큰 공백(17~28초)이 `Found @SpringBootConfiguration` 직후에 있었다. 그중 2개(`PaidOrderCancelContractIntegrationTest`, `InventoryCapacityAdjustmentIntegrationTest`)는 공백 직후 첫 로그가 이전 컨텍스트의 백그라운드 작업이었다(`HikariPool-1 - Pool is empty, failed to create/setup connection`, `Scheduled expiry sweep failed`). 나머지 1개(`ScheduledExpiryMultiInstanceIntegrationTest`)는 자기 클래스의 시작 로그였고, 1개(`SettlementFeeReservePayoutIntegrationTest`)는 큰 공백이 1.2초뿐이었다. 이 관찰은 원인이 아니라 정황이다.

## 가설과 로컬 검증 결과

- **H1. 한 JVM에서 처음 실행되는 클래스가 공통 초기화 비용을 떠안는다.** **부분적으로만 지지된다.** JVM의 첫 Spring 클래스(`BuyerFlowIntegrationTest`)는 13.4초(f1), 17.6초(f2b), 23.9초(f2a)로 저렴한 클래스 중앙값(1.9초)보다 훨씬 길었다. 그러나 이 클래스는 세 실행 모두 첫 번째여서 클래스의 성질과 위치를 가를 수 없다. 더 큰 비용(22~35초)은 첫 클래스가 아니라 실행마다 다른 클래스가 낸다(사실 5). 비용은 "처음 실행되는 클래스"가 아니라 "앞서 쌓인 상태에 따라 어느 클래스가 내느냐"에 달린 것으로 보이며 그 상태의 정체는 모른다.
- **H2. 두 fork가 CPU를 두고 경쟁해 같은 클래스가 느려진다.** **이 호스트의 깨끗한 실행에서는 관찰되지 않았다.** fork 2개(f2b)의 클래스 시간 합이 417초로 fork 1개(f1)의 412초와 같았고(+1%), 클래스 구간 폭은 412초에서 226초로 1.82배 줄었다. 외부 부하가 겹친 f2a에서는 합이 551초(+34%)로 늘어 외부 부하에는 민감했다. 이 결과는 8 vCPU 로컬 VM의 것이며 [ADR-0070](../02-decisions/adr/ADR-0070-parallel-backend-ci.md)이 적은 4 vCPU runner에서 fork 2개가 경쟁하는지는 검증하지 못했다.
- **H3. 컨테이너·컨텍스트를 클래스마다 새로 만드는 고정 비용이 shard 시간의 큰 부분이다.** **컨텍스트 기동은 기각, 나머지는 미해결.** Spring 기동 합은 클래스 시간 합의 약 16%다. 비싼 시간의 대부분은 테스트 메서드 밖에서 쓰이지만 그 정체(컨테이너 기동·종료, 컨텍스트 종료, 앞선 컨텍스트의 백그라운드 작업 중 무엇인지)는 모른다.
- **H4(새로 세워 기각). Spring 테스트 컨텍스트 캐시가 가득 차 오래된 컨텍스트를 닫는 비용이다.** Spring TestContext 캐시의 기본 한도는 32이고 이 저장소의 테스트 리소스와 `build.gradle`에서 한도 설정을 찾지 못했다. 비싼 클래스의 JVM 내 Spring 컨텍스트 순번이 f2a에서 1, 1, 2, 5, 10, 14, 18, 19, 20, 22, 28, f2b에서 1, 2, 10, 11, 14, 23, 25, 32로 대부분 32 이하이고, fork 1개(f1)에서 순번 32를 넘은 저렴한 클래스가 51개 중 21개였다. 예측과 맞지 않는다.

## 아직 하지 않은 개선 제안(효과는 측정하지 않음)

1. **컨테이너 공유**: 클래스마다 컨테이너를 띄우는 대신 JVM당 한 번만 띄우고 클래스마다 스키마를 나눠 쓴다. 이미 `ReservationEventTestSupport.migratedDataSource`가 같은 방식(스키마 분리)을 쓰고 있어 선례가 있다. 컨테이너 비용의 상한은 위 사실 2의 약 110초(로컬 기준)이며, 실제 절감은 CI runner에서 재야 한다.
2. **Spring 컨텍스트 재사용**: 같은 설정 키 집합을 쓰는 클래스끼리 한 컨텍스트를 공유하게 한다. 위험이 크다. 클래스가 서로의 데이터와 스케줄러 상태를 건드리지 않는다는 보장이 먼저 필요하고, 52개 클래스의 격리 가정을 깰 수 있다.
3. **가중치를 합이 아닌 fork 단위로 계산**: 사실 4가 맞다면 shard 균형의 기준을 바꿔야 하지만 효과를 시뮬레이션하지 않았다. 로컬 측정에서 fork 2개의 시간 합이 fork 1개와 같았으므로(H2) 이 제안의 전제는 더 약해졌다.
4. **클래스 시간으로 균형 잡는 방식 자체를 의심한다**: 같은 클래스가 2초에도 32초에도 나오므로(사실 5) 한 번의 실측으로 만든 클래스별 가중치는 예측력이 낮다. 비용의 정체를 모르는 채 가중치를 다듬어도 편차가 줄지 않은 것은 이 때문일 수 있다. 비싼 시간의 정체를 먼저 찾아야 한다.

네 제안 모두 이번에 구현하지 않았다. 구현 전에 사실 5의 비싼 시간이 무엇인지 찾는 것이 먼저다. 후보는 비싼 구간 중 테스트 워커 스레드 덤프, 컨테이너 기동·종료 시각 로그, 앞선 컨텍스트의 `close` 시각이다. [ADR-0070](../02-decisions/adr/ADR-0070-parallel-backend-ci.md)에서 가중치를 runner 실측으로 바꿔도 편차가 줄지 않았으므로, 효과를 측정하지 않은 개선은 같은 불확실성을 가진다.

## 한계

- 사실 3은 CI 실행 2회, 사실 2는 로컬 3회의 값이다. 사실 5는 로컬 유효 실행 3회(f1, f2b, 참고용 f2a)와 단일 클래스 실행 2회이고, 호스트는 8 vCPU Mac이다. CI runner(ubuntu-latest)의 값이 아니다. 표본이 작다.
- 클래스 이름은 CI 로그에서 잘린 형태(`Jdbc...Repositor`)를 소스 이름과 대응시킨 부분이 있다.
- 비싼 시간이 어디서 쓰이는지(테스트 메서드 밖, Spring 기동 밖)는 좁혔지만 무엇인지는 확정하지 못했다. 이 문서는 원인을 확정하지 않는다.
