# EXP-072: Kafka가 멈추거나 죽어도 relay는 이벤트를 잃지 않고, 클라이언트 응답은 영향받지 않는가

- 질문: 예약 workflow 이벤트를 order DB의 로그에서 Kafka로 내보내는 relay([ADR-0067](../02-decisions/adr/ADR-0067-event-log-kafka-relay.md))가 켜진 운영형 스택에서 Kafka를 `pause`하거나 `kill`하면, 이벤트가 유실되는가? 중복과 순서 뒤바뀜은 어떤 형태로 나타나는가? 예약 요청의 응답은 영향을 받는가? 복구에 얼마나 걸리는가?
- 상태: 탐색 실험. 시나리오별 n=1. **하네스는 저장소에 올리지 않았다**(아래 "코드를 올리지 않은 이유").
- 날짜: 2026-11-24
- 관련: [EXP-071](EXP-071-production-like-fault-injection.md)(같은 스택), [ADR-0067](../02-decisions/adr/ADR-0067-event-log-kafka-relay.md), 소비자 쪽 계약은 EXP-067(PR #518)

## 왜 했는가

relay의 안전성은 단위·통합 테스트로만 확인했다. `ReservationEventKafkaIntegrationTest`는 전송을 강제로 실패시켜 cursor가 그대로이고 재시도가 모든 이벤트를 전달한다는 것, 실패한 묶음이 중복 전달된다는 것을 단언한다. 그러나 이 테스트는 Kafka가 실제로 멈추거나 죽은 경우, application 2대가 relay를 함께 켠 경우, 부하가 계속 들어오는 경우를 다루지 않는다.

## 환경과 방법

- 구성: [EXP-071](EXP-071-production-like-fault-injection.md)의 운영형 스택(nginx, application 2대, location 2대, PostgreSQL 3개)에 Kafka 1대(`apache/kafka:3.9.1`, KRaft 단일 노드, 1 CPU, 768MiB, 재시작 정책 `unless-stopped`)를 더하고 두 application에서 relay를 켠다. 토픽은 자동 생성됐고 파티션 1개, 복제 1개다(`kafka-topics --describe`로 확인).
- relay 설정은 기본값이다: 묶음 500건, 폴링 0.2초, 전송 제한 10초, cursor lease 30초. producer는 `acks=all`, 멱등 활성화다. 두 application이 같은 cursor lease를 경쟁해 한 쪽만 전송한다.
- 부하: 초당 30건의 신규 예약을 70초(2,100건). 예약마다 이벤트가 2건 생겨 초당 약 60건이 로그에 쌓인다. 장애는 시작 15초 뒤 주입한다. 대조군은 40초(1,200건).
- 장애: `pause30`은 Kafka를 30초 `docker pause`, `kill20`은 SIGKILL 후 20초 뒤 `start`, `stop10x2`는 10초 `stop` 후 `start`를 15초 간격으로 2번.
- 감사: 이 실행이 만든 workflow의 이벤트 집합을 order DB에서 읽고, 토픽을 처음부터 읽은 메시지와 대조한다. 누락(DB에 있는데 토픽에 없음), 예상 밖 메시지, 중복(같은 `workflowId`와 `aggregateVersion`), 같은 키의 첫 전달이 버전이 거꾸로 도착한 횟수를 센다. relay lag은 2초마다 `이벤트 로그 최대 seq - cursor`로 읽는다.

## 결과

| --- | --- | --- | --- | --- | --- | --- | --- |
| control | 없음 | 2,400 | 2,400(2,400) | 0 | 0 | 11 | 해당 없음 |

| stop10x2 | 15.0~25.9초, 40.9~51.7초 | 4,200 | 4,200(4,200) | 0 | 0 | 843 | 6.3초 |
| app1kill | application 1을 15.0초에 kill, 25.2초에 start | 4,198 | 4,198(4,198) | 0 | 0 | 12 | 영향 없음 |

- 모든 시나리오에서 **누락 0, 예상 밖 메시지 0**이다. 모든 예약 요청은 `201 RESERVED`였고(대조군 1,200건, 장애 시나리오 각 2,100건) 응답 지연 p95가 0.015~0.023초였고 최대는 대조군 0.143초, 장애 시나리오 0.033~0.057초였다. 이벤트는 workflow 상태와 같은 트랜잭션으로 DB에 쌓이므로 Kafka 장애가 요청 경로에 닿지 않았다.
- lag은 장애 동안 초당 약 60건씩 늘었다(`pause30` 60.1, `kill20` 60.2). 이벤트 생산 속도와 같아 relay가 장애 중에는 하나도 내보내지 못했다는 뜻이다.
- **중복은 `pause`에서만 나왔다.** `pause30`에서 89건(키 42개)이 두 번 도착했고, 그중 44건은 이미 더 높은 버전이 전달된 뒤에 낮은 버전이 다시 온 것이다. 같은 토픽 전체(15,089건)에서 **키마다 첫 전달의 순서가 거꾸로인 경우는 0건**이었다. 즉 순서가 거꾸로 보이는 것은 모두 중복 재전달이다.
- 중복의 원인에 대한 해석(검증하지 않음): `pause`는 TCP 연결이 열린 채 응답만 멈춘다. relay의 한 묶음 전송이 10초 제한을 넘겨 실패로 처리돼 cursor가 움직이지 않는데, 이미 broker로 간 요청이 해제 뒤 기록되고 relay가 같은 묶음을 다시 보낸다. `kill`과 `stop`은 연결이 끊겨 요청이 기록되지 않아 중복이 없었다. 이 동작은 코드의 의도(전송이 실패한 묶음은 cursor를 옮기지 않고 다시 보낸다)와 테스트의 단언("실패한 묶음은 중복 전달된다")과 일치한다. 결함이 아니라 최소 한 번 전달의 모습이다.
- **relay를 가진 application을 죽여도 평소에는 영향이 없다. 단 Kafka가 멈춰 있을 때는 다르다.** `app1kill`과 `app2kill`에서 lag 최대는 12, 13으로 대조군(11)과 같았고 중복과 누락이 없었다. 응답 `502`는 `app1kill`에서 1건뿐이었다(죽은 application에 이미 전달된 요청으로 보이며 확인하지는 않았다). `app2kill`은 2,100건 모두 `201`이었고 `pausekill` 두 실행에도 `502`가 1건씩 있었다. 코드를 읽으면 이유가 보인다. `ReservationEventServiceImpl.relay`는 묶음마다 lease를 잡고(`claimLease`), 읽고, 전송하고, 성공하면 `advanceFenced`로 cursor를 옮기며 lease를 푼다. 실패하거나 묶음이 비면 즉시 `releaseLease`한다. 정상일 때 lease를 쥐는 시간은 Kafka 왕복 시간이라 죽이는 순간 쥐고 있을 확률이 낮다. Kafka가 멈추면 전송이 제한 시간(10초)까지 걸려 lease를 쥔 시간이 길어진다.
- **`pausekill1`이 이를 직접 보였다.** Kafka를 멈춘 채 app1을 죽이고 Kafka를 풀었는데, lag가 해제 후에도 1,586에서 1,834까지 올랐다가 9.4초 뒤에야 10으로 떨어졌다. 같은 조건에서 app2를 죽인 `pausekill2`는 해제 1.1초 만에 회복했다. 죽은 application이 쥔 lease는 만료(기본 30초)돼야 다른 replica가 인계한다. 죽은 시점(20.0초)에 lease가 있었다면 만료는 최대 약 50초이고 관측과 맞는다(lag가 45.6초에 정점, 49.7초에 10). **lease를 쥔 쪽이 app1이었다는 것은 직접 관측하지 않았다.** 한 쪽만 지연됐다는 사실에서 추정했다(보유자를 가리킬 열은 DB에 없다). 두 실행 모두 중복 12건, 키별 첫 전달의 순서 뒤바뀜 0건이다.
- 복구 시간은 장애 종류에 따라 다르다. `pause`는 해제 뒤 0.5초 안에 lag이 50 이하가 됐다(2초 간격 표본에서 lag 최대가 1,586이었고 해제 뒤 첫 표본이 50 이하였다). `kill` 뒤 Kafka를 `start`한 시점부터는 18.6초가 걸렸다. 이 18.6초에는 broker 기동, producer의 메타데이터 재조회, relay의 재시도 간격이 섞여 있고 분해하지 않았다.

## 이 결과가 증명하는 것과 아닌 것

- 증명한 것: 이 스택과 이 조건에서 Kafka의 `pause`(30초), `kill`(20초), `stop`(10초 2회) 동안 이벤트 누락이 없었고, 부하가 계속 들어오는 중에도 클라이언트 응답이 영향받지 않았으며, 장애 후 모든 이벤트가 전달됐다. 중복은 있을 수 있고 중복에 낮은 버전이 높은 버전 뒤에 오는 경우가 포함된다. 소비자가 `aggregateVersion`이나 `eventId`로 중복과 오래된 이벤트를 거르지 않으면 상태가 거꾸로 갈 수 있다(소비자 계약은 EXP-067).
- 증명하지 못한 것:
  - 시나리오별 n=1이다. 중복 건수(89)는 실행마다 다를 것이다.
  - 토픽 파티션이 1개다. 파티션이 여러 개일 때 키별 순서와 처리량은 다루지 않았다.
  - 장애가 20~30초로 짧다. 장기 중단에서 이벤트 로그가 얼마나 쌓이고(초당 약 60행이면 10분에 약 36,000행) 복구 중에 DB 부하가 어떻게 되는지는 측정하지 않았다.
  - 소비자가 없다. 토픽을 읽은 것은 감사용 콘솔 소비자뿐이다.
  - lease 인계는 `pause` 중에 죽이는 경우 n=1이다. lease 보유자를 직접 관측하지 않았고 인계가 만료에 따른 것이라는 해석은 시각의 일치에 기댄다. lease를 15초 등으로 줄였을 때 회복이 그만큼 앞당겨지는지는 시험하지 않았다. EXP-071의 application kill은 relay를 끈 상태였다.
  - Kafka 장애와 DB 장애가 동시에 일어나는 경우는 다루지 않았다.
  - 호스트 자원을 통제하지 않아 처리량·지연 절댓값은 일반화할 수 없다.

## 코드를 올리지 않은 이유

compose 파일, 부하·감사 스크립트는 Docker 소켓과 Colima VM에 의존하는 로컬 실험용이다. 저장소 밖에 보관하고 이 문서에 구성, 파라미터, 감사 방법을 적었다. **저장소만으로는 재현할 수 없다.**

## 후속 제안(적용하지 않음)

- lease 보유 중 죽인 경우의 회복이 `lease-duration`에 비례하는지(예: 15초, 30초, 60초) 같은 입력으로 비교한다. 설정 문서가 말하는 "send-timeout보다 5초 이상 길게" 제약 안에서 어느 값이 적당한지 정할 근거가 된다.
- 장기 중단(예: 10분)에서 로그 증가와 복구 중 DB 부하를 잰다. 로그 보관 정책이 필요한지 판단하는 근거가 된다.
- `pause`에서 중복이 생기는 조건을 줄일지 검토한다. 전송 제한(10초)과 producer 타임아웃의 관계를 조정하는 방안이 후보이나 효과는 측정하지 않았고, 최소 한 번 전달이 계약이므로 중복 제거는 소비자의 책임으로 두는 것이 기존 설계와 맞다.
