# EXP-039: 요청당 DB 작업량 측정과 "DB로 풀 수 있는 한계"

**추적 이슈:** [#360](https://github.com/Neo1228/ATLAS/issues/360)

**상태:** 실측 완료 · PostgreSQL 18.6, 2 vCPU, 2M 상품

## 왜 이 실험을 했는가

EXP-038에서 160 it/s(960 HTTP RPS)의 남은 드롭 4.9%를 두고 "쿼리 작업량"과 "DB 코어" 중 무엇이 원인인지 분리하지 못했습니다. 서버 CPU%만으로는 **어느 statement가 그 CPU를 쓰는지** 알 수 없습니다.

인프라를 도입하기 전에 답해야 할 질문은 하나입니다.

> DB가 지금 병목인가? 아니라면, 병목이 되기까지 얼마나 더 버티는가?

이 실험은 `pg_stat_statements`로 요청당 쿼리 수와 총 실행 시간을 측정해 그 질문에 답합니다.

## 방법

- `shared_preload_libraries=pg_stat_statements`, `track=all`로 PostgreSQL 재시작
- `pg_stat_statements_reset()` 후 부하 실행 → 측정 구간만 집계
- 부하: replica 3, Hikari pool 5, PgBouncer 경유, 60초
- 시나리오: 전 도메인 여정(목록→검색→상세→장바구니→체크아웃→결제)

## 결과

실행량: **1,801 iterations / 7,680 HTTP 요청 / 60초 = 128 HTTP RPS**

| 항목 | 값 |
| --- | ---: |
| 총 쿼리 호출 | **46,240** |
| HTTP 요청당 쿼리 | **6.02** |
| DB 총 실행 시간 | 4,115 ms |
| 그중 exporter·내부 통계 | 308 ms (7%) |
| **애플리케이션 DB 시간** | **3,807 ms** |
| **60초 중 DB 사용률** | **6.3%** (1코어 기준) |

### 상위 소비 statement

| 호출 | 평균 | 총 시간 | statement |
| ---: | ---: | ---: | --- |
| 3,602 | 0.406 ms | **1,463 ms** | `product_listing` 목록 조회 |
| 3,602 | 0.283 ms | **1,019 ms** | `seller_sku` 목록용 SKU 조회 |
| 3,602 | 0.135 ms | **485 ms** | `product_channel_availability` 조회 |
| 3,602 | 0.015 ms | 55 ms | `product_category_assignment` 조회 |
| 9,388 | 0.009 ms | 85 ms | `BEGIN READ ONLY` |

**목록 1건 = 4개 쿼리**. `product_listing` → SKU → 채널 → 카테고리를 각각 조회합니다. N+1은 아니지만(배치 `IN` 조회), **요청당 왕복이 4회**입니다.

### 핵심 수치

```text
목록 조회 3종 = 2,967 ms = 애플리케이션 DB 시간의 78%
목록 쿼리 호출 = 3,602건 = 전체 쿼리의 8%
```

즉 **소수(8%)의 쿼리가 대부분(78%)의 DB 시간을 쓰지만, 그 총량 자체가 작습니다.**

## 판정: DB는 지금 병목이 아니다

| HTTP RPS | 필요 DB 코어 |
| ---: | ---: |
| 128 (측정) | 0.06 |
| 512 | 0.25 |
| 1,024 | 0.51 |
| **2,048** | **1.02** |

측정된 DB 효율을 그대로 연장하면 **2 vCPU를 완전히 쓰려면 약 4,000 RPS**가 필요합니다. EXP-038에서 160 it/s(960 RPS)의 드롭은 **DB 코어 부족이 아니었습니다.**

이것이 EXP-038에서 남은 4.9% 드롭의 성격을 규정합니다. 원인은 DB가 아니라 다음 중 하나입니다.

- 애플리케이션 CPU(앱 2 vCPU에서 75% 관측)
- 커넥션 획득 대기(acquire 2.15초 관측)
- k6 생성기 자체의 한계(VU 768까지 확장됨)

## 그래서 캐시·replica를 지금 도입하지 않는 이유

목록 3종이 DB 시간의 78%를 차지하므로, 캐시하면 DB 시간이 **최대 78% 줄어듭니다**. 그러나 **줄어든 절대량이 3.8초/분**입니다. 지금 DB는 6.3%만 쓰고 있어, 78%를 없애도 병목이 옮겨갈 뿐 처리량이 늘지 않습니다.

캐시가 의미를 가지려면 **DB 사용률이 먼저 병목 수준(예: 70%)에 도달**해야 합니다. 현실적인 조건은 다음과 같습니다.

| 조건 | 근거 |
| --- | --- |
| DB CPU 70% 이상이 15분 지속 | 이 실험의 6.3%에서 10배 이상 |
| 목록 라우트 p95가 SLO 초과 | 현재 목록 p95는 13ms |
| 캐시 도입 후에도 primary 읽기가 병목 | 아직 미검증 |

## 대신 지금 할 수 있는 것 (DB로 해결 가능)

측정이 지목한 것은 **요청당 6.02 쿼리**입니다. 이는 인프라가 아니라 쿼리 통합으로 줄일 수 있습니다.

| 개선 | 예상 효과 | 근거 |
| --- | --- | --- |
| 목록 4쿼리 → 1쿼리(JOIN/집계) | DB 시간 78% 감소, 왕복 4→1 | 목록 3종이 78% |
| 커넥션 점유 시간 감소 | acquire 대기 완화 | acquire 2.15초 관측 |
| pool 왕복 감소 | 앱 CPU 감소 | 128 RPS에서 6쿼리/요청 |

즉 **다음 최적화는 인프라가 아니라 목록 조회의 쿼리 통합**입니다. 이것이 "DB만으로 해결할 수 있는 한계" 안에 있습니다.

## 이 실험의 한계

- 단일 호스트·로컬 Docker 측정이며 프로덕션 수치가 아닙니다.
- `pg_stat_statements`의 `total_exec_time`은 실행 시간만이며, 클라이언트 대기·네트워크·커넥션 획득 시간은 포함하지 않습니다. 따라서 "DB 사용률 6.3%"는 **DB가 실행에 쓴 시간**이고, 애플리케이션이 체감한 지연과 다릅니다.
- 쿼리 정규화로 서로 다른 파라미터가 하나로 합쳐집니다. 호출 수는 정확하지만 statement별 분포는 근사입니다.
- exporter 자체 쿼리(`pg_database_size`, `pg_stat_*`)를 308ms 제외했으며, 이는 측정 환경 특성입니다.

## 다음 단계

1. **목록 쿼리 통합**(4→1)을 구현하고 같은 부하로 재측정 → DB 시간과 p95 변화 확인
2. 통합 후에도 병목이면 그때 DB 코어 또는 캐시를 근거와 함께 검토
3. 160 it/s 드롭의 실제 원인(앱 CPU vs 커넥션 획득 vs 생성기)을 분리 측정
