# EXP-039: 요청당 DB 작업량 측정과 "DB로 풀 수 있는 한계"

**추적 이슈:** [#360](https://github.com/Neo1228/ATLAS/issues/360)

**상태:** 실측 완료 · PostgreSQL 18.6, 2 vCPU, 2M 상품

## 왜 이 실험을 했는가

EXP-038에서 160 it/s(960 HTTP RPS)의 남은 드롭 4.9%를 두고 "쿼리 작업량"과 "DB 코어" 중 무엇이 원인인지 분리하지 못했습니다. 서버 CPU%만으로는 **어느 statement가 그 CPU를 쓰는지** 알 수 없습니다.

인프라를 도입하기 전에 답해야 할 질문은 하나입니다.

> DB가 지금 병목인가? 아니라면, 병목이 되기까지 얼마나 더 버티는가?

이 실험은 `pg_stat_statements`로 요청당 쿼리 수와 총 실행 시간을 측정해 그 질문에 답합니다.

## 방법

- `shared_preload_libraries=pg_stat_statements`, `track=all`로 PostgreSQL 재시작
- `pg_stat_statements_reset()` 후 부하 실행 → 측정 구간만 집계
- 부하: replica 3, Hikari pool 5, PgBouncer 경유, 60초
- 시나리오: 전 도메인 여정(목록→검색→상세→장바구니→체크아웃→결제)

## 결과

실행량: **1,801 iterations / 7,680 HTTP 요청 / 60초 = 128 HTTP RPS**

| 항목 | 값 |
| --- | ---: |
| 총 쿼리 호출 | **46,240** |
| HTTP 요청당 쿼리 | **6.02** |
| DB 총 실행 시간 | 4,115 ms |
| 그중 exporter·내부 통계 | 308 ms (7%) |
| **애플리케이션 DB 시간** | **3,807 ms** |
| **60초 중 DB 사용률** | **6.3%** (1코어 기준) |

### 상위 소비 statement

| 호출 | 평균 | 총 시간 | statement |
| ---: | ---: | ---: | --- |
| 3,602 | 0.406 ms | **1,463 ms** | `product_listing` 목록 조회 |
| 3,602 | 0.283 ms | **1,019 ms** | `seller_sku` 목록용 SKU 조회 |
| 3,602 | 0.135 ms | **485 ms** | `product_channel_availability` 조회 |
| 3,602 | 0.015 ms | 55 ms | `product_category_assignment` 조회 |
| 9,388 | 0.009 ms | 85 ms | `BEGIN READ ONLY` |

**목록 1건 = 4개 쿼리**. `product_listing` → SKU → 채널 → 카테고리를 각각 조회합니다. N+1은 아니지만(배치 `IN` 조회), **요청당 왕복이 4회**입니다.

### 핵심 수치

```text
목록 조회 3종 = 2,967 ms = 애플리케이션 DB 시간의 78%
목록 쿼리 호출 = 3,602건 = 전체 쿼리의 8%
```

즉 **소수(8%)의 쿼리가 대부분(78%)의 DB 시간을 쓰지만, 그 총량 자체가 작습니다.**

## 판정: DB는 지금 병목이 아니다

| HTTP RPS | 필요 DB 코어 |
| ---: | ---: |
| 128 (측정) | 0.06 |
| 512 | 0.25 |
| 1,024 | 0.51 |
| **2,048** | **1.02** |

측정된 DB 효율을 그대로 연장하면 **2 vCPU를 완전히 쓰려면 약 4,000 RPS**가 필요합니다. EXP-038에서 160 it/s(960 RPS)의 드롭은 **DB 코어 부족이 아니었습니다.**

이것이 EXP-038에서 남은 4.9% 드롭의 성격을 규정합니다. 원인은 DB가 아니라 다음 중 하나입니다.

- 애플리케이션 CPU(앱 2 vCPU에서 75% 관측)
- 커넥션 획득 대기(acquire 2.15초 관측)
- k6 생성기 자체의 한계(VU 768까지 확장됨)

## 그래서 캐시·replica를 지금 도입하지 않는 이유

목록 3종이 DB 시간의 78%를 차지하므로, 캐시하면 DB 시간이 **최대 78% 줄어듭니다**. 그러나 **줄어든 절대량이 3.8초/분**입니다. 지금 DB는 6.3%만 쓰고 있어, 78%를 없애도 병목이 옮겨갈 뿐 처리량이 늘지 않습니다.

캐시가 의미를 가지려면 **DB 사용률이 먼저 병목 수준(예: 70%)에 도달**해야 합니다. 현실적인 조건은 다음과 같습니다.

| 조건 | 근거 |
| --- | --- |
| DB CPU 70% 이상이 15분 지속 | 이 실험의 6.3%에서 10배 이상 |
| 목록 라우트 p95가 SLO 초과 | 현재 목록 p95는 13ms |
| 캐시 도입 후에도 primary 읽기가 병목 | 아직 미검증 |

## 쿼리 통합은 실제로 얼마나 줄어드는가 (검증 후 정정)

처음에는 "목록 4쿼리를 1쿼리로 합치면 DB 시간이 78% 줄 것"이라고 적었습니다. 실제 계획을 측정하니 **틀렸습니다.**

측정한 사실:

| 항목 | 값 |
| --- | ---: |
| 목록 1건의 4개 쿼리 총 실행 시간 | **0.839 ms** |
| 페이지 조회만(100행) | 0.849 ms |
| 4쿼리를 1쿼리로 합친 `json_agg` 버전 | **47 ms** |

두 가지가 드러났습니다.

1. **통합해도 행 작업은 사라지지 않습니다.** 현재 0.839 ms는 100개 상품의 실제 행 읽기 비용입니다. 쿼리를 합치면 **왕복(round-trip) 3회**가 줄 뿐, 행 작업은 그대로입니다.
2. **JSON 집계 통합은 더 느립니다.** 47 ms vs 0.839 ms로 56배 악화됐습니다. `json_agg` 서브쿼리가 100행 각각에서 실행되기 때문입니다.

즉 "목록 3종이 DB 시간의 78%"는 **맞지만, 그 78%는 대부분 행 작업**이며 쿼리 수를 줄여서 없앨 수 없습니다.

### 그럼 남는 개선은 무엇인가

왕복 감소는 여전히 의미가 있습니다. 128 RPS에서 요청당 6.02 쿼리 중 4개가 목록용이므로, **커넥션 점유 시간**과 **앱의 JDBC 오버헤드**가 줄어듭니다. EXP-038에서 관측한 `acquire 2.15초`는 행 작업이 아니라 **커넥션을 잡고 있는 시간**의 문제였습니다.

| 개선 | 실제 효과 | 근거 |
| --- | --- | --- |
| 목록 4쿼리 → 1쿼리(단일 JOIN) | 왕복 3회 감소, 행 작업 동일 | 0.839 ms 중 행 작업이 대부분 |
| 행 작업 자체 감소 | 인덱스/커버링 인덱스 필요 | 별도 측정 필요 |
| 캐시 | 행 작업 제거(78% 가능) | 사용률 6.3%라 지금은 무의미 |

**정정된 결론:** 지금 단계에서 가장 확실한 개선은 **커넥션 점유 시간 단축**(왕복 감소·pool 튜닝)이며, 그것도 DB 사용률이 6.3%인 현 상태에서는 처리량을 늘리지 않습니다. 인프라든 쿼리든, **DB가 실제로 병목이 된 뒤에 손대야** 효과를 측정할 수 있습니다.

## 160 it/s 드롭의 정체: 전역 포화이지 특정 라우트가 아니다

EXP-038에서 남긴 "원인 미분리"를 보유한 측정 요약으로 다시 분석했습니다.

| 구성 | 초당 도착 | 완료 | 드롭 | 목록 p95 | 장바구니 쓰기 평균 | 달성 it/s |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| replica 3 | 40 | 4801 | 0% | 6.5 ms | 10.9 ms | 40.0 |
| replica 3 | 80 | 9601 | 0% | 7.3 ms | 10.9 ms | 80.0 |
| replica 3 + pooler | 160 | 18258 | 4.9% | **384 ms** | **438 ms** | 152.2 |

**핵심 비율:** 도착률 2배(80→160)에 처리량은 **1.9배**만 늘고, 지연은 **53배**(7.3→384 ms)가 됐습니다.

### 특정 라우트 문제가 아니다

160 it/s에서 모든 라우트가 균등하게 느려집니다.

| 라우트 | 평균 | p95 |
| --- | ---: | ---: |
| 목록 첫 페이지 | 384 ms | 1,826 ms |
| 목록 두 번째 페이지 | 379 ms | 1,810 ms |
| 상품 상세 | 354 ms | 1,803 ms |
| 검색 | 364 ms | 1,816 ms |
| 장바구니 조회 | 400 ms | 2,000 ms |
| 장바구니 쓰기 | 438 ms | 2,127 ms |
| 체크아웃 | 310 ms | 1,744 ms |

모든 라우트가 310–438 ms 구간에 몰립니다. 특정 쿼리나 특정 엔드포인트가 아니라 **공유 자원에서 대기**한다는 뜻입니다.

### 생성기 한계가 아니다

Little's Law로 동시성을 계산했습니다.

| 구성 | 달성 it/s | 평균 지연 | in-flight | VU |
| --- | ---: | ---: | ---: | ---: |
| pool 10 | 137.7 | 809 ms | **111** | 768 |
| pool 5 | 150.5 | 404 ms | **61** | 768 |
| pool 5 + pooler | 152.2 | 376 ms | **57** | 768 |

in-flight는 **57–111**인데 VU는 **768**입니다. 즉 k6가 VU를 768까지 늘렸지만 실제로 동시에 처리 중인 요청은 60개 안팎입니다. **생성기가 요청을 못 보내서가 아니라, 서버가 받은 요청을 오래 붙잡고 있어서** 드롭이 발생합니다.

### 남은 원인 후보

이 실험으로 DB 코어도, 생성기도 아니라는 것이 배제됐습니다. 남은 것은 두 가지입니다.

1. **JDBC 커넥션 대기** — EXP-038에서 `acquire_seconds_max` 2.15초, `pending` 51을 관측했습니다. 모든 라우트가 커넥션을 필요로 하므로 전역 지연과 일치합니다.
2. **애플리케이션 CPU** — 앱 2 vCPU에서 75% 관측. 다만 CPU만으로 53배 지연을 설명하기는 어렵습니다.

**가장 유력한 것은 커넥션 대기**입니다. in-flight 57–111이 pool 5(replica당) × 3 = 15를 크게 넘고, pooler를 붙였을 때 드롭이 6.0%→4.9%로 줄었기 때문입니다.

### 판정과 검증

160 it/s는 **DB 코어도, 생성기도 아니다**는 것이 배제됐습니다. 다음 후보는 커넥션 계층이었고, 이를 pool 5→20 실험으로 직접 검증했습니다(아래 "연결 예산 실험"). 결과는 **pool 확대가 오히려 붕괴를 일으킨다**였습니다.

## 연결 예산 실험: pool을 늘리면 더 나빠진다

"커넥션 대기가 원인"이라는 가설을 직접 검증했습니다. pool을 replica당 5 → **20**으로 4배 늘리고 같은 160 it/s를 측정했습니다.

| 구성 | replica당 pool | 총 연결(3대) | 완료 | 드롭 | 달성 it/s |
| --- | ---: | ---: | ---: | ---: | ---: |
| pool 5 + pooler | 5 | 15 | 18,258 | **4.9%** | 152.2 |
| **pool 20 + pooler** | **20** | **60** | **5,165** | **73.1%** | **43.0** |

**풀을 4배 늘렸더니 처리량이 3.5분의 1로 떨어졌습니다.**

### 원인: PostgreSQL 연결 상한 초과

측정 중 DB가 다음 오류를 **261회** 기록했습니다.

```text
FATAL: sorry, too many clients already
```

`max_connections=60`인데 3 replica × pool 20 = **60**에 pooler·exporter·psql·모니터링이 더해져 상한을 넘었습니다. 애플리케이션은 커넥션을 얻지 못해 요청을 처리하지 못했고, 그것이 73% 드롭으로 나타났습니다.

### 이 실험이 확정한 것

| 항목 | 결과 |
| --- | --- |
| pool 확대가 처리량을 늘리는가 | **아니다.** 4배 확대에 처리량 3.5배 감소 |
| 커넥션 상한이 실제 병목인가 | **그렇다.** 상한 초과 시 즉시 붕괴 |
| 적정 pool은 얼마인가 | 연결 예산 안에서 결정해야 하며, 크기 자체가 성능을 만들지 않는다 |

이것은 HikariCP 위키와 AWS 문서가 말하는 "연결 증설은 처리량을 늘리지 않는다"를 **우리 환경에서 직접 재현한 결과**입니다. 동시에 "pool이 작으면 병목"이라는 반대 가설도 함께 반박합니다. pool 5에서 이미 152 it/s를 냈고, 20에서는 오히려 무너졌습니다.

### 정정: 그 4.9%는 pooler를 거치지 않은 측정이었다

EXP-038의 "pool 5 + pooler" 수치는 실제로 **pooler를 경유하지 않았습니다.** `compose.capacity-distributed.yaml`이 replica에 `ATLAS_DB_URL: jdbc:postgresql://postgres:5432/atlas`를 하드코딩해, 뒤에 추가한 pooler 오버레이의 URL을 덮어썼습니다.

이를 `${ATLAS_DB_URL:-...}`로 바꾸고 재측정했습니다.

| 구성 | 완료 | 드롭 | avg | p95 | 달성 it/s |
| --- | ---: | ---: | ---: | ---: | ---: |
| replica 3, **postgres 직접** (기존 "pool5+pooler") | 18,258 | 4.9% | 376 ms | 1,856 ms | 152.2 |
| replica 3, **실제 pooler 경유** | **24,001** | **0%** | **2 ms** | **4 ms** | **160.0** |

150초 부하에서 **드롭 0, 평균 2 ms, p95 4 ms**로 목표 도달률을 정확히 맞췄습니다. 주문 372건·결제 372건도 정상 처리됐습니다.

### pooler 대기 지표 (측정 중 7회 샘플)

| 시각 | client_waiting | client_maxwait | server_active | server_idle |
| ---: | ---: | ---: | ---: | ---: |
| 15–105초 | **0** | **0 s** | 1–2 | 4–9 |

pooler는 **한 번도 클라이언트를 세우지 않았고**(waiting 0, maxwait 0), 서버 연결도 1–2개만 활성입니다. 즉 pooler는 병목이 아니라 **정상 동작하는 다중화 계층**입니다.

### 왜 2 ms가 나오는가

pooler를 경유하면 각 애플리케이션 인스턴스가 짧은 트랜잭션마다 서버 연결을 빌려 씁니다. 직접 연결에서는 15개 연결이 계속 점유되어 PostgreSQL이 60개 상한에 가까워졌고, 그것이 376 ms 지연으로 나타났습니다.

이는 EXP-038의 "pooler가 드롭을 6.0%→4.9%로 줄였다"는 결론도 정정합니다. 그 측정에서는 pooler가 **아예 쓰이지 않았으므로** 그 차이는 측정 잡음이었습니다.

### 실제 확장 곡선: 320까지 여유, 640에서 붕괴

pooler를 정상 경유한 상태에서 부하를 2배씩 올렸습니다.

| Offered it/s | HTTP RPS | 완료 | 드롭 | avg | p95 | pooler waiting | server active/idle |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 160 | 480 | 24,001 | **0%** | 2 ms | 4 ms | 0 | 1–2 / 4–9 |
| 320 | 960 | 38,400 | **0%** | 2 ms | 5 ms | 0 | 3–8 / 7–12 |
| **640** | 1,920 | 27,603 | **62.9%** | **2,400 ms** | **5,625 ms** | 0 → **15 active, 0 idle** | 포화 |

**한계는 320~640 it/s 사이**입니다. 320 it/s(960 HTTP RPS)까지는 평균 2 ms를 유지했고, 640 it/s에서 평균이 2 ms → 2,400 ms로 **1,200배** 악화되며 63%가 드롭됐습니다.

### 640에서 무엇이 포화됐는가

측정 중 pooler 서버 연결 샘플:

| 시각 | active | idle |
| ---: | ---: | ---: |
| 18–36초 | 12 | 3 |
| 54초 | 14 | 1 |
| 90초 | **15** | **0** |

`DEFAULT_POOL_SIZE=24`인데 **active가 15에서 멈췄습니다.** 이는 PostgreSQL 쪽 상한(`MAX_DB_CONNECTIONS=32`)이나 DB 처리 능력이 아니라, **서버 연결 15개로는 1,920 RPS의 트랜잭션을 소화하지 못한다**는 뜻입니다.

이때 `client_waiting`은 0으로 유지됐습니다. pooler가 클라이언트를 세우지 않고도 지연이 2,400 ms가 된 것은, **각 트랜잭션이 서버 연결을 오래 점유**하기 때문입니다.

### 이 실험이 확정한 확장 경계

```text
검증된 안전 구간 : 320 it/s = 960 HTTP RPS  (avg 2 ms, drop 0)
붕괴 시작       : 640 it/s = 1,920 HTTP RPS (drop 63%, avg 2.4 s)
```

이 구간에서 **DB CPU는 6.3%**였습니다(128 RPS 측정 기준). 즉 960 RPS까지는 DB가 병목이 아니며, 병목은 **커넥션 다중화 계층의 서버 연결 수**입니다.

### 그럼 160 it/s의 4.9% 드롭은 무엇인가 (정정 전 기록)

pool 5 + pooler에서 152.15 it/s를 달성했고, 도착률 160과의 차이는 4.9%입니다. 이는 연결 고갈이 아니라 **다음 중 하나**입니다.

- 앱 CPU(2 vCPU에서 75% 관측)
- pooler의 서버 풀(`DEFAULT_POOL_SIZE=24`) 대기
- 요청당 평균 400 ms 지연에서 오는 자연스러운 큐 지연

이 셋을 분리하려면 pooler 쪽 지표(`pgbouncer` pool 대기 시간)를 수집해야 하며, 이번 실험에는 없습니다.

## 이 실험의 한계

- 단일 호스트·로컬 Docker 측정이며 프로덕션 수치가 아닙니다.
- `pg_stat_statements`의 `total_exec_time`은 실행 시간만이며, 클라이언트 대기·네트워크·커넥션 획득 시간은 포함하지 않습니다. 따라서 "DB 사용률 6.3%"는 **DB가 실행에 쓴 시간**이고, 애플리케이션이 체감한 지연과 다릅니다.
- 쿼리 정규화로 서로 다른 파라미터가 하나로 합쳐집니다. 호출 수는 정확하지만 statement별 분포는 근사입니다.
- exporter 자체 쿼리(`pg_database_size`, `pg_stat_*`)를 308ms 제외했으며, 이는 측정 환경 특성입니다.

## 다음 단계

검증된 경계(`320 it/s` 안전, `640 it/s` 붕괴)를 기준으로 다음을 진행합니다.

1. **pooler 서버 연결 확대** — 640에서 `active`가 15에서 멈췄습니다. `DEFAULT_POOL_SIZE` 24→48과 `MAX_DB_CONNECTIONS` 32→64로 같은 부하를 재측정해, 병목이 pooler 설정인지 확인합니다.
2. **PostgreSQL 상한 확인** — 연결을 늘렸을 때 DB가 받아주는지(`max_connections`), 받는다면 DB CPU가 어디까지 오르는지 측정합니다.
3. **앱 replica 추가** — 앱 CPU가 병목이 되는 지점을 확인하고, 그때 수평 확장이 처리량을 늘리는지 검증합니다.
4. DB 사용률이 70%에 도달하면 **그 시점에** 캐시·read replica를 검토합니다.

인프라 도입은 이 순서를 따릅니다. 측정이 지목하지 않은 계층은 손대지 않습니다.
