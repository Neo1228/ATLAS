# EXP-091: broker pause 뒤 같은 키의 높은 버전이 낮은 버전보다 먼저 첫 전달되는 원인은 무엇이고 어디서 막아야 하는가

- 질문: [#644](https://github.com/Neo1228/ATLAS/issues/644)에서 `pause20`을 새 스택에서 처음 도는 실행(run-1)에 한해 같은 workflow의 v2가 v1의 첫 전달보다 앞선 offset에 쌓였다(보조 실행 39회 중 3회, 누락 0). 원인(producer, relay, 감사 도구, broker 중 어느 층)은 무엇이고, 가장 단순한 올바른 층에서 어떻게 막는가? 그리고 같은 consumer group의 소비자 둘 사이에 리밸런스가 일어나도 `(workflowId, version)` 단위의 실효 1회 적용이 유지되는가?
- 상태: 완료(로컬). 가설 절과 "수정 이력"은 실행 전에 커밋했고(git 이력이 증거, 수정 1~5는 해당 캠페인 결과를 보기 전의 커밋이다) 결과·결론 절은 실행 뒤에 덧붙였다. 사전 등록한 설계 두 개(음성 대조군, 노출 정의)가 틀렸고 수정 이력에 있다. 원인 메커니즘은 로그와 세그먼트 덤프로 확인했고 수정은 운영 코드로 144 시행-단계에서 위반 0이다. 원자료는 저장소에 두지 않았고(`/tmp`, 커밋하지 않음) 집계값과 방법을 이 문서에 적었다.

## 문제 (한 문장)

relay가 보낸 이벤트를 `aggregateVersion` 없이 도착 순서대로 적용하는 소비자는, broker가 20초 멈췄다 풀린 뒤 상태를 거꾸로 되돌릴 수 있다. 관측된 빈도는 보조 실행 39회 중 3회(7.7%), 한 실행의 workflow 1,000개 중 14~20개(1.4~2%)가 영향을 받았고, 누락은 0이었다. 원인이 어느 층인지 모르는 채 `aggregateVersion` 검사에만 기대고 있다(수치는 모두 [EXP-089](EXP-089-kafka-outage-repeated.md)에서 가져왔고, "첫 실행에서만"이라는 패턴은 사후에 찾은 것이다).

## 이미 아는 것 (EXP-089 증거와 코드 읽기, 아직 새로 실행한 것은 없다)

- 위반 실행의 파티션 0은 offset 0~132가 seq 10~392, offset 133~157이 seq 387~415와 764~798, offset 158부터 seq 387~2000이다.
- 이 값을 시간으로 환산하면(초당 40건) 부하 10초 지점이 seq 약 400이다. 다시 말해 첫 시도의 묶음은 seq 387부터 시작하고, 전송 한도(10초) 뒤 재시도한 묶음은 약 seq 387~798이다. 764~798은 재시도 묶음의 끝 부분과 겹친다. 이 해석은 **추정**이며 가설로만 쓴다.
- relay 코드: 한 묶음을 `kafka.send`로 전부 낸 뒤 `allOf(...).get(전송한도+1초)`를 기다린다. 시간이 지나 예외를 던져도 이미 낸 레코드는 producer 안에 남아 있고 취소되지 않는다. producer는 `acks=all`, `enable.idempotence=true`, `delivery.timeout.ms=10000`, `request.timeout.ms=5000`, `linger.ms=5`이고 `max.in.flight.requests.per.connection`은 기본값(5)이다. kafka-clients 4.2.2, broker는 `apache/kafka:3.9.1`이다.

## 설계

### 재현기 (결정적 재현이 아니라 고빈도 재현)

실제 relay 경로(DB, lease, 앱 두 대)는 실행 한 번이 스택 기동까지 합쳐 수 분이라 위반 빈도 0.2 수준의 사건을 여러 번 보기에 비싸다. 같은 층(producer와 broker)만 떼어 내 재현기(Java 단일 파일, 저장소 `load-tests/kafka-outage/` 아래)를 만든다. 재현기는 relay의 읽기→전송→대기→cursor 전진 루프를 메모리 이벤트 로그 위에서 그대로 흉내 낸다.

- producer 설정: `ReservationEventConfiguration`과 같은 값을 그대로 쓴다(acks=all, idempotence, delivery.timeout 10초, request.timeout 5초, linger 5ms, max.in.flight 기본 5).
- relay 루프: 0.2초 간격 poll, 묶음 500, 전송 후 `allOf.get(11초)`, 실패하면 lease를 풀고 다음 poll에서 replica 중 하나가 무작위로 잡는다(replica 1대 조건은 항상 같은 producer).
- 부하: 초당 20 workflow, workflow마다 v1과 약 1초 뒤 v2(실행 한 번당 이벤트 2,000건), 부하 10초 뒤 broker를 `docker pause` 20초(EXP-089 `pause20`과 같다).
- broker: `apache/kafka:3.9.1` 단일 노드 KRaft, 토픽 파티션 3개·복제 1개, 컨테이너 하나(`atlasexp=h1` 라벨).
- 판정: 각 시행의 토픽 내용을 파티션·offset 순서로 읽어 `outage_audit.delivery_order`(하네스 감사와 같은 함수)에 넣는다. 위반 시행은 세그먼트를 `kafka-dump-log.sh`로 덤프해 batch 단위 producerId, epoch, baseSequence, offset을 본다.
- 시행(trial) 하나는 독립된 토픽과 producer(들)이다. 한 라운드에서 시행 여러 개를 한 broker 위에서 동시에 돌리고(broker pause는 라운드 단위로 공유), 라운드는 broker를 새로 띄운다. 시행마다 장애를 두 번 겪는다(첫 장애는 cold, 두 번째는 warm). 시행 사이는 서로 다른 토픽·producer라 독립이지만 같은 broker·같은 장애 시각을 공유하므로, 보고에는 시행 단위와 라운드 단위를 같이 쓴다.

### 조건

| 조건 | 내용 | 역할 |
| --- | --- | --- |
| `R2` | replica 2대, relay 설정 그대로 | 원래 조건의 재현 |
| `R1` | replica 1대, 나머지 같음 | HC 판별 |
| `R2mif1` | `R2`에 `max.in.flight.requests.per.connection=1` | HB 판별, 후보 수정 |
| `R2b100` | `R2`에서 relay 묶음만 100(현재 main 기본값, 수정 이력 1) | 현재 기본값에서도 나오는지 |
| 각 조건의 두 번째 장애 | 같은 producer에서 두 번째 pause | HD 판별 |

수정안 후보(원인이 밝혀진 뒤에 같은 재현기로 비교한다. 후보와 결정 기준은 이 문서의 "수정 이력"에 그 시점의 커밋으로 남긴다):

- F1 `max.in.flight.requests.per.connection=1`.
- F2 relay가 전송 실패 시 producer를 닫아 남은 레코드를 버린다(재시작).
- F3 묶음마다 이전 묶음의 모든 레코드가 완료(성공이나 실패)됐음을 확인한 뒤에만 다음 묶음을 보낸다.
- F0 아무것도 바꾸지 않고 소비자 계약(`aggregateVersion` 기준 적용)에만 기댄다(do nothing).

### 대조군

- 무변경 대조군: `R2` 원래 설정에서 장애를 넣지 않은 시행(위반 기대 0, 이것이 0이 아니면 재현기나 감사가 틀린 것이다).
- 음성 대조군(검출기가 반드시 울려야 하는 경우): (1) 합성 토픽에 키별 v2를 v1보다 앞에 쓴 입력을 넣어 감사가 위반으로 센다. (2) 정상 재전달(같은 묶음이 순서대로 다시 옴)만 있는 합성 입력은 첫 전달 위반 0이고 재전달 역행 수만 센다. (3) 실제 broker에 producer 두 개로 레코드를 일부러 엇갈려 보낸 토픽(알려진 역행)이 감사와 세그먼트 덤프에서 모두 위반으로 나온다.
- 전후 비교: 같은 재현기·같은 broker 이미지·같은 부하이고 시행 순서는 라운드마다 조건을 섞는다. 첫 20초(워밍업)는 판정에 쓰지 않는다.

### 표본 크기와 종료 기준

- 원래 관측은 첫 장애에서 중복이 생긴 16건 중 3건(약 0.19, 사후에 찾은 값이라 가정이다). 조건당 첫 장애 시행이 n=18이면 p=0.19일 때 1회 이상 볼 확률은 1−0.81^18≈0.98이다.
- 조건당 n=18에서 0건이면 3/n=0.167(95% 상한, rule of three)이라 0.19와 가를 수 없다. 이때는 라운드를 6까지 늘려 n=36(상한 0.083)에서 멈춘다. 그래도 0건이면 "재현하지 못함, 위반 확률 상한 8.3%"로 기록하고 원인을 확정하지 못했다고 쓴다.
- 수정안은 수정 전 조건에서 위반이 확인된 뒤에만 같은 n으로 시험하고, 위반 0이 나오면 3/n 상한을 같이 쓴다.
- 시행이 라운드 안에서 같은 pause를 공유하므로 효과적 독립 단위는 라운드와 시행 사이 어딘가다. 상한은 시행 단위와 라운드 단위(더 보수적)를 같이 적는다.

### 층별 조사 순서

앱 로그·relay 시도 기록 → producer debug 로그(epoch, sequence, batch id) → broker 로그·세그먼트 덤프 → 필요하면 tcpdump → 그 아래(런타임 thread dump, GC, cgroup)는 증거가 거기를 가리킬 때만 간다. 멈춘 층과 이유를 결과에 적는다.

### 소비자 리밸런스(두 번째 질문)

EXP-082의 시험용 참조 소비자(`ReservationEventReferenceConsumer`)를 확장해 같은 group에 소비자 둘을 두고, 전달 도중 하나를 죽이거나 하나를 추가한다. 불변식: (a) 모든 `(workflowId, version)`이 최종적으로 적용되고, (b) 어떤 workflow도 낮은 버전이 높은 버전 뒤에 적용되지 않으며, (c) 같은 `(workflowId, version)`이 두 번 적용되지 않는다(한계: 적용 기록과 offset commit이 한 트랜잭션이라는 전제). 반복 n≥5, 가설 HF는 "리밸런스를 가로질러도 위 세 불변식이 유지된다"이며 반증 조건은 하나라도 어긋난 시행이다. 첫 전달 역행이 있는 입력(합성)에서도 같은 불변식이 유지되는지 확인한다.

## 사전 위험과 중단 조건

- 재현기가 실제 relay와 다르게 동작해 현상이 안 나올 수 있다 → 재현기에서 안 나오면 실제 하네스(`run-kafka-outage.sh`)를 `pause20`으로 반복해 같은 조건을 시험한다(그때 n과 중단 기준은 같다).
- 호스트가 공유돼 pause 시각이 흔들린다 → 판정은 개수와 불변식으로만 한다. 시작·종료 시 `uptime`을 남긴다.
- 컨테이너는 라벨 `atlasexp=h1`로만 만들고 끝에 라벨로 0개를 확인한다.

## 수정 이력

- 수정 1(첫 라운드 실행 전, 같은 커밋): (a) 조건 `R2b100` 추가. 코드를 읽다가 `origin/main`의 relay 묶음 기본값이 이미 100으로 바뀌었음([ADR-0082](../02-decisions/adr/ADR-0082-relay-batch-size-and-producer-log.md))을 확인했다. 이슈의 위반은 모두 묶음 500·2,000에서 나왔으므로 현재 기본값에서의 상태를 따로 봐야 한다. 가설과 판정 기준은 바꾸지 않았다. (b) 재현기 기계 동작을 확인하려고 사전 등록 라운드 전에 스모크 실행을 한 번(`R2` 1시행, 장애 1회) 했다. 이 실행은 위반 19건이 나왔고 표본 n에 넣지 않는다(결정에 쓰지 않음). 그 실행에서 broker 세그먼트 덤프가 비어(로그 경로 설정 누락) 고쳤고, 시험 코드의 음성 대조군 기대값 하나가 틀려 고쳤다(감사 함수는 그대로).
- 수정 2(첫 라운드 실행 전): 스모크 실행의 producer DEBUG 로그에서 가설 HG를 세웠다. 근거 관찰 세 가지: 같은 시도의 batch 다섯 개가 요청 시한(5초)으로 한꺼번에 연결이 끊기고 `Reordered incoming batch with sequence ...`로 재정렬됐다. 그 뒤 `ProduceResponse returned SUCCEEDED ... after batch with base offset ... had already been FAILED`(실패 처리한 batch를 broker가 나중에 기록)가 나왔다. 두 번째 시도가 시작된 시각에서 전송 한도(10초)를 더한 시각이 unpause 시각(pause 20초)과 겹쳤다. 이 관찰들은 한 번의 스모크 실행에서 나온 것이라 가설일 뿐이고, 판정은 사전 등록된 라운드의 숫자로만 한다. 조건 `R2b100`에 "파티션당 batch 하나" 예측이 걸려 있어 새 조건은 필요 없다. pause 길이 스윕(15, 18, 20, 22, 25초)을 `R2`·`R2b100`에 추가한다(시행 n은 표와 같은 방식으로 라운드당 6).
- 수정 3(첫 라운드 실행 전): 장애 없는 대조 라운드(`ctl1`: `R2nofault` 시행 3, `NEGreverse` 시행 3, 장애 단계 2회씩)를 먼저 돌렸다. 장애 없는 `R2nofault`는 위반 0, 중복 0, 누락 0이었다(무변경 대조군 통과). 그러나 `NEGreverse`(묶음을 거꾸로 보내는 음성 대조군)도 장애가 없으면 **위반 0이었다**. 원인: v1과 v2는 약 1초(20건) 떨어져 만들어지고 relay는 0.2초마다 몇 건씩 읽으므로 둘이 같은 묶음에 들어가지 않아 묶음을 뒤집어도 순서가 바뀌지 않는다. 이 음성 대조군은 장애 없이는 설계가 틀렸다(감사가 못 잡은 것이 아니라 역행 자체가 없었다). 고침: `NEGreverse`는 장애를 건 라운드(밀린 묶음에 v1·v2가 함께 있음)에 넣는다. 이 조건에서 위반이 크게 나와야 음성 대조군이 통과이고, 위반 0이면 라운드 전체 결과를 믿지 않는다. 추가 음성 대조군으로 감사 함수 단위 시험(합성 입력)을 이미 올렸다.
- 수정 4(캠페인 1 결과를 본 뒤, 캠페인 2 실행 전): 캠페인 1(`main1`~`main3`, 라운드 3개, 조건당 시행 6, 장애 2회, 시행 총 90)의 결과가 사전 등록된 표본 계획과 맞지 않아 설계를 바꾼다. **관측**: 음성 대조군 `NEGreverse`는 36회(시행 18 × 단계 2) 전부 위반(최소 약 360건)으로 울렸다. 장애 없는 대조군은 위반 0. 원래 조건 `R2`는 첫 장애 18시행 중 위반 0(3/18=0.167 상한)이었고 `R1`도 0/18, `R2b100`도 0/18이었으며, 위반은 `R2mif1`의 첫 장애 18시행 중 1건(최대 in-flight 1에서도 나옴)이었다. 이 1건의 세그먼트 덤프는 아래 "결과"에 쓴다. 이 시점에 HG는 덤프로 지지됐고 HB의 예측(`max.in.flight=1`이 막는다)은 이 1건으로 반대됐다. 그러나 위반 빈도가 너무 낮아(스모크 1건 포함 2건) 조건 간 비교에는 쓸 수 없다. **사후 분석(탐색, 판정 아님)**: 위반 두 건(스모크 `+18ms`, `R2mif1-t18` `+11ms`)은 모두 장애 구간의 마지막 실패한 시도가 끝난 시각이 unpause 시각보다 11~18ms 늦은 시행이었다. 이 값이 [0, 100)ms인 시행 14개 중 2건, 나머지 구간 105개 중 0건이다. **설계 변경**: (1) 노출 정의 사전 등록: 장애 단계마다 시행의 마지막 실패 시도(이벤트 10건을 넘는 시도)의 끝 시각 − unpause 시각 `W`가 [0, 60]ms이면 그 단계를 "노출"로 센다. 판정은 (조건별) 위반 수 / 노출 수로 한다. (2) 시행의 relay poll 위상(0.2초 주기 안의 시작 위치)을 조건 안에서 고르게 나눠 `W`가 넓게 퍼지게 한다(주기와 설정은 relay와 같다). (3) 단계를 3회로 늘리고 조건 12시행씩 라운드 2종을 각 3회: 라운드 A는 `R2`·`R1`·`R2mif1`, 라운드 B는 `R2`·`R2chunk`(F3)·`R2reset`(F2). **캠페인 2 예측**: (a) `R2`의 노출 단계 중 위반 비율 ≥ 0.3이고 노출이 아닌 단계는 위반 0. (b) `R1`과 `R2mif1`의 노출 단계 위반 비율이 `R2`와 같다(producer 수와 `max.in.flight`가 무관). (c) `R2chunk`는 노출 단계 위반 0이다(노출 수 E일 때 상한 3/E를 같이 적는다). (d) `R2reset`은 위반이 줄지만 0이 아닐 수 있다(예측 약함: 닫는 시각과 unpause 시각의 경쟁). **반증 조건**: `R2` 노출 단계에서 위반 비율 < 0.1이면 노출 정의(타이밍)가 틀린 것이고 HG의 시간 의존 설명을 기각한다. `R1`이 노출 단계에서 위반 0(E≥10)이면 producer 하나로는 안 된다는 뜻이라 HG를 기각한다. `R2chunk`가 위반하면 F3를 채택하지 않는다.

## 결과

모든 수치는 로컬 단일 Docker 호스트(Colima, 다른 실험이 동시에 돌아 `uptime` load average 20~30, 시간 값은 맥락용)의 재현기 실행이다. 재현기는 relay의 전송 루프를 메모리 이벤트 로그 위에서 흉내 내며(DB·lease는 같은 규칙, 단일 파일 `load-tests/kafka-outage/RelayOrderRepro.java`), `real` 모드는 운영 `KafkaReservationEventPublisher`·`ReservationEventConfiguration` 클래스를 그대로 쓴다. 용어: **시행-단계** = 시행 하나가 겪은 장애(pause 20초) 한 번. 위반 = 키별 첫 전달 순서 위반이 1건 이상인 시행-단계. 토픽은 시행마다 따로(3 파티션), broker 하나를 시행들이 공유하고 pause 시각이 같다.

- 현재 기본값(묶음 100, [ADR-0082](../02-decisions/adr/ADR-0082-relay-batch-size-and-producer-log.md))의 모사 `R2b100`은 36 시행-단계에서 0이었다. 이 n으로는 상한이 8.3%라 "이미 막혔다"고 말할 수 없다. 묶음 100(약 11KB)은 파티션 3개에 나뉘어 batch가 대부분 하나이므로 확률이 낮을 뿐이다(운영 클래스 `base`는 묶음 500에서 측정했고 묶음 100은 운영 클래스로 재지 않았다).

### 3. 메커니즘 (로그와 세그먼트 덤프)

한 위반 시행의 producer DEBUG 로그, 같은 시행의 broker 세그먼트 덤프(`kafka-dump-log.sh`: batch마다 producerId, epoch, baseSequence), relay 시도 기록을 맞춘 결과:

1. relay가 500건 묶음을 보내면 producer는 한 파티션에 batch를 여러 개(16KB `batch.size`, linger 5ms) 만들어 `max.in.flight=5`로 동시에 보낸다.
2. broker가 pause되면 요청 시한(5초)에 연결이 끊기고(`Disconnecting ... due to request timeout`) batch가 큐에서 재정렬되며(`Reordered incoming batch`) 재시도된다. `delivery.timeout.ms`(10초)는 **batch마다 생성 시각 기준**으로 흐른다. unpause가 이 시한 근처에서 오면 먼저 만들어진 batch는 만료돼 폐기되고 나중에 만든 batch는 아직 살아 있다.
3. 만료로 producer는 `No inflight batches remaining ... Going to bump epoch and reset sequence numbers`로 epoch를 올리고 sequence를 0부터 다시 매긴다. 살아남은 뒤 batch가 broker에 먼저 기록된다(`ProduceResponse returned SUCCEEDED ... after batch ... had already been FAILED`는 스모크에서 관찰).
4. relay는 시도 전체를 실패로 보고 같은 묶음을 다시 보낸다. 다시 보낸 묶음은 처음부터이므로 이미 기록된 뒤쪽 v2 다음에 앞쪽 v1이 온다(첫 전달 순서 역행). 이슈 #644의 형태(offset 133~157에 seq 387~415와 764~798, 그다음 offset 158에서 387부터 다시)와 일치한다. 위반 시행 하나의 batch 목록에서도 같은 형태를 보았다: 한 파티션에서 epoch 1의 batch 뒤에 baseSequence 0의 epoch 2 batch(seq 673~777)가 먼저 오고 그다음에 같은 relay 시도의 앞부분(seq 376~)을 다시 보낸 batch가 온다.

집계(스모크와 캠페인 1~2의 모든 라운드에서 위반 키를 세그먼트로 분류. 덤프에서 batch를 찾지 못한 19키는 분류에서 빠졌고 아래 325키는 찾은 것이다):

| 분류 | 키 수(전체 325) |
| --- | --- |
| v1과 v2가 모두 하나의 **실패한 relay 시도** 안에 있었음 | 325 (100%) |
| 높은 버전이 실린 batch가 epoch가 오른 직후 첫 batch(epoch>0, baseSequence 0) | 287 (88%) |
| 두 버전이 같은 producerId | 181 (56%) |
| 높은 버전 batch가 epoch 0 | 15 |
| 낮은 버전 batch의 epoch가 더 높음 | 59 |

해석: 분류한 위반 전부가 "한 시도 안에 v1·v2가 함께 있고 그 시도가 실패한 경우"다(필요조건). 88%는 epoch 증가 직후 batch다. 44%는 두 버전이 서로 다른 producer에서 왔지만(replica 2대), producer가 하나인 `R1`에서도 위반이 같은 정도로 나오므로(14/108) replica 겹침은 필요하지 않다. 한 batch 안에서 eventSeq가 오름차순이 아닌 경우가 batch 260,925개 중 10개 있었고 원인은 확인하지 못했다(위반 분류에는 쓰지 않았다). **정정([EXP-100](EXP-100-kafka-first-delivery-fix-real-stack.md))**: 보관 원자료 전체를 다시 세면 이웃 레코드의 `eventSeq` 감소가 10개인 것은 재현되지만(모두 한 라운드) 분모 260,925는 재현되지 않았다(레코드 2,788,082개, batch 468,193개). 10건은 앞 시도의 미취소 레코드와 다음 시도의 머리가 한 batch에 담긴 실제 현상이다(감사 오류 아님). 이 메커니즘은 로그와 덤프에서 확인한 사실과 추정이 섞여 있다: 사실 = 시도 안에 v1·v2가 있고 실패한 시도, epoch 증가 뒤 batch가 먼저 기록됨, 수정(batch 하나로 제한)으로 위반 0. 추정 = "batch마다 시한이 따로 흘러 앞 batch만 만료되는" 시간 순서의 세부(스모크 한 시행의 로그에서 읽었고 모든 위반에서 확인하지 않았다).

### 4. 수정 (F3, 이 PR)

`KafkaReservationEventPublisher.publish`가 묶음을 64KB 이하의 덩어리로 나눠 덩어리마다 `flush`하고 모든 ack(또는 실패)를 받은 뒤 다음 덩어리를 보낸다. producer `batch.size`는 덩어리의 두 배(128KB), linger는 1초(덩어리는 flush가 즉시 내보냄)로 해 덩어리 하나가 파티션마다 batch 하나에 담기게 했다. 한 파티션에 batch가 하나만 걸려 있으면 그 batch는 기록되거나 폐기되는 둘뿐이라 "뒤만 기록되는" 경우가 없다. 전송 한도(`send-timeout`)는 묶음 전체의 한도에서 덩어리 한 개의 한도로 바뀌어 최악 소요가 2배가 되므로 `ReservationEventWorker`의 lease 검사를 `send-timeout`×2+5초로 올렸다(기본 PT30S ≥ 25초라 통과, 운영 설정은 바뀌지 않음).

### 5. 조사한 층과 멈춘 이유

앱(relay 시도 기록) → producer debug 로그(epoch, sequence, batch 재정렬) → broker 세그먼트 덤프(batch 순서, producerId, epoch, baseSequence) 까지 갔다. tcpdump, thread dump, GC, cgroup은 가지 않았다: 덤프가 순서 역행이 broker에 기록되는 시점에 이미 생김을 보였고(broker가 요청 순서대로 기록한 결과), 수정이 그 층(producer batch 수)에서 위반을 없앴기 때문이다.

### 9. 소비자 그룹 리밸런스 (두 번째 질문)

테스트 전용 참조 소비자(`ReservationEventReferenceConsumer`, [EXP-082](EXP-082-event-consumer-contract.md))를 확장했다: 상태를 더 높은 `aggregateVersion`으로만 올리고(`reservation_event_state`, 조건부 UPSERT), 이미 지난 낮은 버전은 부수 효과를 내지 않고 넘긴다. 새 통합 시험 `rebalanceWithACrashedInstanceAndInvertedFirstDeliveryKeepsStateMonotonicAndEffectsOnce`: 합성 토픽(파티션 3, workflow 30개: 홀수 번째는 v2를 v1보다 먼저 싣고, 앞 10개는 통째로 한 번 더 실음), 같은 group의 소비자 A가 먼저 일부를 적용(commit 없음), B 합류로 파티션이 나뉜 뒤 A가 그룹에서 나가지 않은 채 죽음(세션 6초), B가 모든 파티션을 이어받아 끝까지 읽음. 단언: 모든 workflow의 최종 상태가 v2, 효과 행이 `(workflowId, version)`마다 정확히 하나(낮은 버전이 높은 버전 뒤에 도착한 경우는 효과 없음), 건너뛴 stale 전달 수가 역행 workflow 수와 같음, commit이 토픽 끝까지 감.

## 삭제한 파일의 내용

이 실험의 원자료(시행별 토픽 판독 TSV, producer DEBUG 로그, 세그먼트 덤프 약 8~9MB/라운드)와 재현기 구동 스크립트·분석 스크립트는 저장소에 올리지 않았다(`/tmp`와 홈 디렉터리 작업 영역에만 있다). 증거가 되는 집계값은 위 표에 있고, 재현은 `load-tests/kafka-outage/RelayOrderRepro.java`(단일 파일) 머리말의 명령으로 한다. 사용한 분석: 시행·장애 단계별로 `outage_audit.delivery_order`와 같은 규칙(키별 첫 전달 버전이 엄격히 증가하는가)을 적용, 세그먼트 덤프의 batch 헤더(`baseOffset`, `baseSequence`, `producerId`, `producerEpoch`)를 offset으로 토픽 판독과 결합해 분류.
시험 환경 값: broker `apache/kafka:3.9.1` KRaft 단일 노드(토픽 3 파티션·복제 1), client kafka-clients 4.2.2, producer 설정은 운영과 같음(acks=all, idempotence, delivery.timeout 10초, request.timeout 5초, linger 5ms; `fix`는 batch.size 128KB, linger 1초), 부하 초당 20 workflow(v1, 1초 뒤 v2), 단계당 부하 50초, 부하 10초 뒤 broker `docker pause` 20초, 단계 사이 10초 간격, 라운드마다 broker를 새로 띄움, poll 위상은 시행마다 균등 분산, 컨테이너는 라벨 `atlasexp=h1`로만 만들고 끝나고 0개임을 확인했다.

## 이 결과가 증명하는 것과 아닌 것

- 증명한 것: 이 스택에서 broker pause 뒤 relay 묶음 하나가 한 파티션에 producer batch 여럿으로 걸린 상태에서 실패하면, 높은 버전이 낮은 버전보다 먼저 첫 전달되는 일이 약 6~8%의 시행-단계(한 단계 안에서 workflow의 약 1~2%)에서 일어나고, 묶음을 batch 하나 크기의 덩어리로 나눠 하나씩 끝내면 운영 클래스 144 시행-단계에서 0이었다(95% 상한 2.1%).
- 증명하지 못한 것:
  - 위반이 생기는 시간 순서의 세부(batch마다 시한이 따로 흐른다는 부분)는 한 시행의 producer 로그에서 읽었고 모든 위반에서 확인하지 않았다. 한 batch 안에서 순서가 어긋난 10개(260,925개 중)는 설명하지 못했다.
  - 이슈의 "새 스택 첫 실행에서만"은 재현되지 않았다(HD 판정 참고). 원래 3건이 왜 모두 첫 실행이었는지는 우연으로 보이나 확정하지 못했다.
  - (정정: [EXP-100](EXP-100-kafka-first-delivery-fix-real-stack.md)이 실제 스택에서 AFTER 0/35, BEFORE 2/35를 측정했다.) 실제 DB·앱 두 대·lease를 쓰는 `run-kafka-outage.sh`로 `fix`를 반복하지 않았다(재현기가 DB를 메모리 로그로 대체). `fix`가 실제 앱에서 같은 효과를 낸다는 것은 같은 클래스를 쓴 재현기 결과로만 지지된다.
  - relay 처리량의 한계, 장기 중단, broker 여러 대, `min.insync.replicas`는 보지 않았다. 처리량은 측정하지 않았다(성공한 시도 소요 중앙값 20 대 16ms, 95퍼센타일 485 대 224ms는 장애 근처 시도에서 본 맥락 값이다).
  - 시행 간 독립성: 시행은 같은 broker와 같은 pause 시각을 공유하므로 효과적 독립 단위는 시행-단계보다 적다(라운드 단위로 보면 운영 `base` 4 라운드, `fix` 4 라운드). p 값은 시행-단계를 독립으로 본 것이다.
  - 소비자 리밸런스는 파티션 3개·소비자 2개·1회 crash다. 세션 만료 시간이 짧은(6초) 설정에서만 보았다.
