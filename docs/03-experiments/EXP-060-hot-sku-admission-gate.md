# EXP-060: 재고보다 훨씬 많은 주문이 한 SKU에 몰릴 때 PostgreSQL만으로 버티는가

- 질문: 재고 100인 SKU 하나에 초당 100~2,000건이 몰리면, 거절될 주문이 order DB에 남기는 비용 때문에 처리량이 무너지는가? 무너진다면 어느 지점인가?
- 상태: 탐색 실험(도착률당 기준선 1~3회, gate 1~2회, 단일 호스트). 운영 SLO나 용량 보증이 아니다.
- 날짜: 2026-11-23(결과 파일 시각 02:52~03:39와 06:54~07:13)
- 관련: [ADR-0066](../02-decisions/adr/ADR-0066-redis-admission-gate.md), [EXP-053](EXP-053-inventory-location-failure-load.md), [ADR-0053](../02-decisions/adr/ADR-0053-shared-infra-adoption-gates.md)(도입 조건)

> 해석 주의(2026-11-23, ADR-0068): 기준선과 gate는 서로 다른 시각에 돌린 실행이고, 도착률당 기준선은 1~3회, gate는 1~2회다. 기준선의 반복 변동만으로도 1,000/s에서 383.0~525.0(최대/최소 1.37배), 2,000/s에서 456.0~1,041.9(2.28배)라 퍼센트 개선과 절대 처리량은 근거로 쓰지 않는다. 방어 가능한 결론은 "거절 주문이 durable 쓰기를 만든다"와 "그 쓰기를 없애면 포화 지점이 크게 밀린다"는 자릿수 수준이다. 같은 세션 짝 반복 비교와 gate 변형(Redis·precheck) 비교는 [EXP-062](EXP-062-admission-gate-paired-comparison.md)와 [EXP-063](EXP-063-redis-gate-failopen-and-paired-rerun.md)에서 했다.

## 환경과 입력

- 격리된 새 Compose 프로젝트(측정 때마다 생성·삭제). 컨테이너 CPU/메모리 한도: application 3 CPU/2 GiB(Hikari 최대 10), order PostgreSQL 2 CPU/2 GiB, inventory-location 1 CPU/1 GiB(Hikari 20)와 전용 PostgreSQL 1 CPU/1 GiB, k6 1 CPU/1 GiB, Redis 7.4 1 CPU/512 MiB(영속화 끔, gate를 켠 실행에만 기동), order-mailpit 0.25 CPU. JDK 25, PostgreSQL 18.6. 모든 구성요소가 한 호스트에 있다. Docker VM의 vCPU는 이 실험에서 따로 기록하지 않았고, 같은 날 같은 머신에서 돌린 [EXP-062](EXP-062-admission-gate-paired-comparison.md)는 8 vCPU였다. 한도 합은 Redis를 뺀 구성에서 8.25, Redis를 포함하면 9.25 CPU다.
- 입력: 위치 1개, 재고 100인 SKU, 주문 1건=SKU 1줄. 워밍업 100/s × 10초 뒤 도착률 100/300/500/1,000/2,000 주문/초를 20초 동안 건다(constant-arrival-rate, k6 VU 300~3,000). 같은 입력으로 gate를 끈 기준선과 켠 실행을 비교했다. 기준선은 run1·run2·base3, 2,000/s는 run1·base3·run3-2000이다. run3-2000은 gate 설정을 기록하지 않았지만 주문당 DB tx가 기준선과 같아(5.78) 기준선으로 분류했다. gate는 Redis(gate1·gate2)와 precheck(precheck1·precheck2), 같은 날 스윕의 Redis(redis3)다.
- 지표 정의: `dropped`는 도착률×20초(예: 1,000/s는 20,000건) 가운데 VU가 모자라 시작하지 못한 반복 수다. `completed/s`는 완료한 반복 수를 k6 전체 실행 시간(종료 대기 포함)으로 나눈 값이다. 주문당 DB tx는 order DB의 트랜잭션 증가량에서 유휴 시간분을 뺀 뒤 주문 수로 나눈 값이다.
- 기준선은 [ADR-0046](../02-decisions/adr/ADR-0046-order-payment-transactional-outbox.md)의 원칙(원격 호출을 DB 트랜잭션 밖에서 실행)을 그대로 따르는 현재 구현이다.
- 재현: `load-tests/run-hot-sku-coordinator.sh`(gate는 `GATE=redis` 또는 `GATE=precheck`). 결과 원본은 `.local/hot-sku-coordinator/`에 있고 git에서 제외되어 저장소만으로는 재현·검증할 수 없다.

- 기준선에서 거절된 주문은 모두 `order_inventory_reservation_workflow` 행을 1개(FAILED) 남기고 주문당 약 5.6~5.9개의 DB 트랜잭션을 썼다. Redis gate를 켜면 거절 주문은 workflow 행도 location 호출도 만들지 않아 workflow 행 증가는 승인된 100건에 머물렀다. precheck는 음성 캐시가 차기 전에 지나간 요청이 durable 경로로 내려가 추가 행이 생긴다([EXP-063](EXP-063-redis-gate-failopen-and-paired-rerun.md): 26~33행).
- 기준선은 500/s까지 3회 모두 드롭 0이었고(전체 요청 p50 4.8~28.9 ms) 1,000/s부터 completed/s가 383.0~525.0으로 포화됐다(p50 2.4~3.8 s). 2,000/s는 456.0~1,041.9로 run 사이에 2.28배 차이가 나고 p50은 2.3~5.4 s였다.
- 1,000/s 이상에서 gate를 켠 실행은 모두 기준선 실행보다 높았다. 1,000/s는 gate 5회(981.5~992.2) 대 기준선 3회(383.0~525.0), 2,000/s는 gate 5회(1,303.2~1,959.2) 대 기준선 3회(456.0~1,041.9)다. 2,000/s에서 gate 5회 중 4회는 1,907.4~1,959.2였고, precheck1의 1,303.2는 같은 스윕의 precheck2(1,907.4)와 1.46배 차이라 이 구성의 run 사이 변동이 크다.
- 불변식: 모든 실행에서 승인(RESERVED)은 100을 넘지 않았고 location 용량 보존(available+reserved+claimed=initial)이 유지됐다. RESERVED가 100 미만인 실행은 gate1 300/s(98)와 Hikari 40 진단의 2,000/s(83)이며 둘 다 오버셀이 아니다.
- gate1의 300/s는 이상치다(드롭 203, p95 1,568.8 ms). 원인은 조사하지 못했고, 같은 스택의 워밍업에서도 fail_open 10건이 있었다. gate2의 300/s는 정상이었다.
- 진단(gate 끔, Hikari 최대 풀 10에서 40으로 변경, 03:05, 도착률당 n=1): 500/s 499.4(드롭 0), 1,000/s 247.8(dropped 10,865), 2,000/s 79.5(dropped 37,227, RESERVED 83). 풀을 키웠는데 기준선보다 낮아졌다. 원인은 조사하지 않았다. 기준선 범위에는 넣지 않았다.

## 실패 주입: Redis 중지(1,000/s)

- 입력: 재고 100인 SKU, 도착률 1,000/s × 20초(offered 20,000건), k6 실행 시작 후 8.03~8.04초(3회 모두)에 Redis 컨테이너를 중지했다(`REDIS_KILL_AFTER=8`). 다른 조건은 위와 같다. 03:30~03:39에 실행했다.
- "중지 후 완료 속도"는 k6 누적 완료 곡선(약 1초 간격)에서 중지 약 2초 뒤부터 실행 종료까지의 기울기다.

| 구성 | n | 실행 시간(s) | completed/s | dropped | FAILED workflow 행 | 중지 후 완료 속도(/s) | 오버셀 |
| --- | ---: | --- | --- | --- | --- | --- | --- |
| breaker 없음 | 1 | 35.8 | 355 | 7,299 | 5,294 | 189 | 없음 |
| breaker 적용(down2 / down3) | 2 | 23.0 / 22.7 | 707 / 730 | 3,774 / 3,472 | 8,562 / 8,861 | 595 / 626 | 없음 |

- breaker 없이는 중지 후 완료 속도가 189/s였다. 기준선의 completed/s(383.0~525.0)는 전체 실행 시간 기준이라 산출 방식이 달라 대략적인 비교에만 쓰며, 그 범위보다 낮다. 요청마다 죽은 Redis의 command timeout(200ms)을 기다리는 것이 원인이라는 해석은 **추정**이다(계측으로 분리하지 않았다). breaker(기본 cool-down 2초) 뒤에는 595~626/s로 올라갔지만 gate가 정상일 때의 991.3~992.2/s에는 못 미쳤다.
- 즉 Redis 장애 시 안전성(오버셀 없음, 201·409 외 응답 0건)은 유지되지만 처리량은 gate가 정상일 때로 돌아가지 않는다. 복구 후 breaker가 닫히는 동작은 측정하지 못했다. breaker 없음은 n=1, 적용은 n=2라 두 구성의 차이는 크기가 아니라 방향만 본다.

## 이 결과가 증명하는 것과 아닌 것

- 증명한 것: 이 구성(위 CPU 한도, 재고 100, 20초 측정)에서 gate 없는 PostgreSQL 경로는 약 1,000 주문/초부터 처리량이 포화됐다(n=3, 383.0~525.0). 포화 원인 후보 중 하나는 거절 주문마다 남는 durable 쓰기다. 거절이 쓰기를 만들지 않게 하자 같은 입력에서 포화 지점이 2,000/s 부근까지 밀렸다(2,000/s gate 5회 중 4회가 1,907.4~1,959.2/s). 단, 같은 호스트의 CPU 한도 안에서의 결과다.
- 증명하지 못한 것: 도착률당 기준선 3회, gate 1~2회라 신뢰구간이 없다. Redis가 app과 같은 호스트에 있어 네트워크 지연과 CPU 경쟁이 실제 배포와 다르다. 2,000/s 초과의 포화점, k6 생성기 한계와 앱 한계의 구분, Redis 재시작 후 복구는 측정하지 않았다. gate가 없는 쪽을 개선하는 대안(거절 주문의 쓰기를 줄이는 PostgreSQL 내부 최적화)은 비교하지 못했다. Hikari 풀을 키운 진단 1회가 오히려 낮았다는 점도 원인을 모른다.
