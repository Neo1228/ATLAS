# EXP-115: 실 데이터 규모에서 판매자 락 안 환불·정산서·성장 표 질의가 이력에 비례하는 곳을 측정으로 고친다

- 상태: ✓ 완료(PostgreSQL 18.6, 단일 호스트, 합성 원장 항목 970만 행). 가설·반증 조건·쓰기 예산·판정 규칙은 첫 시간 측정 전에 커밋했다(이 브랜치의 첫 커밋 `docs(experiments): EXP-115 가설과 반증 조건·쓰기 예산을 측정 전에 등록한다`, 16:08, 첫 시간 측정 16:13). 결과: Ac(기간 조건 + 배분 날짜)와 Ae(쓰기 경로 밖 잔액 마감 + 꼬리)를 V10으로 채택, A1·Aa·Ab·Ad·Ad16은 쓰기 예산 탈락으로 기각. 리뷰 뒤 마감 경계를 xid 스냅숏으로 바꾸고(추가 사전 등록 H10·H11) 새 데이터셋에서 다시 쟀다.
- 날짜: 2026-11-27
- 관련: [#723](https://github.com/Neo1228/ATLAS/issues/723), [EXP-114](EXP-114-seller-statement-projection-and-transition-signals.md), [EXP-080](EXP-080-seller-statement-index.md), [EXP-112](EXP-112-queue-wakeup-lock-crossdb-alternatives.md), [EXP-113](EXP-113-account-notification-delivery-and-audit-stream.md), [ADR-0103](../02-decisions/adr/ADR-0103-eda-read-projection-deferred-event-contract-and-signals.md)

## 문제 한 문장

판매자 advisory 락 안의 환불 분개와 지급 예약, 그리고 판매자 정산서는 판매자 원장 이력 전체(보류·지급 가능 잔액 합산, 30일 합계의 수수료·보류 갈래, checkout 배분 갈래)를 읽어 판매자 항목 39.2만 건에서 환불 분개 p50 191 ms, 392만 건에서 999 ms, 정산서 p50 579/945 ms였고(EXP-114 A0), 유일하게 잰 수정안(A1 덮는 인덱스)은 capture 쓰기 p50 +27%, 처리량 -31%로 쓰기 예산을 넘었다.

재현: EXP-114 합성 원장(아래 데이터)을 같은 생성기로 다시 만들고 `pgbench`로 환불 분개(판매자 락 + 보류 잔액 합산 + 분개 1 + 항목 3)와 정산서 1회(REPEATABLE READ, 질의 5개)를 돌린다.

## 측정 전 설계 탐색 (계획만, 시간 값은 판정에 쓰지 않음)

이 커밋 전에 새로 적재한 데이터에서 `EXPLAIN (ANALYZE, BUFFERS)`를 두 번 돌려(두 번째 값) 대안을 설계했다. 버퍼 수만 근거로 쓰고 시간은 쓰지 않는다.

| 질의(30일, 기존 인덱스) | 100k 판매자 버퍼 | 1m 판매자 버퍼 | 이력 비례 원인 |
|---|---|---|---|
| 정산서 합계, 현행 | 161,276 | 171,977(`read` 18,911 포함) | 수수료·보류 갈래가 판매자 항목 전체를 읽고 분개 날짜로 거름(EXP-114) |
| 정산서 합계, 수수료·보류 갈래를 분개 쪽에서 찾게 바꿈(아래 (c)) | 103,057 | 237,154 | 남은 큰 몫: checkout 배분 갈래(100k: 판매자 배분 18,000건 전부를 분개 PK로 조회해 날짜로 거름, 72,002 버퍼), 1m: 기간 항목 41,099 분개 × 고유 인덱스 조회(206,978 버퍼) |
| 행 첫 페이지(21행) | 74,834 | 20,743 | 100k: 같은 checkout 배분 갈래(판매자 배분 전체 조회). 1m: 배분 표 전체 병렬 순차 스캔 |

발견: 결과 21행인 행 첫 페이지가 100k 판매자에서 74,834 버퍼를 읽는다. checkout 배분(`settlement_seller_allocation`)에는 날짜가 없고 인덱스가 `(seller_id, journal_id)`뿐이라 기간 조건을 분개 조인 뒤에만 걸 수 있어서다. EXP-080·114는 이 갈래를 재지 않았다. 그래서 기간 조건 수정 (c)에 배분 날짜 X1을 더한다(아래).

## 데이터

EXP-114 생성기 그대로(EXP-114 "삭제한 파일의 내용"의 SQL): 목표 판매자 4명(분개 1천/1만/10만/100만 건, 항목 3,920 / 39,200 / 392,000 / 3,920,000), 배경 판매자 5,000명(Zipf s = 1.1, 분개 합 100만 건), 최근 730일 균등, `recorded_at` 순서로 삽입, 종류 비율 capture 75 / checkout 18 / refund 6 / payout 1%. 적재 결과: 분개 2,111,042, 항목 9,704,275(2,056 MB), 배분 707,951. 생성기 검사: 불균형 분개 0, 항목 없는 분개 0. 마이그레이션 V1~V9. 근거: EXP-114와 수치를 바로 비교하려고 같은 분포를 쓴다. 판매자 항목 39.2만 건(100k)을 현실 상한, 392만 건(1m)을 스트레스로 본다.

실험 DB에서만: checkout 칸이 쓰는 외래 키 3개(`settlement_journal.checkout_id`, 배분의 `order_id`·`seller_id`)를 모든 암에서 똑같이 뗀다(생성기가 대상 표를 만들지 않음).

## 대안 (암)

| 암 | `settlement_entry` 판매자 인덱스 | 질의 | 쓰기 경로 변화 |
|---|---|---|---|
| A0 | `(seller_id, account_code, entry_side)` (68 MB, B-tree 중복 제거) | 현행 | 없음 |
| A1 | `(seller_id, account_code, recorded_at) INCLUDE (entry_side, amount_won)`로 교체 | 수수료·보류를 항목 `recorded_at`으로(EXP-114 A1 그대로) | 큰 인덱스, 중복 제거 없음 |
| Ac | A0 그대로 | (c) 수수료·보류 갈래를 판매자의 기간 분개(분개·배분 인덱스)에서 `journal_id`로 찾음 + X1 | X1만 |
| Aa | `(seller_id, account_code, entry_side, amount_won)`로 교체(INCLUDE 없음, 같은 키는 중복 제거) | (c) + X1 + 잔액을 계정별 합산 3개로 | 인덱스 교체 |
| Ab | 계정별 부분 인덱스 3개 `(seller_id, entry_side, amount_won) WHERE account_code = 'SELLER_PAYABLE' / 'SELLER_RESERVE' / 'PLATFORM_FEE'`로 교체 | (c) + X1 + 계정별 합산 | PSP_CLEARING 항목은 판매자 인덱스에 안 들어감 |
| Ad | 판매자 인덱스 없음(잔액 행이 대신함) | (c) + X1 + 잔액·보류를 `settlement_seller_balance` 한 행에서 읽음 | 항목 INSERT 문장마다 문장 단위 트리거가 판매자별 증분을 `seller_id` 순서로 UPSERT 1회 |
| Ad16 | 없음 | Ad와 같고 판매자당 16칸(`hashtext(journal_id) & 15`)에 나눠 쓰고 읽을 때 합산 | 같은 판매자 동시 쓰기의 행 경합을 16칸으로 나눔 |
| Ae | 시간 경계(월 마감 스냅숏 + 꼬리) 또는 `settlement_entry` 기간 분할 | 조건부: Aa·Ab·Ad·Ad16이 모두 쓰기 예산에서 탈락할 때만 설계·측정. 하나라도 통과하면 범위 밖 결정으로 닫는다(분할은 PK·고유 인덱스에 분할 키를 넣어야 해 "분개·계정·판매자당 항목 1개" 고유 보장이 분할마다로 약해지고, V7 트리거를 분할마다 다시 걸어야 한다) | — |

X1(Ac·Aa·Ab·Ad·Ad16 공통): `settlement_seller_allocation.recorded_at`을 더하고 BEFORE INSERT 트리거가 그 분개의 `recorded_at`으로 채운다(앱이 넘기지 않아도 같음이 DB에서 보장됨). 배분 인덱스 `(seller_id, journal_id)`를 `(seller_id, recorded_at, journal_id)`로 바꾸고 checkout 갈래의 기간 조건을 배분 날짜에 건다. 쓰기 비용은 checkout 경로(배분 삽입)에만 생긴다.

Ad의 잠금 순서: capture는 판매자 1명, 환불·지급은 판매자 advisory 락 뒤 그 판매자 행 1개, checkout은 한 문장에 넣은 모든 판매자 항목을 트리거가 `ORDER BY seller_id`로 UPSERT한다. 잔액 행을 잡은 채 advisory 락을 기다리는 경로가 없으므로 순환이 생기지 않는다는 것이 코드 읽기 예측이다. 음성 대조(Adrow): 항목 행마다 삽입 순서대로 UPSERT하는 행 단위 트리거(EXP-114 A2와 같은 순서 문제).

## 측정 방법

공통: PostgreSQL 18.6 일회용 컨테이너(라벨 `atlasexp=scale`, `shared_buffers=2GB`, `max_wal_size=8GB`, `checkpoint_timeout=30min`, 메모리 6 GB), 시간 측정 중 `--cpus 4`. 시간 값은 `measure-lock.sh acquire scale 40`을 쥔 구간에서만 잰다. run마다 load1(전/후)과 다른 라벨 컨테이너를 적고 load1 > 12이거나 다른 라벨 스택이 있으면 오염으로 표시해 머리 수치에서 뺀다(라벨 없는 다른 프로젝트 컨테이너는 공변량으로 기록).

칸(암마다, 라운드마다 1회):

| 칸 | 내용 | c | 초 |
|---|---|---|---|
| R100k, R1m | 환불 분개: `pg_advisory_xact_lock` + 보류 잔액 + 분개 1 + 항목 3 | 1 | 8 |
| S100k, S1m | 정산서 1회(30일, REPEATABLE READ READ ONLY, 합계 + 잔액 + 행 21개 + 지급 합계 2개) | 1 | 6 |
| W1 | capture(분개 1 + 항목 4를 한 문장), 배경 판매자 무작위 | 1 | 10 |
| W8 | 같음 | 8 | 10 |
| W8s | capture, 1m 판매자 고정(같은 판매자 동시 쓰기) | 8 | 10 |
| K8 | 판매자 2명 checkout(배경 판매자 20명 중 2명, 항목 8개를 한 문장에 무작위 판매자 순서로 + 배분 2행) | 8 | 10 |

- 쓰기 칸 전에 `CHECKPOINT`(모든 암이 같은 전체 페이지 쓰기 조건에서 시작), 뒤에 적재 시각 이후 행 삭제 + `VACUUM`(원장 크기 고정). Ad·Ad16은 쓰기 칸 뒤 잔액 행 = 원장 합산을 판매자 전체에서 비교(불일치 수)한 뒤 기준 잔액으로 되돌린다.
- 지표: tps, p50·p95·p99(트랜잭션 로그), WAL 바이트/트랜잭션(`pg_current_wal_lsn` 차), 실패(교착) 수, 인덱스 크기(`pg_relation_size`).
- Ac는 A0와 문장·인덱스가 다른 칸(S100k, S1m, K8)만 잰다(환불·capture 문장과 항목 인덱스가 A0와 같다). 음성 대조 Adrow는 K8만 5 run(라운드 밖, 같은 잠금 구간).
- 라운드 5회, 라운드 안에서 모든 암을 연달아(홀수 라운드 A0 → Ac → Ab → Aa → A1 → Ad → Ad16, 짝수 라운드 역순). 같은 라운드 안의 A0 대비 비를 라운드마다 구하고 5개 비의 중앙값으로 판정한다.
- 결과 정확성(시간 측정 밖): 암마다 판매자 7명(목표 4 + 배경 3) × 기간 3개(최근 30일, 전체, 400~370일 전)의 합계·행 페이지와 잔액·보류 출력이 A0와 글자 그대로 같은지.
- 병렬 질의(H8): 1m 판매자 정산서 독자 c = 4(14초)를 돌리는 2초 뒤 capture c = 4(10초). 독자 스크립트만 `SET LOCAL max_parallel_workers_per_gather = 0` 유무로 바꿔 5쌍. A0 상태와 채택 암 상태에서 각각. 독자 없이 정산서만(S100k, S1m) 같은 두 설정으로 5쌍.
- 성장 표 전수 조사(H9): 주문·주문 항목·결제·환불·배송·웹훅·이벤트 로그·outbox·감사 로그·장바구니·재고 예약 질의를 코드에서 모두 목록으로 만들고, 별도 컨테이너(`atlasexp=sweep`)의 큰 데이터(크기·분포·근거를 표로)에서 `EXPLAIN (ANALYZE, BUFFERS)`를 이력 크기 두 지점에서 잰다.

## 쓰기 예산 (사전 등록, H4와 같은 꼴)

암 X가 칸 W1·W8·W8s·K8 각각에서: 라운드별 (X p50 / A0 p50)의 중앙값 ≤ 1.10 그리고 (X tps / A0 tps)의 중앙값 ≥ 0.90. p99는 보고하되 판정에 쓰지 않는다. K8 교착 실패 0건. 결과 정확성 A0와 같음(모든 칸).

## 가설과 반증 조건

| ID | 가설 | 반증 조건(수치) |
|---|---|---|
| H1 | (c) + X1은 판매자 1m의 30일 합계와 행 페이지 버퍼를 합쳐 A0의 1/3 이하로 줄이고 모든 칸의 결과가 A0와 같다 | 버퍼 감소가 1/2보다 작거나 결과 불일치 1건 이상 |
| H2 | X1(Ac)은 K8 쓰기 예산을 통과한다(배분 인덱스에 8바이트 + 트리거 PK 조회 1회) | K8 p50 비 > 1.10 또는 tps 비 < 0.90 |
| H3 | Aa(INCLUDE 없는 키 인덱스)는 금액이 다양해 중복 제거가 거의 안 되므로 크기가 A1의 50% 이상이고 W1 예산을 넘는다 | 크기가 A1의 25% 이하이거나 W1·W8·W8s·K8 예산을 모두 통과 |
| H4 | Ab(계정별 부분 인덱스 3개)는 W1 예산을 넘는다(중복 제거되던 4개 대신 중복 제거 안 되는 3개) | 네 칸 예산을 모두 통과 |
| H5 | Ad는 R1m p50을 5 ms 이하로(이력 무관) 만들고 W1·W8·K8 예산을 통과하지만(판매자 인덱스 제거가 UPSERT 비용을 상쇄) W8s 처리량을 10% 넘게 줄인다(같은 판매자 행 경합) | W1·W8·K8 중 하나라도 탈락, 또는 W8s 처리량 감소 ≤ 10% |
| H6 | Ad16은 W8s 처리량 감소를 10% 이하로 줄이고 나머지 예산도 통과한다 | W8s tps 비 < 0.90 |
| H7 | Ad·Ad16의 K8 교착은 0건이고, 음성 대조(Adrow, 행 단위 삽입 순서 UPSERT)는 K8 5 run 합에서 교착 1건 이상을 낸다 | Ad·Ad16 교착 1건 이상, 또는 Adrow 교착 0건(대조가 순서 문제를 재현 못 함) |
| H8 | 정산서 세션에 `SET LOCAL max_parallel_workers_per_gather = 0`을 두면 A0 상태에서 독자 4개와 함께 도는 capture c = 4 처리량이 50% 이상 오른다(EXP-114 hold5와 같은 방향) | 오름 < 20% |
| H9 | 성장 표 질의 중 요청 경로 또는 락 안에서 이력 크기에 비례해 버퍼가 느는 질의가 1개 이상 남아 있다 | 이력 4배에서 버퍼 2배 이상 느는 요청 경로·락 안 질의가 0개 |

## 판정 규칙 (측정 전 고정)

1. (c) + X1: H1이 서고 Ac가 K8 예산을 통과하면(H2) 채택한다. H2가 반증되면 (c)만 채택하고 X1은 빼서 배분 갈래를 재검토 조건으로 남긴다.
2. 잔액 경로(환불·지급 예약·정산서 잔액): Aa, Ab, Ad, Ad16 중 쓰기 예산 4칸과 정확성, K8 교착 0을 모두 통과한 암에서 R1m p95가 가장 낮은 것을 채택한다. R1m p95 차이가 10% 안이면 움직이는 부품이 적은 것(인덱스 < 트리거 + 표)을 고른다. A1은 EXP-114 판정(H4 반증)을 다시 확인하는 기준선으로만 잰다.
3. 아무 암도 통과하지 못하면 잔액 경로는 A0를 유지하고, Ae를 설계·측정하며, 수치와 함께 탈락 이유를 적는다.

### 시험과 변이 확인

새 시험 `SellerLedgerBoundedReadIntegrationTest` 8건: 배분 날짜 트리거(앱이 다른 값을 넘겨도 분개 값), 정산서 `[from, to)` 경계, 정산서 기간 읽기 버퍼가 판매자 이력 400 → 1,600건에서 합계 26 → 27, 행 11 → 12, 흩어진 판매자 checkout 배분 이력 50 → 200건에서 행 14 → 14(아래 M3), 마감 뒤 판매자 잔액 버퍼가 이력 400건 판매자 6, 1,600건 판매자 6, 다른 DB 역할의 미커밋 항목을 마감이 넘지 않음, 첫 쓰기가 항목인 트랜잭션의 시계·xid 틈, 롤백 스크립트. 기존 `SettlementLedgerAuditIntegrationTest` 2건(점검 3개 추가, 주입 3개 추가), `SettlementStatementIntegrationTest` 4건, `SettlementFeeReservePayoutIntegrationTest` 20건(노출 지표 포함), `SettlementLedgerGuardIntegrationTest` 8건이 변경 후 통과했다. 새 시험은 변경 전 코드에서는 V10 열·표가 없어 실행되지 않으므로, 변경 전 동작은 아래 변이(새 스키마 위에 옛 질의)와 M9(마감 경계 코드 3파일을 마감 경계 수정 전 커밋 `1488a60f`의 것으로 되돌림)로 확인했다.

- **다른 역할 시험**(`foldNeverPassesAnUncommittedEntryOfAWriterUnderAnotherRole`): 쓰기는 `ledger_writer_probe`로 로그인한 별도 연결에서 분개·항목을 넣고 커밋하지 않는다. 마감은 앱 연결이지만 트랜잭션 안에서 `SET LOCAL ROLE ledger_fold_probe`(슈퍼유저 아님)로 네 번 돈다. 커서가 그 미커밋 항목 id 이하인지, 커밋 뒤 마감 + 꼬리 = 원장인지 본다. 마감 수정 전 코드(M9)에서 실패한다.
- **첫 쓰기 틈 시험**(`anEntryThatIsItsTransactionsFirstWriteHasItsXidBeforeItsIdClock`): 시험 전용 BEFORE INSERT 트리거가 기본값(id)을 계산한 뒤 heap 삽입 전에 advisory 잠금에서 쓰기를 멈춘다. 그동안 마감이 네 번 돈다. PostgreSQL 18.6에서 BEFORE 트리거 시점의 `pg_current_xact_id_if_assigned()`는 그 트랜잭션의 첫 행에서 NULL이었다(실험 컨테이너에서 확인). 그래서 `uuidv7()` 기본값(M10)이면 xid 없는 쓰기를 마감이 기다리지 않고 넘는다.
- **M3 시험**(`statementRowsDoNotReadTheSellersScatteredCheckoutHistory`): 판매자 checkout 배분 한 건마다 다른 판매자 배분 99건을 같은 문장에서 사이에 넣어 판매자 배분을 페이지마다 흩고(운영 모양), 기간 밖 플랫폼 checkout 5만 건과 기간 안 2만 건을 쌓았다. 몰아 넣은 이력에서는 판매자 배분 전체가 몇 페이지라 M3가 살아남았다(이전 run: 행 362 → 434, 기간 안 플랫폼 2만 건만 쌓았을 때). 흩은 뒤 M3에서 행 365 → 1,822 버퍼(올바른 질의 14 → 14).

## 삭제한 파일의 내용

측정 구동 파일은 저장소에 올리지 않았다. 생성기는 EXP-114 "삭제한 파일의 내용"과 같다(끝에 `CREATE TABLE gen_meta AS SELECT now() AS loaded_at`). 암별 상태(인덱스 DDL)는 대안 표, Ad·Ad16 트리거는 EXP-114 A2와 같은 누적 UPSERT를 문장 단위 트리거(`REFERENCING NEW TABLE`, `GROUP BY seller_id ORDER BY seller_id`)로 바꾼 것, Ad16은 `(seller_id, hashtext(journal_id) & 15)` 키, Adrow는 행 단위 트리거다. Ae 실험판은 위 결정의 질의를 plpgsql 함수(`EXECUTE format(... %L, 커서)`)로 감싼 것이다. 칸 하나: `pgbench -n -M prepared -c <c> -j <c> -T <초> --failures-detailed --log`, 쓰기 칸 전 `CHECKPOINT`, 뒤 적재 시각 이후 행 삭제(복제 역할) + `VACUUM` + 잔액 표 기준값 복원. WAL = `pg_wal_lsn_diff` / 트랜잭션 수.

운영판 마감 재측정(라운드 101~125, 새 데이터셋)에 더한 것: 적재 스크립트는 V10 이후 마이그레이션을 건너뛴다(기준선 = V1~V9). 운영판 마감 `e_fold2(lag interval DEFAULT '1 second')`는 `SettlementBalanceCheckpointServiceImpl.foldOnce`를 plpgsql로 옮긴 것이다: 커서 행 `FOR UPDATE` → `pending_xid IS NOT NULL AND pg_snapshot_xmin(pg_current_snapshot()) <= pending_xid`이면 끝 → 아니면 `[커서, pending_entry_id)`를 판매자별로 마감 행에 더하고 커서 = `pending_entry_id` → `pending_entry_id = (uuidv7((now() - lag) - clock_timestamp())의 밀리초 하한)`, `pending_xid = pg_current_xact_id()`. 실험 커서 표에 `pending_entry_id uuid`, `pending_xid xid8` 열을 더했다. 암 전환 스크립트는 Ae일 때만 `settlement_entry.entry_id` 기본값을 `settlement_entry_next_id()`(V10과 같은 본문)로, 다른 암은 `uuidv7()`로 둔다. 쓰기 칸 뒤 마감은 두 번 부른다(첫 번째는 앞 pending까지, 두 번째는 새 pending까지). 겹침 재현은 hold 스크립트의 잠금 줄을 끈 사본 두 개를 5초 차로 같은 컨테이너에 돌리고 바깥에서 잠금을 한 번 쥔다. 결정적 끼움: Ae 상태에서 K8 칸(`c = 8`, 10초) → 마감 2번 → `cleanup.sql`(적재 시각 이후 분개·항목·배분 삭제, 복제 역할) → 모든 판매자 마감 + 꼬리 = 원장 비교.
