# EXP-055: 같은 재고 행의 동시 차감에서 조건부 UPDATE·비관적 잠금·낙관적 잠금 비교

- 질문: 원래 계획 2단계("로컬 transaction으로 해결할 수 있는 범위 확인")에서 세 동시성 제어 방식이 모두 초과 판매를 막는가? 막는다면 비용 차이는 얼마인가? 재고 서비스가 이미 쓰는 조건부 UPDATE를 유지할 근거가 있는가?
- 상태: 일회성 탐색 실험(방식별 3회 반복, 단일 호스트). harness를 보존하지 않아 재실행할 수 없다.
- 날짜: 실행일은 기록하지 않았다. 원본 표준 출력을 보존하지 않았고 이 문서의 표가 유일한 기록이다.
- 관련: [ADR-0059](../02-decisions/adr/ADR-0059-independent-inventory-location-service.md), [ADR-0060](../02-decisions/adr/ADR-0060-order-inventory-reservation-workflow.md)

## 환경과 입력

- 대상: 재고 행 하나(`available`, `version`)를 1개씩 차감한다.
  - 조건부 UPDATE: `UPDATE … SET available = available - 1 WHERE available >= 1` 한 문장.
  - 비관적 잠금: transaction 안에서 `SELECT … FOR UPDATE` 후 확인·차감.
  - 낙관적 잠금: version을 읽고 `WHERE version = ?`로 차감하고, 실패하면 재시도.
- 입력: 두 시나리오를 방식마다 실행했다. 마지막 1개 시나리오는 재고 1에 100 스레드가 1회씩 경쟁한다. 지속 경쟁 시나리오는 재고 2,000에 32 스레드가 100회씩(총 3,200회) 시도하므로 성공은 최대 2,000건, 실패는 1,200건이다.
- 반복: 방식별로 두 시나리오를 각각 3회 실행했다(n = 3). 3회는 신뢰구간을 계산하기에 부족하다.
- 환경: Apple M3 Pro(11 CPU), Colima Docker의 PostgreSQL 18.6 Testcontainers, JDK 25. 연결 풀 없이 스레드마다 연결 하나를 연다. 실행 harness는 `StockLockStrategyExperimentTest`라는 일회성 탐색 test였고 production 코드가 아니며, 이후 저장소에서 제거했다. 불변식(초과 판매 없음)만 단언했고 시간은 표준 출력으로 기록했다.
- 지표: "성공/실패"는 차감 시도 중 재고를 1 줄인 건수와 재고 부족으로 거절된 건수다. "소요"는 모든 스레드를 동시에 출발시킨 시점부터 32개 스레드가 100회 시도를 모두 마칠 때까지의 경과 시간(ms)이며, 스레드별 연결 생성 시간을 포함한다. "처리율"은 성공 2,000건 ÷ 소요(초)로 다시 계산한 값이다(예: 2,000 ÷ 1.838초 = 1,088/초). "재시도"는 낙관적 잠금에서 version 충돌로 다시 시도한 횟수이며 조건부 UPDATE와 비관적 잠금은 재시도가 없다.

## 결과

| 방식 | 마지막 1개: 성공/실패 | 지속 경쟁: 성공/실패 | 지속 경쟁 소요(3회) | 처리율(성공/초) | 재시도 |
|---|---|---|---|---:|---:|
| 조건부 UPDATE | 1/99 (3회 동일) | 2,000/1,200 | 1,838 · 1,386 · 690 ms | 1,088 · 1,443 · 2,899 | 0 |
| 비관적 잠금(`FOR UPDATE`) | 1/99 | 2,000/1,200 | 7,166 · 12,447 · 8,331 ms | 279 · 161 · 240 | 0 |
| 낙관적 잠금(version) | 1/99 | 2,000/1,200 | 5,310 · 6,109 · 4,283 ms | 377 · 327 · 467 | 27,954 · 27,704 · 28,109 |

- 세 방식 모두 매회 마지막 1개는 정확히 1건만 성공했고, 지속 경쟁에서도 정확히 2,000건만 성공해 최종 재고 0으로 끝났다. 초과 판매는 없었다.
- 지속 경쟁에서 조건부 UPDATE가 3회 모두 가장 빨랐다. 소요는 조건부 UPDATE 690–1,838 ms, 낙관적 잠금 4,283–6,109 ms, 비관적 잠금 7,166–12,447 ms(각 3회의 범위)이고, 처리율은 각각 1,088–2,899/초, 327–467/초, 161–279/초다. 비관적 잠금은 확인과 차감을 한 transaction에서 하며 행 잠금을 왕복 2회 동안 쥔다. 낙관적 잠금은 성공 1건당 약 14회 재시도했다(재시도 27,704–28,109회 ÷ 성공 2,000건 = 13.9–14.1).
- 마지막 1개 시나리오의 소요 시간은 스레드별 연결 생성 시간이 대부분이라 방식 비교에 쓰지 않는다.

## 해석과 판단

- 재고 서비스의 조건부 UPDATE 유지가 타당하다. 같은 정합성을 가장 적은 DB 왕복으로 얻고, 재시도 루프나 transaction 경계가 필요 없다. 이 결론은 "한 행의 수량 비교 후 차감"처럼 조건이 한 문장으로 표현될 때만 성립한다.
- 비관적 잠금은 읽은 값으로 여러 테이블을 갱신하는 등 판단이 한 문장으로 끝나지 않을 때 필요하다. 예약 item 여러 줄이나 tombstone 확인처럼 이런 경우는 이미 reservation 행 `FOR UPDATE`로 직렬화하고 있다.
- 낙관적 잠금은 hot row에서 재시도가 폭증해 부적합하다. 충돌이 드문 데이터에 맞다.

## 한계

- 단일 행·단일 DB의 차감만 비교했다. 여러 location에 걸친 예약은 로컬 transaction으로 묶을 수 없어 [ADR-0060](../02-decisions/adr/ADR-0060-order-inventory-reservation-workflow.md)의 workflow로 다룬다. 이것이 원래 계획 3단계로 넘어간 근거다.
- 조건부 UPDATE의 소요는 반복 순서대로 줄었지만(1,838 → 1,386 → 690 ms) 다른 두 방식은 같은 경향이 없어 warm-up만으로 설명할 수 없다. 반복 사이 편차가 크고(비관적 잠금 7,166–12,447 ms), 3회는 신뢰구간을 계산하기에 부족하며, 공유 호스트라 다른 부하를 배제하지 못했다.
- 연결 풀을 쓰지 않아 실제 애플리케이션의 Hikari 대기, `lock_timeout`, deadlock 재시도는 포함하지 않았다. 재고 서비스의 실제 HTTP 경로 측정은 [EXP-053](EXP-053-inventory-location-failure-load.md)에 있다.

## 재현

- 재현할 수 없다. 실행 harness(`StockLockStrategyExperimentTest`)와 원본 표준 출력을 저장소에 보존하지 않았고, git-ignore된 로컬 디렉터리에도 원본이 남아 있지 않다. 표의 수치는 당시 기록을 옮긴 것이며, 소요·처리율은 같은 조건으로 다시 측정하면 달라질 수 있다.
- 같은 질문을 다시 확인하려면 위 입력(재고 1에 100 스레드 1회씩, 재고 2,000에 32 스레드 × 100회, 방식별 3회, 연결 풀 없이 스레드당 연결 1개)으로 harness를 새로 작성해야 한다. 저장소에는 조건부 UPDATE를 쓰는 재고 서비스의 동시성 회귀로 `InventoryReservationIntegrationTest`(2026-11-23 no-cache 실행 13건 통과)만 남아 있고, 이는 세 방식의 비용 비교가 아니다.
