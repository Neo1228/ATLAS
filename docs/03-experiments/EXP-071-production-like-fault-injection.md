# EXP-071: 운영 형태에 가까운 스택에서 컨테이너 장애를 주입해도 예약 상태는 어긋나지 않는가

- 질문: 부하 분산(nginx), application 2대, 자원 한도, 재시작 정책을 갖춘 스택에서 order DB, location 서버, location DB, application에 장애를 주입하면 응답받은 예약이 사라지거나 주문과 창고의 상태가 어긋나는가? 장애가 클라이언트에 어떤 형태로 드러나는가?
- 상태: 탐색 실험. 시나리오별 n=1(풀 크기 비교만 같은 시나리오를 2회). **하네스는 저장소에 올리지 않았다**(아래 "코드를 올리지 않은 이유").
- 날짜: 2026-11-24
- 관련: [EXP-070](EXP-070-real-stack-fault-injection.md), [EXP-064](EXP-064-location-fault-convergence.md), EXP-066(PR #515), [EXP-050](EXP-050-toxiproxy-postgres-fault-probe.md)

## 왜 했는가

[EXP-070](EXP-070-real-stack-fault-injection.md)은 application JVM 1개, 자원 한도 없음, 장애를 사람이 직접 되돌리는 구성이었다. 운영에 가까운 구성(복제본, 부하 분산, 한도, 재시작 정책)과 표준 장애 주입 도구에서도 같은 불변식이 유지되는지, 그리고 장애가 클라이언트에 어떤 형태로 드러나는지는 확인하지 못했다.

## 도구 선택

| 후보 | 판단 |
| --- | --- |
| EXP-070의 직접 `docker pause/kill`과 `tc` | 시작·종료 시각과 해제를 사람이 맞춘다. 같은 명령으로 다른 사람이 재현하기 어렵다 |
| Chaos Mesh | Kubernetes가 필요하다. 이 저장소에는 Kubernetes 매니페스트가 없고(추적 파일 965개 중 0개) compose 파일 5개만 있다 |
| Toxiproxy([EXP-050](EXP-050-toxiproxy-postgres-fault-probe.md)) | 프록시를 거치는 연결에만 장애를 건다. 프로세스 kill이나 컨테이너 pause를 표현하지 못한다 |
| **Pumba 1.6.0**(선택) | Docker 컨테이너에 `kill`, `pause`, `netem`(지연·손실)을 지정한 시간 동안 걸고 스스로 해제한다. 명령 한 줄로 재현된다 |

Pumba는 `docker kill`과 같은 방식으로 죽이므로 재시작 정책을 타지 않는다(아래 하네스 조건).

## 환경과 방법

- 호스트: Apple 실리콘 Mac, Colima Docker VM(8 vCPU, 12.6GiB, Docker 29.5.2). VM에는 이 프로젝트와 무관한 컨테이너 19개가 있었고 유휴 상태였다(CPU 합 14%/800%). 부하기는 호스트 Mac의 Python이다.
- 구성(Docker Compose, 로컬 전용): nginx → application JVM 2대 → order PostgreSQL 1개, inventory-location JVM 2대(창고 A, B) → 창고별 PostgreSQL 1개, mailpit. compose의 CPU 한도를 합하면 9.75로 VM의 8 vCPU보다 크다. application 1.5 CPU·1280MiB ×2, location 1 CPU·768MiB ×2, order DB 2 CPU·1536MiB, location DB 1 CPU ×2, nginx 0.5 CPU. 한도 적용은 cgroup `cpu.max`(location 100000/100000, application 150000/100000, order DB 200000/100000)로 확인했다.
- 설정: Hikari 풀 10(application당), connection-timeout 500ms, PostgreSQL `max_connections=100`, `synchronous_commit=on`, 재시작 정책 `unless-stopped`, nginx 업스트림 `max_fails=2 fail_timeout=5s`, `proxy_read_timeout` 10초, 요청이 이미 전달된 POST는 다른 서버로 재시도하지 않는다(`non_idempotent` 미지정).
- 부하: 초당 50건. 신규 예약 70%, 취소 20%, 같은 idempotency key 재전송 10%. SKU는 실행마다 새로 만들고 창고당 재고 1,000,000을 둔다. 장애는 시작 15초 뒤 주입한다.
- 장애(Pumba): `kill`, `pause --duration 40s`, `netem --duration 40s delay --time 250 --jitter 100`(order DB), `netem loss --percent 20`(location A). PostgreSQL 내부 크래시는 컨테이너 안에서 checkpointer 프로세스에 SIGKILL을 보낸다.
- 감사: 이 실행이 만든 SKU만 대상으로 order DB의 workflow 상태와 두 location DB의 예약·재고를 `psql`로 직접 센다. 응답으로 확정(`201 RESERVED`)을 받은 요청이 최종 `RESERVED`로 남았는지(`LOST`), 취소 확정 응답을 받은 요청이 실제로 취소됐는지(`NOT_CANCELLED`), 같은 key 재전송의 응답이 원래와 같았는지(`replay_mismatch`), order의 `RESERVED` 수와 location이 쥔 수가 같은지를 본다.
- 지표 정의: "마지막 오류"는 오류 응답을 받은 요청의 **시작 시각**(inject 기준)이다. `kill`·`crash`의 "장애 구간"은 inject 직후 3초(150건), 나머지는 40초(약 2,000건)이다.

## 관찰

1. **`202` 경로는 location 장애를 흡수하지만 회복이 장애보다 오래 간다.** location B `pause` 40초 동안 요청 1999건 중 1852건이 `202`로 접수됐다(실패가 아니라 접수). 그러나 `pause`가 끝난 뒤에도 오류가 21.5초 더 이어졌다(마지막 오류 63.6초, Pumba 종료 42.1초). `kill`에서도 location B가 약 6.9초 뒤 재시작됐는데 장애 이후 구간 2850건 중 1859건이 `202`였고 마지막 오류가 40.3초였다. 원인은 측정하지 않았다. 후보는 location JVM의 기동 시간, 밀린 요청이 한꺼번에 들어오며 생기는 location DB 경합(같은 구간 loc-a-postgres 피크 101%), application의 HTTP 클라이언트와 스레드 적체이며 하나도 검증하지 않았다.
2. **order DB 지연은 `kill`이나 `crash`보다 클라이언트에 훨씬 크게 드러난다.** 250ms 지연에서 장애 구간의 91%(1815/2000)가 `503`이었다. `kill`은 장애 구간 150건 중 55건(`500`+`503`)이 실패하고 3.8초 만에 끝났고, 내부 크래시는 20건 실패에 0.6초였다. 느린 의존성이 죽은 의존성보다 나쁘다. [EXP-070](EXP-070-real-stack-fault-injection.md)의 300ms 조건(`503` 351/360)과 같은 방향이다.
3. **연결 점유 시간으로 설명하는 편이 풀 크기만으로 설명하는 것보다 맞다.** EXP-070은 `503`을 "연결 풀 고갈 후 500ms connection-timeout"으로 가설을 세웠다. 풀을 10에서 30으로 올려 같은 시나리오를 다시 돌렸다(앞서 풀 30으로 한 번 돌린 실행은 Pumba가 주입에 실패해 무효여서 버렸다). 빠른 `503`은 1815건에서 415건으로 줄었지만 성공은 177건에서 367건(9%에서 18%)으로만 늘었고 실패가 느린 `504` 179건과 즉시 반환 `502` 1002건으로 옮겨 갔다. 같은 조건을 다시 돌린 실행(스레드 덤프 포함)은 성공이 28%(359/1275)였으므로 이 비교는 n=1이고 반복 간 폭이 크다.
   - 스레드 덤프(장애 시작 약 20초, 33초 뒤 app1에 SIGQUIT): 요청 스레드 40개 중 **29개가 PostgreSQL 소켓 응답을 기다렸고**(모두 트랜잭션 안, `LocationReservationRepository`의 `claim`·`updateLocation`·`findHeaderByWorkflowId`·`save`), **11개는 풀 연결을 기다렸다.** 두 덤프의 수가 같았다. 29는 풀 크기 30과 거의 같다. 풀이 DB 응답을 기다리는 트랜잭션으로 가득 찬 상태다.
   - 정상 상태에서 예약 요청 1건은 같은 백엔드 연결에서 문장 23~26개를 실행한다(`log_statement`로 6건 측정, BEGIN·COMMIT 8개 포함). 요청이 없어도 스케줄러와 복구 worker가 초당 약 56문장(4초에 223건)을 실행한다.
   - 연결 점유 시간은 대략 왕복 수 × 지연이다. 위 측정은 신규 예약 요청만 쟀고 부하는 신규 70%, 취소 20%, 재전송 10%의 혼합이라 평균 왕복 수는 재지 않았다. 문장당 왕복 수도 재지 않았다. 평균을 16~24회로 **가정**하면 250ms 지연에서 점유 시간이 4~6초다. 처리량 상한은 (application 수 × 풀) ÷ 점유 시간이므로 풀 10은 3.3~5.0건/초, 풀 30은 10~15건/초다. 관측은 풀 10이 (성공 177 + `202` 8) ÷ 40초 ≈ 4.6건/초, 풀 30이 (367 + 37) ÷ 40초 ≈ 10.1건/초로 모두 범위 안이다. **이 계산은 관측 뒤에 맞춘 것이라 독립 검증이 아니다.**
   - 모델이 예측을 걸 수 있는지 보려고 지연을 100ms로 낮춰(풀 30) 같은 모델의 예측 25~37건/초를 시험했다. 관측은 (1320 + 65) ÷ 40초 ≈ 34.6건/초로 범위 안이지만, 지연 p50이 4.77초이므로 폐쇄 루프 부하기(160 worker)의 상한이 160 ÷ 4.77 ≈ 33.5건/초라서 관측이 모델이 아니라 부하기 한계와 겹친다. 이 조건은 모델을 지지하지도 반박하지도 못한다.
4. **느린 DB가 부하 분산기의 업스트림 제외를 일으켜 장애를 증폭했다.** 풀 30 실행에서 `502` 1002건의 지연 p50은 0.007초로 거의 즉시 반환이었다. 같은 시간 창(112초)의 nginx 오류 로그를 세면 `no live upstreams` 1044건이 클라이언트 `502` 1044건(1002+42)과, `upstream timed out` 179건이 `504` 179건과 같았다. 로그의 순서도 이 설명과 맞는다. 첫 `upstream timed out`이 먼저 나왔고 타임아웃 29건이 쌓인 뒤 5초 지나 첫 `no live upstreams`가 나왔다. 따라서 `proxy_read_timeout` 10초를 넘긴 응답이 `max_fails=2` 조건을 채워 두 application을 모두 `fail_timeout` 5초씩 제외했고, 그동안 요청이 nginx에서 곧바로 거부된 것으로 본다(nginx의 제외 규칙에 따른 해석이며 제외 시작·해제 시각을 직접 대조하지는 않았다). 풀 10 실행에는 `502`와 `504`가 없었다(응답이 500ms 안에 `503`으로 돌아와 제외 조건이 쌓이지 않은 것으로 보이며 로그로 확인하지 않았다).
5. **application 1대 장애는 부하 분산이 흡수했다.** `kill`에서 `502`가 2건뿐이었고 마지막 오류는 1.4초였다. 요청이 이미 전달된 POST를 재시도하지 않으므로 전달 직후 끊긴 요청은 실패로 남는다.

## 이 결과가 증명하는 것과 아닌 것

- 증명한 것: 이 스택과 이 조건에서 위 장애 9종(대조군 1회 제외)과 풀·지연 비교 3종 어디에서도 응답받은 예약이 사라지거나 취소 확정이 유실되거나 주문과 창고의 상태가 어긋나지 않았다(풀·지연 비교 실행을 포함한 표의 13개 실행 모두). [EXP-070](EXP-070-real-stack-fault-injection.md)의 결론이 복제본·부하 분산·한도·무작위 혼합 부하(신규·취소·재전송)에서도 같았다.
- 증명하지 못한 것:
  - 시나리오별 n=1이다. 표의 응답 건수와 시각은 실행마다 다르며 오차를 모른다. 같은 조건(풀 30, 250ms)을 두 번 돌렸을 때 성공 비율이 18%와 28%였다.
  - 부하기가 폐쇄 루프다(스레드 160개). 응답이 느리면 실제 요청률이 초당 50건 아래로 떨어진다(스레드 덤프 실행은 장애 구간 요청이 2000건이 아니라 1275건). 장애 구간 건수는 실행 간에 같은 기준이 아니고, 느린 응답이 많은 실행일수록 요청이 덜 들어갔다. control 한 번에서 `503`이 5건 나왔고 기동 직후(JVM 예열 전)였다. 이후 시나리오는 예열된 스택이라 control이 소음 기준으로 완전히 대응하지 않는다. 그래서 "마지막 오류"가 수 초 이내인 시나리오(crash, loc-a-db-crash)는 소음과 구별할 수 없다.
  - 장애 시작·종료 시각이 정확하지 않다. inject 시각은 Pumba 컨테이너를 띄우기 직전이고 종료는 Pumba 종료 시각(`fault_done`)이다. 둘의 간격이 40초보다 2~8초 길었다(`pause` 42.1~43.5초, `netem` 45.2~48.0초). `netem`은 헬퍼 컨테이너를 띄우기 때문일 수 있으나 측정하지 않았다. 따라서 "마지막 오류"가 장애 종료 전이면(order-db-pause40 42.6초, loc-a-loss 46.0초, order-db-delay 47.3초) 해제 뒤 남은 오류를 관측하지 못했다는 뜻이다.
  - CPU 피크는 해석하지 않는다. `loc-a-loss`에서 `docker stats`가 한도(1 CPU)를 넘는 359%와 application 375%(한도 1.5)를 보고했고, cgroup 한도는 적용 중이었으므로 이 값의 산출 방식을 확인하지 못했다.
  - PostgreSQL 크래시는 프로세스 SIGKILL이다. 전원 차단이나 디스크 손상은 다루지 않았다. 별도 단건 확인에서 checkpointer 종료 뒤 로그상 복구 시작에서 접속 수락까지 0.3초였다.
  - [EXP-070](EXP-070-real-stack-fault-injection.md)의 DNS 부정 캐시 10초 지연은 재확인하지도 반증하지도 못했다. EXP-070은 order DB `kill` 뒤 진행 중 workflow가 사라지기까지 21.1초를 쟀고 이 실험은 마지막 클라이언트 오류 시각을 쟀다(inject 3.7초에 재시작, 마지막 오류 3.8초). 같은 JVM의 같은 풀에서 신규 요청 경로는 즉시 회복하는데 백그라운드 경로만 지연된다는 설명은 아직 없다.
  - 네트워크 분리, CPU·메모리 압박, Kafka 중단, 6초·40초보다 긴 장애, 결제 연동은 다루지 않았다.

## 하네스 조건(결과 해석에 필요한 것)

- Docker 29.5.2에서 `docker kill`(Pumba `kill` 포함)로 죽은 컨테이너는 `restart: unless-stopped`가 재시작하지 않았다(`restarts=0`, exit 137). 컨테이너 안에서 PID 1을 SIGKILL하면 재시작됐다(`restarts=2`). 그래서 `kill` 시나리오에서는 감독자 스레드가 3초마다 종료된 컨테이너를 찾아 `start`한다. 이 간격(최대 3초)이 `kill`의 복구 시간에 포함돼 있고, 오케스트레이터가 다르면 달라진다. 감독자 없이 돌린 order DB `kill`은 컨테이너가 계속 죽어 있어 이후 2850건이 모두 `503`이었다(결과에서 제외).
- Pumba `netem`은 헬퍼 이미지를 내려받으므로 첫 실행 전에 같은 명령으로 1회 예열했다.
- 장애 주입이 실패한 실행을 유효한 결과로 읽지 않도록 `fault_done`의 종료 코드가 0이 아니면 `INVALID_RUN`을 출력한다. 풀 30의 첫 실행이 이 경우였다(Pumba exit 78, "refusing to replace a foreign or stale root qdisc"). 이후 짧은 `netem`을 같은 컨테이너에 두 번 걸었을 때는 모두 성공했으므로 "두 번째 주입은 거부된다"는 가설은 기각했고, 거부 원인은 확정하지 못했다. 실행 직전 root qdisc가 기본값(`noqueue`)이고 Pumba 컨테이너가 없음을 확인한 뒤 다시 돌린 결과만 표에 썼다.
- 한도를 합한 CPU가 VM보다 크고(9.75 대 8), 부하기가 같은 호스트에서 돈다. 처리량·지연 절댓값은 일반화할 수 없다.

## 코드를 올리지 않은 이유

compose 파일, nginx 설정, 부하·감사·장애 주입 스크립트는 Docker 소켓과 `docker`·`psql` 명령, Colima VM에 의존하는 로컬 실험용이고 CI에서 안정적으로 돌릴 대상이 아니다. 저장소 밖에 보관하고 이 문서에 구성, 파라미터, 감사 방법을 적었다. **저장소만으로는 재현할 수 없다.**

## 후속 제안(적용하지 않음)

- 관찰 4의 증폭을 줄이는 방안을 비교한다. 후보는 nginx `max_fails=0`으로 수동 제외 끄기, `proxy_read_timeout` 단축, application의 쿼리·트랜잭션 타임아웃, 요청당 문장 수와 트랜잭션 안의 왕복 수 줄이기다. 지연 시나리오를 같은 입력으로 돌려 성공 비율과 `502`·`504` 건수로 비교해야 하고, 어느 것이 효과가 있는지는 아직 모른다. 운영 설정 변경이므로 효과를 측정한 뒤 별도 결정(ADR)이 필요하다.
- 부하기를 개방 루프(요청 시각을 고정)로 바꿔 느린 응답이 요청률을 낮추지 않게 한 뒤 연결 점유 모델을 예측으로 시험한다(지연 100ms, 175ms, 250ms에서 처리량이 점유 시간에 반비례하는지).
- 관찰 1의 회복 지연 원인을 가르는 측정을 추가한다. 후보별로 application의 HTTP 클라이언트 상태, location JVM 기동 시각, location DB 활성 연결 수를 시간축으로 기록한다.
- 같은 시나리오를 3회 이상 반복해 분산을 먼저 본다. 지금은 시나리오 간 차이가 소음보다 큰지 판단할 근거가 control 1회뿐이다.
