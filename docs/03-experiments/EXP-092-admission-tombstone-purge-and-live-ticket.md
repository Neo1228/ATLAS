# EXP-092: admission tombstone 정리와 구매자별 live ticket 1개 규칙의 비용·안전성

**상태:** 로컬 합성 측정 · 운영 부하/SLA 근거 아님 · 시간 값은 맥락으로만 사용 · 가설·반증 조건은 실행 전 commit(`99e77394`)에 등록했고 아래 "사전 등록과 달라진 점"에 어긋난 부분을 적는다

## 문제 (한 문장)

[ADR-0083](../02-decisions/adr/ADR-0083-admission-operational-values-and-lock-failure.md)이 결정만 하고 구현하지 않은 두 가지 때문에, `admission_ticket`은 행당 약 473 B로 정리 없이 늘고(EXP-090) 같은 구매자가 Idempotency-Key만 바꿔 join을 반복하면 ticket과 K slot을 여러 개 잡는다. 피해자: 운영자(표 크기, 무제한 증가), 같은 Seller-SKU의 다른 구매자(한 구매자나 bot이 slot을 독점). 크기는 가정이다: 실제 구매자 분포·트래픽이 없다.

## 가설과 반증 조건

모든 가설은 **개수·buffer 수·불변식**으로 판정한다. 공유 Mac의 시간 값은 맥락이다. 판정은 확정 / 기각 / 판단 불가 셋 중 하나다.

| # | 가설 | 지표와 기대값 | 반증 조건 | 이 결과가 정하는 것 |
|---|---|---|---|---|
| H1 | retention 조건 부분 인덱스가 있으면 정리 문장이 읽는 buffer는 표 크기와 무관하다 | `EXPLAIN (ANALYZE, BUFFERS)` shared hit+read. 후보가 많은 상태(A1)와 정리할 행이 없는 정상 상태(A2), N=100k·1M·5M. 기대: 최대/최소 비율 ≤ 2 | 비율 > 2 | 인덱스를 마이그레이션에 넣을지 |
| H1-음성 | 인덱스가 없으면 A2 정상 상태의 buffer가 표 크기에 비례한다(탐지기가 O(표)를 잡는지 증명) | 인덱스 없음, A2, N=100k 대 1M의 buffer 비율 ≥ 5 | 비율 < 5이면 **하네스가 O(표)를 못 잡는다**: H1의 초록은 무의미 | H1 판정의 유효성 |
| H2 | 주문이 가리켜 영영 못 지우는 오래된 tombstone(P개)이 인덱스 앞쪽에 쌓이면 정리 문장의 읽기가 P에 비례해 늘어난다 | N=1M, 인덱스 있음, anti-join(`NOT EXISTS purchase_order`), P=0·1k·10k·100k. 기대: buffers(P=100k) ≥ 20 × buffers(P=0) | ≤ 5배 | 완화책이 필요한지 |
| H3 | batch 상한이 한 번의 잠금 수·WAL·실행 시간을 batch에 비례하게 묶는다 | N=1M, 인덱스 있음, batch 100·500·5,000. WAL bytes/행의 최대/최소 ≤ 1.5, 실행 시간(5,000)/(500) ≤ 15, 잠긴 행 수 = batch | 어느 하나라도 어긋남 | 기본 batch와 상한 |
| H4 | 정리 인덱스가 만료 UPDATE 경로(WAITING→EXPIRED)에 더하는 비용은 작다 | 1,000행 UPDATE의 WAL bytes와 시간, 인덱스 있음 대 없음. 기대: 각각 ≤ +30% | +30% 초과 | 쓰기 경로에 인덱스를 둘 값이 있는지 |
| H5 | live ticket 검사 문장은 인덱스가 있으면 해당 Seller-SKU의 ticket 수와 무관하게 몇 buffer만 읽는다 | 검사 문장의 buffer. 선적재 ticket 0·50k·500k. 기대: ≤ 8, 비율 ≤ 2 | > 8 이거나 비율 > 2 | 검사 위치(잠금 안)가 비용상 허용되는지 |
| H5-음성 | 인덱스가 없으면 같은 문장이 ticket 수에 비례한다 | 인덱스 없음, 50k 대 0의 buffer 비율 ≥ 20 | < 20이면 하네스 무효 | ADR-0083이 우려한 비용이 실재하는지 |
| H6 | 규칙(잠금 안 검사 + 부분 인덱스)이 join 지연에 더하는 비율은 작다 | 한 Seller-SKU에 30 스레드, 선적재 50k ticket, 실행당 join 900건, 첫 100건은 워밍업으로 버린다, 조건당 n=5 실행. 같은 실행 안에서 규칙 없는 대조군을 번갈아 돌린다. 기대: p50 ≤ +10%, p99 ≤ +20% | 초과. 대조군 자체의 실행 간 폭((최대-최소)/중앙값)이 10%를 넘으면 **판단 불가** | 규칙을 잠금 안에 둘지 |
| H6-음성 | 인덱스 없이 규칙만 켜면 join이 눈에 띄게 느려진다 | 같은 조건, p50 ≥ +50% | < +20%이면 인덱스가 불필요하다는 뜻이므로 마이그레이션 제외 | V4 인덱스의 필요성 |
| H7 | 규칙이 한 구매자의 동시 join이 live ticket 2개를 갖는 것을 막는다 | 한 구매자, 서로 다른 Idempotency-Key 16개를 동시에 join, 200회 반복. 기대: 매 회 live 1개, 나머지는 409, 그 밖의 결과 0건 | 한 회라도 live ≥ 2 또는 409 아닌 실패 | 규칙의 정확성 |
| H7-음성 | 규칙이 꺼져 있으면 같은 경쟁에서 live ≥ 2개가 나온다(탐지기가 우는지) | 규칙 끔, 200회. 기대: ≥ 95%의 회차에서 live ≥ 2 | < 95%이면 경쟁이 안 만들어지는 하네스 | H7 판정의 유효성 |
| H7-변이 | 검사가 counter 잠금 앞에 있으면 중복이 생긴다 | 소스를 임시로 바꿔 200회. 기대: ≥ 1회 live ≥ 2 | 0회이면 이 하네스는 검사 위치를 구분하지 못한다: 그 사실을 적는다 | 검사 위치가 잠금 뒤여야 한다는 근거 |
| H8 | DB 유일 부분 인덱스는 같은 경쟁을 막지만, 이 규칙이 한 번도 강제되지 않았으므로 기존 데이터에 중복이 있으면 생성이 실패한다 | 중복 live 행이 든 표에서 `CREATE UNIQUE INDEX`와 비유일 인덱스. 기대: 유일은 실패, 비유일은 성공 | 유일도 성공 | 규칙을 유일 인덱스로 둘지 |
| H9 | 정리는 주문이 가리키는 ticket을 지우지 않는다 | N=1M(5%가 `purchase_order`에 연결), 끝까지 batch로 비운다. 기대: 가리키는 ticket 삭제 0건 | 1건이라도 | 보존 계약의 정확성 |
| H9-음성 | `NOT EXISTS`를 뺀 변형은 가리키는 ticket을 지운다 | 같은 데이터. 기대: ≥ 1건 삭제 | 0건이면 하네스가 가리키는 행을 못 본다 | H9 판정의 유효성 |
| H10 | 두 인스턴스가 동시에 정리해도 중복 삭제·오류·교착이 없다 | 2개 연결이 같은 후보를 비움, 20회. 기대: 삭제 합 = 후보 수, 오류 0 | 합 ≠ 후보 수 또는 오류 | 다중 인스턴스 안전성(DB lease 필요 여부) |
| H11 | 정리가 도는 동안 join 지연이 나빠지지 않는다 | H6 조건에 정리 loop(batch 500)를 추가, n=5. 기대: p99 ≤ +20% | 초과(또는 대조군 폭 > 10%이면 판단 불가) | 정리 batch·주기 |

표본 크기: H1~H5는 같은 데이터에 5회 반복(buffer 수는 결정적이라 반복은 오류 확인용), 시간은 최소·중앙·최대를 적는다. H6·H11은 조건당 n=5이고 조건 순서는 실행마다 무작위로 섞는다. H7은 200회에서 0건이면 실패율 상한이 3/200 = 1.5%(95%, rule of three)다. H10은 20회에서 0건이면 상한 3/20 = 15%이므로 **강한 증거가 아니다**: 구조(SKIP LOCKED)에 대한 확인이다.

## 통제와 교란 요인 계획

- 대조군: (가) 변경 없음(규칙 끔, 인덱스 없음), (나) 음성 대조군(위 `-음성`·`-변이`), (다) 같은 컨테이너·같은 데이터·같은 부하의 전후 비교. 표는 매번 새로 만들지 않고 `BEGIN … ROLLBACK`으로 같은 데이터를 반복한다.
- 공유 호스트: 실행 전후 `uptime`과 `docker stats`를 남기고, 시간은 맥락으로만 쓴다. 한 번만 제어할 수 없는 교란은 "교란 요인" 표에 남긴다.
- 알려진 교란 후보와 배제 방법(결과에 채운다): shared buffers 상태(cold는 컨테이너 재시작 직후 1회로 따로 적음, 결론은 hit+read 합), autovacuum·hint bit(VACUUM 뒤 측정), 플래너 통계(ANALYZE 뒤 측정), JIT(꺼서 고정), Hikari 풀 대기와 counter 잠금 대기가 섞이는 문제(EXP-090과 같아 분리하지 않음), GC(JVM 한 개 안에서 조건을 번갈아 돌림), 측정 하네스 버그(음성 대조군으로 증명).
- 내려갈 층: 앱 지연 → PostgreSQL(`EXPLAIN`, `pg_stat_*`, WAL 위치) 까지. 증거가 가리키지 않으면 네트워크·OS 층으로 내려가지 않는다. 멈춘 층과 이유를 결과에 적는다.

## 교차 모듈 사실 (코드 읽기, 실행 전)

- 주문 조회(`OrderServiceImpl`)는 CAMPAIGN 주문마다 `admission.find(campaignId, ticketId)`를 부르고, ticket이 없으면 `TICKET_NOT_FOUND`다. 주문은 영구 보존이라 이 읽기의 시간 창에는 끝이 없다: **보존 기간을 reader 창보다 길게 잡는 방식은 성립하지 않는다.**
- `releaseCheckoutSlot`이 주문 상태에 따라 ticket을 `EXPIRED`(결제 창 만료) 또는 `CHECKOUT_FAILED`(재고 없음·구매자 취소·판매 불가)로 만든다. 즉 주문이 가리키는 ticket도 종료 상태가 된다.
- `purchase_order.ticket_id`는 `UNIQUE`(`purchase_order_ticket_unique`)이고 FK가 없다.
- 주문은 `startCheckout` 직후 같은 transaction에서 만들어진다.

## 대안 (초안; 결과로 보강한다)

| 대안 | 비용 | 위험 | 증거 자리 |
|---|---|---|---|
| 하지 않음 | 0 | 표 무한 증가(행당 473 B), 구매자별 slot 독점 | H1 비교 |
| 보존 기간만으로 보호 | 최소 | 주문이 영구라 기간으로는 안전하지 않음 | 위 교차 모듈 사실 |
| soft-delete 표시 | 열 + 쿼리 변경 | 표가 줄지 않음 | 해당 없음(논리) |
| archive 테이블로 이동 | 테이블·이동 문장 | 같은 주문 조회 문제를 그대로 가짐 | 해당 없음(논리) |
| anti-join 정리(`NOT EXISTS purchase_order`) | SQL 한 문장, 인덱스 1개 | P(보호된 오래된 행)에 비례하는 읽기(H2) | H2·H9 |
| anti-join + "주문이 시작된 ticket" 표시 열 + 인덱스 제외 | 열·backfill·코드 한 줄 | 표시와 주문의 불일치 가능(표시는 최적화일 뿐 정확성은 anti-join이 지킴) | H2 |
| anti-join + 메모리 cursor | 상태 있는 단일 객체 | 재시작 시 처음부터, 인스턴스별 cursor | H2 |
| live 규칙: 잠금 안 검사 + 부분 인덱스 | 인덱스 1개 + 검사 문장 | 잠금 보유 시간 증가(H5·H6) | H5·H6·H7 |
| live 규칙: DB 유일 부분 인덱스 | 인덱스 1개 | 기존 중복 데이터에서 생성 실패, 위반이 500 | H8 |

**의사결정 규칙(실행 전 등록):** (1) H2가 확정이고 P=100k에서 정리 문장이 50,000 buffer 초과 또는 warm 100 ms 초과이면 완화책 둘(표시 열, cursor)을 같은 데이터로 재서 O(batch)이고 표면이 작은 쪽을 고른다. 아니면 완화책 없이 내보내고 되돌아볼 조건을 적는다. (2) live 규칙은 H6이 확정이면 잠금 안 검사 + 부분 인덱스를 기본으로 하고, 유일 인덱스는 join p50이 10% 이상 낫고 H8의 마이그레이션 위험이 해소될 때만 채택한다. (3) 어떤 음성 대조군이라도 울지 않으면 그 가설 판정은 "판단 불가"다.

## 사전 등록과 달라진 점 (정직한 기록)

- **산출물 위치를 바꿨다.** 사전 등록은 `load-tests/admission-tombstone/`에 harness를 두는 것으로 적었다. 실행 뒤 저장소에는 이 문서, ADR-0088, 재현용 SQL 하나(`EXP-092-admission-tombstone-purge.sql`), 코드와 통합 테스트만 두기로 했다. harness(합성 적재 SQL, 단계 스크립트, 계측 Java)는 저장소에 없고 아래 "삭제한 파일의 내용"에 방법·변수·명령을 옮겼다.
- **첫 Part A 실행의 harness 오류.** cutoff를 문장마다 `now()`에서 새로 계산해, 5,000,000행 실행 중(수 분) 표의 행이 cutoff를 넘어 "정리할 행이 없는 정상 상태"에 후보 수백 행이 생겼다(5M A2a에서 buffer 1,349~1,499, 1M에서 22~25). 음성 대조군이 아니라 **정상 상태 값이 이상하게 크게 나와서** 알아챘다. cutoff를 단계별로 고정해 전체를 다시 돌렸고 아래 표는 두 번째 실행이다.
- **H2의 결정 규칙(1)이 발동했다.** P=100,000에서 500,780 buffer라 완화책 두 개를 같은 데이터로 재서 하나를 골랐다(MARK).
- **H6·H11은 이 호스트에서 크기를 주장하지 않기로 결정했다.** 대조군의 실행 간 폭이 사전 등록한 10%를 크게 넘었다. 같은 조건을 12회로 늘려 다시 쟀지만 폭이 줄지 않았고, 결정과 재검토 조건은 아래 "EXP-105 종결 결과"의 G8에 있다.
- H3의 WAL/행 비율 기준은 지켜지지 않았다(아래).
- 시간 값 표본은 H1~H4 조건당 n=5(H3은 batch당 n=5, 실행 순서 교차), H6은 조건당 5회 실행 × 900 join. `control-b`(대조군 반복)는 첫 실행 뒤에 추가하려다 harness만 고치고 다시 돌리지 않았다.

## 환경

macOS arm64, Colima Docker VM(8 CPU)을 다른 에이전트 여섯 개가 같이 썼다. 실행 전 `uptime` 1·5·15분 load average: Part A 두 번째 실행 시작 17.8·26.0·39.4, 끝 13.7·16.4·22.2, Part B·C 시작 17.8·92.6·92.1, 끝 36.0·30.5·42.6. 부하가 매우 높았으므로 **시간은 맥락이고 결론은 buffer 수·개수·불변식에 둔다.** PostgreSQL 18.6 image 기본 설정, `jit=off`로 고정. 스키마는 V1~V3 적용 뒤(전)와 V4(후)이고 앱은 실제 `AdmissionServiceImpl`·JPA·JdbcTemplate(Hikari 풀 10).

## 결과

### H1·H1-음성: 인덱스가 있으면 정리 문장이 표 크기와 무관하다 (확정, 음성 대조군 작동)

정리 문장은 출하하는 모양(`NOT EXISTS (purchase_order)` + `FOR UPDATE SKIP LOCKED` + `LIMIT 500`)이다. 합성 데이터는 EXPIRED 80%·CHECKOUT_FAILED 10%·SUBMITTED 10%를 90일에 고르게 두었고 주문은 SUBMITTED 전부와 EXPIRED의 5%(전체 15%)를 가리킨다. cutoff는 30일. 모든 칸 n=5(buffer는 결정적이라 5회가 같거나 거의 같다). 표는 shared hit+read의 최소~최대와 시간 최소/중앙/최대(ms).

| 표 크기 | 상태 | 인덱스 없음 buffer | 인덱스 없음 시간 | **V4 인덱스(MARK)** buffer | MARK 시간 |
|---|---|---:|---|---:|---|
| 100,000 | A1 후보 많음(500행 삭제) | 5,248 | 135/365/665 | 4,065~4,577(TI) | 38/49/156(TI) |
| 100,000 | A2 정상(지울 행 없음) | 1,969 | 4.2/5.5/6.8 | **4** | 0.1/0.1/1.7 |
| 1,000,000 | A1 | 25,806 | 920/1,439/1,458 | 4,633~5,145(TI) | 3.5/10.3/51.7(TI) |
| 1,000,000 | A2 | 19,614 | 266/414/614 | **3** | 0.2/0.3/0.5 |
| 5,000,000 | A1 | 120,205 | 7,586/9,608/10,855 | 4,633~5,145(TI) | 8.8/15.9/325(TI) |
| 5,000,000 | A2 | 101,247 | 1,074/1,315/3,097 | **3** | 0.1/0.3/0.5 |

- H1 판정: MARK는 A2에서 100k→5M(50배)에서 4→3 buffer라 최대/최소 비율 ≤ 2 기준을 통과한다. A1은 batch 500에 비례하는 4,000~5,200 buffer로 표 크기와 무관하다(5M/100k 비율 1.14).
- **음성 대조군 작동:** 인덱스 없음 A2의 buffer가 100k 1,969 → 1M 19,614 → 5M 101,247이다(1M/100k = 9.96 ≥ 5, 5M/100k = 51). 하네스가 O(표)를 잡는다.
- 인덱스 크기: 부분 인덱스 3.5 MB(100k) / 34.8 MB(1M) / 173.8 MB(5M). 생성 시간(일반 `CREATE INDEX`, 쓰기 차단): 5M에서 9.0~12.5초, 1M에서 1.1~2.5초(n=1, 맥락).
- 표 크기: 표 15/153/791 MB, 인덱스 합 20/207/1,038 MB(행당 약 0.5 KB, EXP-090과 같은 수준).
- cold(컨테이너 재시작 직후 1회, 인덱스 없음 A1): 100k 5,760 buffer 473 ms, 1M 26,318 buffer 1,963 ms, 5M 120,717 buffer 24,145 ms. 결론에는 쓰지 않는다.

### H2: 주문이 가리켜 못 지우는 오래된 행이 쌓이면 읽기가 그 수에 비례한다 (확정) → MARK 선택

1,000,000행 표에서 정리할 행이 없는 정상 상태(A2)에, 영영 못 지우는 오래된 행(주문이 가리키는 EXPIRED) P개를 인덱스 앞쪽에 더하며 센다. n=5. 셋을 같은 데이터에서 비교한다. TI = 조건이 `status`뿐인 인덱스, CURSOR = TI + 지난 위치 이후만 읽는 keyset(상태 필요), **MARK = `checkout_started_at IS NULL` 조건이 붙은 인덱스(채택)**.

| P | TI buffer | TI 시간(중앙, ms) | CURSOR buffer | **MARK buffer** | MARK 시간(중앙) |
|---:|---:|---:|---:|---:|---:|
| 0 | 3 | 0.1 | 3 | 3 | 0.1 |
| 1,000 | 5,658~6,095 | 4.9 | 11 | 3 | 0.1 |
| 10,000 | 50,053 | 32.7 | 9 | 3 | 0.2 |
| 100,000 | **500,780** | 437.7 | 9 | **3** | 0.2 |

- 반증 조건(≤ 5배)을 넘었다: P=100,000에서 TI는 P=0의 167,000배 buffer를 읽는다. 사전 등록한 결정 규칙(1)(50,000 buffer 초과)이 발동했다.
- 후보가 있을 때(A1p: 보호 행 뒤에 지울 500행)도 MARK 4,590~5,173으로 P와 무관하고 TI는 P=100,000에서 505,052~505,635다.
- CURSOR도 O(batch)지만 위치를 기억할 상태가 필요하다(재시작하면 처음부터, 인스턴스마다 따로). MARK는 열 하나와 `startCheckout`에서 값을 쓰는 한 줄이고 상태가 없다. AGENTS.md가 "숨은 mutable singleton state"를 금지하므로 MARK를 골랐다.
- 한계: P는 "주문이 가리키는 30일 넘은 EXPIRED·CHECKOUT_FAILED ticket" 수이고 실제 값은 모른다(가정). P=100,000은 아주 큰 가정이며 P=10,000에서도 한 번에 32.7 ms(중앙)라 MARK가 없어도 급하지는 않다. 그래도 사전 등록한 규칙을 따랐다.

### H3: batch 상한이 잠금·WAL·시간을 batch에 묶는다 (부분 확정, WAL 비율 기준은 기각)

1,000,000행, 인덱스 있음, `CHECKPOINT` 뒤 실제 commit한 한 문장. 순서를 `100 500 5000 5000 500 100 …`로 교차해 batch당 n=5. 삭제 행 수는 모든 실행에서 batch와 정확히 같다(100/500/5,000).

| batch | 시간 min/중앙/max (ms) | WAL bytes min/중앙/max | WAL/행 중앙 |
|---:|---|---|---:|
| 100 | 31/34/111 | 43,896 / 171,128 / 1,200,688 | 1,711 |
| 500 | 32/56/122 | 186,552 / 198,264 / 1,322,128 | 397 |
| 5,000 | 339/373/597 | 1,540,496 / 1,630,616 / 2,675,896 | 326 |

- 시간 비(5,000/500 중앙) 6.6 ≤ 15 통과, 잠긴 행 = batch(`LIMIT`가 `FOR UPDATE` 후보를 묶음).
- **WAL/행 최대/최소 ≤ 1.5 기준은 어긋났다**(중앙값만 봐도 1,711 대 326). `CHECKPOINT` 직후 첫 접촉의 full page image 때문이라는 설명은 아래 "EXP-105 종결 결과"의 G10에서 분해해 확인했다(batch 500 이상). 총 WAL은 batch에 따라 100 → 5,000에서 약 10배(중앙 171 KB → 1.63 MB)이므로 "batch가 한 transaction의 WAL을 묶는다"는 주장만 남기고 "행당 일정하다"는 주장은 하지 않는다.
- 기본값 500·상한 5,000(워커 검증)은 이 표로 정한 것이 아니라 ADR-0083이 미리 정한 값(EXP-079 관례)이며, 이 측정은 그 값이 모순되지 않음을 보인다.

### H4: 정리 인덱스가 만료 UPDATE에 더하는 비용 (확정)

1,000행을 WAITING→EXPIRED로 바꾸는 문장, 인덱스 있음 대 없음을 실행마다 순서를 바꿔 n=5(인덱스는 status만 조건인 TI. MARK는 `checkout_started_at`이 NULL인 새 행이 모두 포함되는 같은 모양). 시간 중앙 72.1 대 72.6 ms(-0.7%), WAL 중앙 6,429,976 대 6,366,080 B(+1.0%). 기대(각각 ≤ +30%) 통과. 이 문장은 `admission_ticket_expiry_idx`·FIFO 인덱스를 어차피 고치므로 WAL이 크다.

### H5·H5-음성: live 검사 문장은 인덱스가 있으면 ticket 수와 무관하다 (확정, 음성 대조군 작동)

`EXPLAIN (ANALYZE, BUFFERS)`로 한 Seller-SKU의 종료 ticket 0·50,000·500,000개와 live 50개를 두고 구매자(없음 / live)로 검사 문장을 잰다(결정적이라 n=1씩).

| 종료 ticket | 인덱스 있음 buffer | 인덱스 없음 buffer | 인덱스 없음 시간 |
|---:|---:|---:|---:|
| 0 | 2 | 2 | 0.02 ms |
| 50,000 | 1~2 | 1,430 | 4.4~6.0 ms |
| 500,000 | 1~2 | 14,624 | 230~308 ms |

H5(≤ 8 buffer, 비율 ≤ 2) 통과. 음성 대조군: 인덱스 없음이 50,000에서 1,430 = 인덱스 있음의 약 715~1,430배(≥ 20) 작동. ADR-0083이 우려한 "잠금 안에서 buyer를 세는 비용"은 인덱스 없이는 실재하고 인덱스가 있으면 사라진다.

### H6·H6-음성·H11: join 지연 비용 (크기 주장 안 함: 결정, 아래 EXP-105 종결 결과 G8·G9)

한 Seller-SKU에 30 스레드, 스레드당 30 join(+실행 전 4회 워밍업은 버림), 같은 Seller-SKU에 종료 ticket 50,000을 선적재, 서로 다른 구매자. 조건당 n=5회 실행, 조건 순서는 실행마다 섞음. 25회 실행 모두 같은 JVM·같은 컨테이너(첫 전체 워밍업 1회 버림). 아래는 실행 5회의 최소/중앙/최대(ms).

| 조건 | p50 | p95 | p99 | 오류 |
|---|---|---|---|---:|
| control(규칙 끔, 인덱스 없음) | 252 / 357 / 424 | 477 / 943 / 1,451 | 727 / 1,352 / 2,298 | 0 |
| **규칙 + V4 인덱스** | 326 / 430 / 774 | 1,046 / 1,855 / 2,143 | 1,679 / 2,683 / 3,750 | 0 |
| 규칙, 인덱스 없음(H6-음성) | 389 / 622 / 711 | 588 / 2,154 / 4,212 | 917 / 3,558 / 8,380 | 0 |
| 유일 인덱스만(검사 없음) | 253 / 337 / 503 | 518 / 1,337 / 2,068 | 729 / 2,040 / 3,351 | 0 |
| 규칙 + 인덱스 + 정리 loop(H11) | 441 / 868 / 1,111 | 785 / 2,210 / 9,957 | 1,235 / 3,609 / 17,058 | 1 |

- **결정: 크기를 주장하지 않는다.** 사전 등록한 조건: 대조군의 실행 간 폭((최대-최소)/중앙값)이 10%를 넘으면 크기를 주장하지 않는다. 대조군 p50 폭 48%, p99 폭 115%다. 중앙값끼리는 규칙+인덱스가 p50 +20%, p99 +98%지만 범위가 겹치고(예: 규칙+인덱스 p50 최소 326이 대조군 최대 424보다 작다) 부하(load average 17.8~92.6)가 높아 "X%만 더한다"는 주장을 하지 않는다. 조건 순서는 실행마다 섞었고 아래 교란 요인 표에 한계를 적었다.
- H6-음성: 인덱스 없는 규칙의 p50 중앙은 대조군의 +74%(기대 ≥ +50%)로 중앙값에서는 작동하나 범위가 겹친다. **H5가 buffer로 같은 사실을 결정적으로 보이므로 V4 인덱스의 필요성은 H5가 근거**다.
- DB 쪽 추가 비용은 H5로 결정적이다: 검사 문장 1~2 buffer, 0.02~0.04 ms. 앱에서는 문장 하나(왕복 한 번)가 counter 잠금 보유 시간에 더해진다. 그 왕복의 실제 값은 이 측정에서 분리되지 않았다.
- H11: 정리 loop(batch 500, 50 ms 간격, 별도 Seller-SKU의 150,000행)와 같이 돌린 join의 p99는 3,609 ms(중앙)로 규칙+인덱스 2,683보다 높지만 대조군 폭 때문에 크기를 주장하지 않는다. 오류 1건은 그 실행에서 유형을 기록하지 않아 그 건 자체는 복원할 수 없다(결정: 복원하지 않는다). 대신 유형 기록 코드를 넣고 12회로 다시 돌렸다. 같은 조건의 오류 유형은 전부 풀 대기(`CannotCreateTransactionException`)였고 `lock_timeout`(55P03)은 0건이다(아래 EXP-105 종결 결과 G9).

### H7·H7-음성: 규칙이 한 구매자의 동시 join이 live 2개를 갖는 것을 막는다 (확정, 음성 대조군 작동)

한 구매자가 서로 다른 Idempotency-Key로 16 스레드 동시 join, 200회 반복(회마다 새 구매자).

| 조건 | live=1 회차 | live≥2 회차 | 결과 분포(3,200 join) |
|---|---:|---:|---|
| **규칙 + 인덱스** | **200** | **0** | ok 200, `LIVE_TICKET_LIMIT_REACHED`(409) 3,000, 그 밖 0 |
| 규칙 끔(음성 대조군) | 0 | **200** | ok 3,200 |
| 유일 부분 인덱스만 | 200 | 0 | ok 200, `DataIntegrityViolationException` 3,000 |

- 0/200 실패: 실패율 상한 3/200 = 1.5%(95%, rule of three).
- 음성 대조군은 200/200에서 live≥2(기대 ≥ 95%)로 작동한다. 규칙이 없으면 한 구매자가 한 번의 동시 요청으로 ticket 16개(이 실험의 스레드 수)를 잡았다.
- 유일 인덱스만 두면 중복은 막지만 위반이 `DataIntegrityViolationException`으로 올라와 지금 `GlobalExceptionHandler`에서 409가 아니라 500이 된다(핸들러를 읽은 것이며 HTTP로 재현하지는 않았다).
- **H7-변이(검사를 counter 잠금 앞으로 이동):** harness로 200회 돌리지 않았다. 대신 통합 테스트(8 스레드 1회)에 같은 변이를 넣어 테스트가 실패함을 확인했다(아래 변이 표 M7, n=1). 이 변이가 harness 200회에서 중복을 만드는지는 확인하지 않았다.

### H8: 유일 부분 인덱스는 기존 중복이 있으면 생성에 실패한다 (확정)

같은 구매자의 live ticket 2개가 든 표에서 `CREATE UNIQUE INDEX`는 `could not create unique index` 오류로 실패하고 같은 조건의 비유일 인덱스는 성공했다(n=1, 결정적). 규칙이 한 번도 강제되지 않았으므로 운영 DB에 이미 중복이 있을 수 있어, 마이그레이션이 유일 인덱스를 만들면 배포가 멈출 수 있다. 이것이 유일 인덱스를 채택하지 않은 이유 하나다.

### H9·H9-음성: 정리는 주문이 가리키는 ticket을 지우지 않는다 (확정, 음성 대조군 작동)

1,000,000행(주문 150,000개), batch 5,000으로 끝까지 비웠다. 안전 문장: 삭제 566,684행, 주문이 가리키는 ticket이 사라진 주문 **0개**. `NOT EXISTS`를 뺀 변형: 삭제 600,018행, 사라진 주문 **33,334개**(≥ 1 작동).

### H10: 두 인스턴스가 동시에 정리해도 중복·오류가 없다 (확정, 약한 증거)

100,000행에서 연결 2개가 같은 후보를 batch 500으로 비우는 일을 20회, `SKIP LOCKED`와 그것을 뺀 변형 각각. 두 변형 모두 20회 전부 삭제 합 = 후보 수(56,667~56,669), 남은 후보 0, 오류 0, 교착 0. 실패율 상한 3/20 = 15%라 **강한 증거가 아니다.** `SKIP LOCKED`를 뺀 변형도 통과했으므로 이 측정은 `SKIP LOCKED`의 필요를 증명하지 않는다. `SKIP LOCKED`는 admission 기존 코드(`tryLockCounter`)와 같은 관례이며 다른 인스턴스를 기다려 풀을 쓰지 않게 하는 구조적 이점으로 둔다(시간 중앙 995 대 1,458 ms는 맥락).

## 되돌리기 시연 (실제 실행)

이전 jar(`origin/main` `82345acd`)와 새 jar를 각각 `bootJar`로 만들고 같은 PostgreSQL 18.6 컨테이너 하나에서 순서대로 띄웠다(`ATLAS_DB_URL`로 연결, 앱 기동 완료는 `Started AtlasApplication` 로그로 확인).

1. 이전 jar가 빈 DB를 만든다: Flyway `1,2,3 성공`.
2. 오래된 종료 ticket 3개(주문 없음 2, 주문 있음 1)를 넣는다.
3. 새 jar + `ATLAS_ADMISSION_TOMBSTONE_PURGE_ENABLED=false`(정리 간격 PT2S): Flyway `1,2,3,4 성공`, 12초 뒤 ticket 3개 그대로, 새 열 1개·인덱스 2개 생성, backfill로 주문이 가리키는 ticket 1개가 `checkout_started_at`을 가짐(시드가 V4보다 앞이라 기대한 결과).
4. 같은 DB, 새 jar, 속성 기본값(켬): 12초 뒤 ticket 1개(주문이 가리키는 것의 순번 3만 남음).
5. **이전 jar를 V4가 적용된 DB에 다시 띄움:** 기동 완료, Flyway 경고 `Schema "public" has a version (4) that is newer than the latest available migration`만 나오고 계속 동작한다(n=1).

롤백 절차: `ATLAS_ADMISSION_TOMBSTONE_PURGE_ENABLED=false`와 `ATLAS_ADMISSION_MAX_LIVE_TICKETS_PER_BUYER=0` 또는 이전 jar 재배포. V4는 데이터와 제약을 바꾸지 않으므로 되돌리지 않는다. **지운 ticket은 되살릴 수 없다**(정리를 켠 뒤에는 롤백으로 복구되지 않는다). 시연하지 않은 것: 큰 표에서 `CONCURRENTLY` 경로, 두 인스턴스를 실제 앱으로 동시에 띄우는 정리.

## 삭제한 파일의 내용 (저장소에 두지 않은 harness)

저장소에는 재현용 SQL 하나만 두었다. 나머지는 이 실험을 돌린 로컬 스크립트이며 방법은 다음과 같다.

- **합성 적재(`gen.sql`, psql 변수 n):** V1~V3 스키마에서 `session_replication_role=replica`로 FK를 끄고 `admission_ticket`을 n행 넣는다. `created_at`은 `now()-90일`부터 `now()`까지 고르게, `expires_at`은 `created_at+2분`, 상태는 `g % 10 < 8` EXPIRED / `= 8` CHECKOUT_FAILED / `= 9` CHECKOUT_SUBMITTED, `sku_id='sku-'||(g%200)`, `buyer_ref='buyer-'||g`, `idempotency_key='key-'||g`. 주문(`purchase_order`)은 SUBMITTED 전부와 `sequence % 20 = 0`인 EXPIRED에 한 개씩(전체의 15%).
- **Part A 단계 스크립트(`run-purge-plan.sh`):** 컨테이너 `postgres:18.6`(label `atlasexp=h2`)에 `probe` 데이터베이스를 V1~V3으로 만들고 단계마다 `CREATE DATABASE … TEMPLATE probe`로 새 데이터베이스를 만든다. `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`을 `BEGIN … ROLLBACK` 안에서 실행해 `Execution Time`과 최상위 `Shared Hit/Read Blocks`와 사용한 인덱스 이름을 한 줄로 기록한다. 단계: `sizes`(100k·1M·5M, 인덱스 없음 → 인덱스 → 정상 상태 → MARK, 조건마다 n=5), `h2`(1M 복제본에 P=0·1k·10k·100k를 더하며 TI·CURSOR·MARK), `h3`(batch 100·500·5,000 교차, 실제 commit, 앞에서 `CHECKPOINT`, `pg_current_wal_lsn()` 차이와 삭제 행 수), `h4`(1,000행 만료 UPDATE, 인덱스 있음·없음 실행마다 순서 교체), `h8`, `h9`(정리 loop를 `DO` 블록으로 batch마다 commit, `NOT EXISTS` 없는 변형은 음성 대조군), `h10`(연결 2개 동시, 20회). 모든 단계는 cutoff를 단계별로 한 번만 계산한다. 명령: `TAG=h2 run-purge-plan.sh /tmp/출력` (환경 변수 `SIZES`, `REPS`, `BASE_N`, `STEPS`). 결과는 `단계 DB 변형 반복 ms hit read 인덱스` 열의 TSV(`results.tsv`)이고 이 문서의 표는 그 최소/중앙/최대와 buffer 범위다.
- **계측 Java(`LiveTicketProbeExperiment`):** 임시로 `atlas-application/src/test/java/com/atlas/experiment/`에 복사해 Gradle로 한 번 실행하고 지운다. 실제 `AdmissionServiceImpl`을 `AdmissionLimits`(`maxLiveTicketsPerBuyer` 0 또는 1)로 직접 조립해 조건을 바꾼다. 조건: control(규칙 끔, 인덱스 없음), 규칙+V4 인덱스, 규칙+인덱스 없음, 유일 부분 인덱스만, 규칙+인덱스+정리 loop. 인덱스는 조건마다 `DROP/CREATE INDEX`로 바꾸고 조건 순서는 시드를 고정해 섞는다. 실행 한 번의 흐름: 새 Seller-SKU를 만들고 종료 ticket 50,000개를 `INSERT … generate_series`로 넣고 `ANALYZE`, 스레드 30개 × 4번 워밍업(버림), 스레드 30개 × 30번 join을 시간 재고, `VACUUM`으로 정리. 경쟁 단계는 구매자 하나·키 서로 다름·16 스레드·`CountDownLatch`로 동시에 출발, 구매자마다 live ticket 수를 센다. 환경 변수 `PROBE_RUNS=5 PROBE_PRELOAD=50000 PROBE_RACES=200 PROBE_PARTS=check,perf,race`.
- **되돌리기 시연 스크립트:** 위 "되돌리기 시연"의 5단계를 `java -jar`와 `docker exec psql`로 자동화한 것이다.
- **로컬 원자료:** Part A 두 번째 실행 `results.tsv` 279줄, Part B·C `probe.txt`는 `/tmp`에만 있다. 저장소에는 두지 않으며 위 표가 정본이다.

## 한계

단일 호스트·공유 VM, 합성 데이터, 모의가 아닌 실제 `purchase_order` 스키마(V1)이지만 데이터는 합성이다. P·구매자 행동·운영 규모는 모른다. H6·H11은 크기를 주장하지 않으므로 "규칙이 join을 X% 느리게 한다/아니다"를 말하지 않는다(G8). H10은 표본이 작다. 정리를 켠 운영 DB에서의 실제 속도·WAL 영향은 측정하지 않았다.

### G8: 대조군 폭을 줄여 H6을 다시 쟀다

| 원래 H6 대조(`rule+index / control` 인덱스 없음) p50·p99 | 1.09 (0.48~2.41), 1.24 (0.66~2.02) |
| 인덱스 없는 규칙 `rule-noindex / control` p50·p99 (음성 대조군) | 1.56 (0.65~3.67), 1.72 (0.87~4.60), 1 초과 10/12 |

해석: 사전 등록한 반증 조건(대조군 폭 10% 이하)은 만족하지 못했다(폭 206~279%). 쌍 비율의 중앙값은 1.02~1.05이고 절반 안팎의 실행이 1을 넘으므로(6/12, 7/12) 규칙 때문의 증가가 보이지 않지만, 범위가 0.5~2.6배라 "+10% 이하"도 증명하지 못한다. 음성 대조군(인덱스 없는 규칙)은 10/12에서 1을 넘어 검출기가 반응한다. 결정(유형 2): join 지연 비율은 이 호스트에서 주장하지 않는다. 규칙의 DB 쪽 비용은 H5(검사 문장 1~2 buffer, 결정적)로만 주장한다. 대안: 코어를 고정한 전용 호스트에서 재측정. 재검토 조건: 대조군 실행 간 폭이 10% 이하로 n≥10을 채우는 호스트가 생기거나, 운영 join p99가 규칙 배포 뒤 20% 넘게 오를 때.

### G9: 정리 loop를 켠 join의 오류 유형

12회 실행에서 오류 유형을 기록했다. join 오류는 `rule-noindex` 10건, `rule+index` 6건, `control+index` 2건, `rule+index+purge` 1건이고 모두 `CannotCreateTransactionException`(SQLState 없음, 풀에서 연결을 얻지 못함: 풀 10에 스레드 30)이다. 정리 loop가 없는 조건에서도 같은 유형이 나왔고, `lock_timeout`(55P03)은 조건당 약 7,200 join 중 0건이다(규칙 3: 상한 약 0.04%). 정리 loop 조건은 876회 호출로 438,000행을 지웠고 오류 1건이었다. 가설(오류 유형은 `lock_timeout`)은 반증됐고 오류는 풀 대기다. 정리가 join 지연을 키우지 않는다는 주장은 G8과 같은 이유로 하지 않는다(결정).

### G10: WAL 행당 비율의 분해 (`CHECKPOINT` 직후 첫 실행과 이후 실행)

1,000,000행, 인덱스 있음, `autovacuum=off`, `jit=off`. 한 번 `CHECKPOINT` 직후 첫 실행("cold")과 같은 데이터에서 `CHECKPOINT` 없이 이어 돌린 실행("warm")을 batch 100·500·5,000에서 각 n=5로 `pg_get_wal_stats`로 분해했다(전체 이미지 FPI와 그 밖의 레코드).

| 측정 직전 상태 | batch | WAL/행 중앙(최소~최대) | 최대/최소 | FPI 비중 중앙 | FPI 제외 WAL/행 중앙 |
| --- | --- | --- | --- | --- | --- |
| cold | 100 | 12,010 (677~12,067) | 17.8 | 0.97 | 340 |
| cold | 500 | 399 (373~2,654) | 7.1 | 0.71 | 109 |
| cold | 5,000 | 326 (310~328) | 1.06 | 0.65 | 109 |
| warm | 100 | 2,215 (113~2,216) | 19.7 | 0.86 | 283 |
| warm | 500 | 128 (113~533) | 4.7 | 0.12 | 109 |
| warm | 5,000 | 116 (114~117) | 1.03 | 0.03 | 108 |

("cold"는 측정 직전에 매번 `CHECKPOINT`, "warm"은 `CHECKPOINT` 뒤 같은 후보 50,000행을 `DELETE`/`ROLLBACK`으로 한 번 훑어 페이지를 읽어 둔 뒤 측정. 순서는 batch를 돌려 가며 교차.)

결과: WAL/행의 실행 간 변동은 FPI가 만든다(batch 100은 cold·warm 모두 FPI 비중 중앙 0.86~0.97, batch 5,000 warm은 0.03). FPI를 뺀 레코드는 batch 500·5,000에서 행당 108~109 B로 일정하고 batch 100은 283~340 B로 크다(batch마다 고정 비용이 있다). 따라서 "첫 접촉의 full page image 때문"이라는 가설은 batch 500 이상에서는 확인됐고, batch 100의 FPI 제외 값이 큰 이유는 분해하지 않았다(결정: batch 100은 기본값 500·상한 5,000 밖이라 운영에 쓰지 않으며 재검토 조건은 batch 기본값을 500 미만으로 바꾸는 변경). 사전 등록한 "WAL/행 최대/최소 ≤ 1.5" 기준은 전체 batch를 합치면 여전히 어긋난다(최대/최소 107배). "행당 일정하다"는 주장은 하지 않는다.
