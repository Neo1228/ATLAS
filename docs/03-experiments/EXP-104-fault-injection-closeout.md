# EXP-104: EXP-095가 남긴 장애 칸(음성 대조군 결함·정지 없는 교차 중복·PT15S 경계·고부하 PT30S·약한 주입)을 닫는다

- 질문: [EXP-095](EXP-095-fault-injection-deep-cells.md)가 "확인하지 못함"·"실행하지 않음"으로 남긴 칸을 각각 (1) 실행으로 확인하거나 (2) 하지 않기로 결정하거나 (3) 이 환경에서 못 하는 증거를 붙여 끝낼 수 있는가?
- 상태: **사전 등록(가동 전).** 이 절까지는 측정 전에 쓴 것이며 결과는 같은 문서의 아래 절에 채운다. 가설은 가동 전 별도 커밋으로 기록한다(커밋 이력이 증거).
- 날짜: 2026-11-26
- 관련: [EXP-095](EXP-095-fault-injection-deep-cells.md), [EXP-085](EXP-085-fault-injection-repeated.md), [EXP-087](EXP-087-fault-injection-network-disk-multi-app.md), [EXP-099](EXP-099-redis-admission-control-test-flake.md), [EXP-068](EXP-068-stage-evidence-map.md)(8단계 표), 이슈 [#669](https://github.com/Neo1228/ATLAS/issues/669), [#667](https://github.com/Neo1228/ATLAS/issues/667), D-164, D-171

## 문제 한 문장

EXP-095는 `a-ctl-L7`의 "교차 인스턴스 중복 0"을 검증하는 음성 대조군(`PLANT_DUP`)이 5개 중 2개에서만 울렸고, 정지가 없는 대조군 1개(host load 34.5)에서 교차 key 23개가 설명 없이 나왔으며, PT15S 경계·고부하 PT30S는 실행하지 않았고, SYN 드롭은 새 연결이 없어 약한 주입이었고, 요청 드롭의 엄격 창 기준은 세는 방법이 불분명했으며, #667의 원래 실패는 원인을 확정하지 못한 채 열려 있다. 영향을 받는 것은 lease 값을 고르는 운영자와 이 하네스의 "0건" 결과를 근거로 읽는 사람이다.

## 읽고 확인한 사실 (설계 근거, 이번 실행 결과 아님)

- EXP-095 2차 가동 원자료를 읽었다(`a-ctl-L7` 5개). 심은 key의 줄 수는 rep-1·2에서 2, rep-3·4·5에서 1이다. `converge_seconds`는 반응한 두 실행이 2.22초·21.75초, 반응하지 않은 세 실행이 1.43·1.40·1.44초다. 이 상관은 가설 A1을 세우게 한 관찰이며(독립적이지 않음) 인과를 보이지 않는다.
- location 컨테이너의 access log는 Spring Boot `server.tomcat.accesslog` 기본값으로 켜져 있고 `buffered` 기본값은 true라고 읽었다(확인하지 않음: A1이 확인한다). 러너는 `docker logs`를 심은 호출 직후와 감사가 끝난 뒤 두 번 읽는다.
- 정지 없는 대조군 rep-2의 교차 key 23개: location A의 호출 쌍은 첫 호출이 201(서버 처리 1.7~3.0초)이고 약 14초 뒤 다른 인스턴스가 같은 key로 200(재생)이다. 같은 실행의 `lease-claims.json`은 `takeover_claims=0`, claim 779건(workflow 560개)이다. 즉 lease 인수가 아니라 "첫 시도의 결과를 못 받은 뒤 recovery worker가 다시 시도"로 읽힌다(가설 B1). 앱 로그에는 호출 실패 줄이 없어(한 인스턴스에서 Hikari 풀 대기 경고만) 앱 쪽 직접 증거는 없다.
- 앱 설정 기본값: HTTP connect timeout 250ms, read timeout PT2S, 복구 lease 기본 PT30S, 첫 재시도 대기 PT1S, 최대 PT1M(`LocationReservationConfiguration`). 검증 규칙은 `lease/2 > connect + read + 1s`. 앱 1의 location 방향에는 netem 400ms(송신)가 걸리므로 SYN 한 번에 400ms가 더해져 connect timeout 250ms를 넘는다. 이 때문에 앱 1은 netem이 걸린 뒤 새 연결을 만들 수 없을 가능성이 있다(가설 B3 이후 pcap으로 본다).
- #667의 원래 실패 로그는 `afull_h4.log`·`afull_h4.status`로 /tmp에 남아 있다. 남은 정보는 "테스트 101행 `AssertionFailedError`", "752건 중 1건 실패", 헤드 `7655f063`, 호스트 부하 평균 약 20, 빌드 23분 59초다. 예외 클래스·WARN 줄·XML 결과는 남아 있지 않다.

## 가설 (실행 전에 적음)

공통 판정: 반증 조건이 관측되면 그 가설은 틀린 것이고 지우지 않고 결과 절에 그대로 둔다. 조건별 n이 작으면 0건은 `3/n`(세 번의 법칙) 상한으로만 쓴다. 호스트(공유 Docker VM)의 시간 값은 맥락이고 결론은 개수와 불변식에 둔다.

### (b) 정지 없는 대조군의 교차 인스턴스 중복

설정: 2대, `FAULTS=none`, PT10S, 앱 1에 netem 400ms, 같은 부하(40/s·14초), 호스트 부하는 내가 띄우는 CPU 사이드카(`atlasexp=t4`, 시작 시 N개 busy loop)로 만든다. 팔: hog 0개(n=6), 16개(n=6), 48개(n=6), 그리고 PT30S + hog 48개(n=5, lease 독립성 대조). 실행 순서는 시드 20261126으로 섞는다. 각 실행에서 order DB의 lease 로그에 claim 시각(ms)·claim한 클라이언트 주소(`inet_client_addr()`)·이전 토큰을 남기고 종료 시 workflow 행(`attempt_count`, `last_error_code`)을 저장한다. 앱 1·2의 네임스페이스에서 `tcpdump`(사이드카, 읽기만)로 location 포트(8090) 패킷을 기록한다.

### (c) PT15S 경계와 고부하 PT30S

설정: 2대, app 1 `docker pause`, netem 400ms. 팔: `a-p15-s12.5`, `s13`, `s14`, `s15`, `s16`(PT15S, 정지 길이 S초, 각 n=5, 25회), `a-p30-hog-s12`(PT30S, 12초, hog 48, n=5), `a-p30-quiet-s12`(같은 조건 hog 없음, n=5), `a-p15-hog-s12`(PT15S, 12초, hog 48, n=5). 전체 40회를 시드 20261126으로 한 목록에서 섞는다. 정지 직전에 lease를 쥔 workflow의 **남은 lease 시간**을 ms 단위로 기록한다(`lease_until − clock_timestamp()`).

| 가설 | 예측 | 반증 | 지표 | 결정 |
| --- | --- | --- | --- | --- |
| C1 정지 중 인수는 정지 직전 남은 lease < S인 workflow에서만 일어난다(이전 토큰이 있는 claim) | 남은 시간 ≥ S+1초인 workflow의 인수 0, 남은 시간 ≤ S−1초인 workflow의 인수 ≥ 90% | 남은 시간 ≥ S+1초인 인수 1건이라도, 또는 ≤ S−1초 인수율 < 70% | workflow별 남은 시간과 인수 여부 | 맞으면 "안전 조건 = lease − 최대 보유 나이 > 정지 길이"를 모형으로 쓴다 |
| C2 PT15S에서 xdup>0 실행 수는 S에 따라 늘어난다 | S=12.5 ≤ 2/5, S=13 ≤ 3/5, S=15 ≥ 4/5, S=16 5/5 | S=16에서 노출 E ≥ 1인데 xdup=0인 실행이 있음, 또는 S=12.5에서 ≥ 4/5 | 팔별 xdup>0 실행 수, E | 경계가 몇 초인지 표로 남긴다 |
| C3 PT30S는 고부하(hog 48)·12초 정지에서도 xdup=0이다 | 5/5 xdup=0 | xdup>0인 실행이 1개라도 | 팔별 xdup | 맞으면 "PT30S는 12초 정지에 호스트 포화가 겹쳐도 안전"(n=5, 상한 `1−0.05^(1/5)=45%`) |
| C4 PT15S는 hog 48·12초 정지에서 xdup>0이 자주 난다(EXP-095의 load 127·216 실행이 부하 때문이었다) | 5개 중 3개 이상 xdup>0 | ≤ 1/5 | 팔별 xdup | 맞으면 EXP-095 A3의 교란을 부하 효과로 정리한다. 틀리면 그 두 실행의 원인은 부하가 아니라고 정정한다 |

기본값 결정 규칙(사전): PT30S 유지. 더 짧은 L\*는 (i) 12초 정지 hog 0·hog 48 모두 xdup=0 5/5, (ii) 네 불변식 통과·이중 201 0, (iii) 수렴 중앙값이 PT30S보다 짧음을 모두 만족할 때만 후보다. 기본값을 바꾸면 코드·설정 변경, 테스트, ADR-0096을 같이 한다. 아니면 변경 없음이고 ADR을 쓰지 않는다.

- 모든 실행은 한 번에 stack 하나(2대 stack은 컨테이너 7개, 사이드카와 hog를 더해 최대 9개: 지시의 6개 상한을 stack 구성상 지키지 못한다. 형제 실험도 같은 구성이었다). 컨테이너·볼륨·네트워크·사이드카는 `atlasexp=t4` 라벨이고 종료 뒤 라벨로 0개를 확인한다.
- 교란: 호스트 부하(Mac `uptime`과 VM `/proc/loadavg`를 실행 앞뒤에 기록), 공유 Docker VM, hog 자체의 CPU 점유, jar가 같은 빌드(`origin/main` `e0a2660a`), 실행 순서(섞기). 앱 1에만 netem이 걸려 인스턴스 대칭이 아니다.
- 사전 부검: (1) hog가 너무 세서 stack이 안 뜨면 시작 뒤 hog를 켠다. (2) 새 판정이 기존 줄을 잘못 읽으면 자체 시험과 기존 원자료(`a-ctl-L7` 5개)로 먼저 비교한다. (3) 버퍼 끄기가 줄 형식을 바꾸면 파서가 0줄을 내므로 0줄이면 실패로 처리한다.
- 되돌리기 시험: 하네스 변경은 새 옵션의 기본값이 기존 동작과 같음을 `origin/main` 사본과 `bash -n`·`selftest`·`cmp`로 확인하고, 실제로 이 PR의 하네스 커밋을 별도 worktree에서 `git revert`해 변경 전 파일과 바이트 단위로 같음을 확인한다.
