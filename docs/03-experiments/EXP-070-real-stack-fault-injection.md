# EXP-070: 실제 서버와 실제 DB에 컨테이너 장애를 주입했을 때 예약 상태는 어긋나는가

- 질문: 메모리 모델이 아니라 실제 JVM 3개와 실제 PostgreSQL 3개로 이루어진 스택에서 order DB, location 서버, location DB 컨테이너에 장애를 주입하면 주문 쪽과 창고 쪽 상태가 어긋나는가? 복구는 얼마나 걸리는가?
- 상태: 탐색 실험. 조건별 n=1(복구 시간 측정만 n=2~3). **하네스는 저장소에 올리지 않았다**(아래 "코드를 올리지 않은 이유").
- 날짜: 2026-11-24
- 관련: [EXP-064](EXP-064-location-fault-convergence.md), [EXP-053](EXP-053-inventory-location-failure-load.md), [ADR-0060](../02-decisions/adr/ADR-0060-order-inventory-reservation-workflow.md), [EXP-071](EXP-071-production-like-fault-injection.md)(운영 형태 스택에서 같은 질문을 Pumba로 반복)

## 왜 했는가

[EXP-064](EXP-064-location-fault-convergence.md)와 EXP-066은 location을 `MockWebServer` 메모리 모델로 대체했다. 모델이 실제 서비스와 같은 규칙을 지키는지, 그리고 실제 DB·JVM·네트워크에서 같은 결과가 나오는지는 검증하지 못했다고 적었다. 이 실험은 그 빈칸을 로컬의 실제 스택으로 채운다.

## 환경과 방법

- 호스트: Apple 실리콘 Mac, Colima Docker VM. 호스트의 CPU·메모리 한도는 기록하지 않았다. 컨테이너에는 자원 한도를 걸지 않았다.
- 구성(Docker Compose, 로컬 전용): application JVM 1개(`eclipse-temurin:25-jre`, 2026-11-24 main의 `bootJar`), inventory-location JVM 2개(창고 A, B), PostgreSQL 18.6 3개(order 1, 창고별 1), mailpit. application은 두 location을 HTTP로 호출한다. 결제는 `disabled`.
- 부하: 초당 40건의 예약 요청(`POST /api/internal/order-inventory/reservations`, 주문마다 창고 A·B에 SKU 1개씩)을 14초간, 총 560건. 요청 시작 시각을 일정 속도로 맞추고 스레드 64개로 보냈다.
- 장애: 시작 3초 뒤 대상 컨테이너에 `docker pause`/`stop`/`kill`을 적용하고 6초 뒤 `unpause`/`start`로 되돌린다. `pause`는 TCP 연결을 유지한 채 응답만 멈추고, `kill`은 SIGKILL이다.
- 감사: 이 실행이 만든 SKU만 대상으로, order DB의 workflow 상태와 두 location DB의 예약 수량을 `psql`로 직접 센다. 응답으로 `RESERVED`를 받은 요청이 최종 `RESERVED`로 남았는지(`lost`), order가 `RESERVED`라고 믿는 수와 location이 쥔 수가 같은지를 본다.
- 설정은 모두 기본값이다(Hikari 풀 10, connection-timeout 500ms, 복구 worker 활성, lease 30초).

## 결과: 컨테이너 장애 6가지(각 n=1, 560건)

| 장애 대상과 방식 | 장애 구간에 시작한 요청 | 클라이언트 결과 | 응답받은 예약 유실 | order 대 location 일치 |
| --- | --- | --- | --- | --- |
| order DB `pause` | 245 | 201 342, 503 218 | 0 | 342 = 342 = 342 |
| order DB `stop` | 253 | 201 284, 500 7, 503 269 | 0 | 285 = 285 = 285 |
| order DB `kill` | 256 | 201 280, 500 4, 503 276 | 0 | 282 = 282 = 282 |
| location B 서버 `kill` | 252 | 201 205, 202 355 | 0 | 560 = 560 = 560 |
| location B 서버 `pause` | 225 | 201 366, 202 194 | 0 | 560 = 560 = 560 |
| location B DB `kill` | 154 | 201 431, 202 129 | 0 | 560 = 560 = 560 |

- 일치 열은 "order가 `RESERVED`로 가진 수 = 창고 A가 쥔 수 = 창고 B가 쥔 수"이다.
- location 장애에서는 요청이 `202 RETRY_PENDING`으로 응답한 뒤 복구 worker가 끝까지 처리해 560건이 모두 `RESERVED`가 됐다. 수렴 대기는 0.1~4.3초였다.
- order DB 장애에서는 `503`을 받은 요청의 workflow 행이 order DB에 없고 location에도 흔적이 없었다(요청이 DB에 닿기 전에 거절됨). `stop`·`kill`에서 클라이언트가 `500`을 받았지만 order DB에 `RESERVED`로 남은 workflow가 1~2건 있었다(`stop` 285 대 응답 284, `kill` 282 대 응답 280). 응답을 알 수 없던 요청이 실제로는 성공한 경우이며 두 location 보유량과 정확히 일치했다.
- `pause`는 장애 구간 요청이 최대 6.19초까지 매달렸고(Hikari 대기 후 실패), `stop`·`kill`은 약 0.5초에 빠르게 실패했다. 연결 거절과 응답 정지가 다르게 관측된다.
- 응답받은 예약이 사라진 경우는 6가지 모두 0건이었다.

## 발견: 복구가 정확히 10초 늦는다 (DNS 부정 캐시)

order DB를 `kill`한 직후 `start`했을 때 앱이 첫 `201`을 돌려줄 때까지의 시간을 잰 결과다(`kill` 직후 바로 또는 0.3초 뒤 `start`, 이후 0.5~0.8초 간격으로 요청. 두 측정의 대기 간격이 조금 달랐다).

| 조건 | 첫 `201`까지 | 횟수 |
| --- | --- | --- |
| DB를 호스트 이름(`order-postgres`)으로 접속(기본) | 10.0초, 9.8초 | n=2 |
| DB를 컨테이너 IP(`172.25.0.4`)로 접속 | 0.2초, 0.3초, 1.3초 | n=3 |
| 호스트 이름 접속 + `networkaddress.cache.negative.ttl=0` | 0.5초, 1.3초, 0.2초 | n=3 |

- 재시작 전후 컨테이너 IP는 같았다(`172.25.0.4`, kill·stop 각 시도에서 확인). 즉 이름 해석 결과가 바뀐 것이 아니라 **재시작 직전·직후 잠깐 이름 조회가 실패한 사실이 JVM에 캐시돼** 있었다.
- 해당 JRE(`eclipse-temurin:25-jre`)의 `java.security`에는 `networkaddress.cache.negative.ttl=10`이 있다(컨테이너 안에서 직접 확인). 실패한 이름 조회를 10초간 기억하고 그동안 새 연결을 시도하지 않는다는 설명과, 관측된 정확히 10초 지연이 일치한다.
- IP로 바꾸거나 부정 TTL을 0으로 두면 지연이 사라진다. 두 개입 모두 같은 효과이므로 원인이 이름 조회의 부정 캐시라는 가설을 강하게 지지한다. 단 이것은 측정과 개입으로 좁힌 결론이고, JVM 내부에서 해당 조회 실패를 직접 관측(예: 조회 로그)한 것은 아니다.
- 같은 부하(560건, `kill`)를 TTL 0 설정에서 다시 돌렸을 때 장애 종료 뒤 진행 중 workflow가 사라질 때까지의 대기가 **21.1초에서 0.1초로** 줄었다(각 n=1). 반면 클라이언트가 받은 `503` 수는 276건과 277건으로 거의 같았다. 지속 부하에서는 첫 실패 이후 풀과 worker가 이미 다시 시도하는 상태라 클라이언트 관점의 이득이 작았고, 이 차이를 완전히 설명하지는 못했다.
- 이 TTL은 JDK 기본값이라 운영에서 DB를 호스트 이름으로 접속하는 모든 JVM에 해당할 수 있다. 영향을 받는 것은 이름 조회가 잠깐 실패하는 환경(컨테이너 재시작, DNS 전환, 장애 조치)이다.

## 결과: 네트워크 지연·손실(각 n=1, 560건)

대상 컨테이너 `eth0`의 송신 쪽에 `tc qdisc netem`을 건다(컨테이너 안에서 실행, `NET_ADMIN`). 적용 여부는 application 컨테이너에서 order DB로 TCP 연결 5회를 맺는 시간으로 확인했다(적용 전 19ms, 지연 200ms 적용 중 1,009ms, 해제 후 4ms). 호스트 포트 포워딩을 거치는 연결로는 지연이 보이지 않아 이 방법을 쓰지 않았다.

| 조건 | 장애 구간에 시작한 요청 | 구간 내 결과 | 전체 결과 | 지연 p50/p95/max | 진행 중 소멸 대기 | 응답받은 예약 유실 | order 대 location |
| --- | --- | --- | --- | --- | --- | --- | --- |
| order DB 송신 지연 300ms±50ms, 13초 | 360 | `503` 351, `201` 9 | `201` 206, `503` 354 | 0.50초, 3.60초, 6.99초 | 27.5초 | 0 | 236 대 236 |
| location B 송신 패킷 손실 30%, 9초 | 264 | `201` 61, `202` 203 | `201` 355, `202` 205 | 0.23초, 3.12초, 3.24초 | 2.4초 | 0 | 560 대 560 |

- 지연 조건에서 `503` 354건 중 324건은 order DB에 workflow 행이 없다(요청이 거부됨). 나머지 30건은 행이 있어 order가 `RESERVED`로 확정했다(order 236 = `201` 206 + 30). 클라이언트는 실패로 보지만 예약은 성립한 요청이 있다는 뜻이다. 같은 idempotency key로 재요청했을 때 재생되는지는 이 실행에서 확인하지 않았다.
- 지연 조건의 `503`은 용량 계산과 일치하지만 검증하지 않은 가설이다. DB 왕복마다 300ms가 붙으면 요청 하나가 연결을 0.3초 이상 쥐고, 초당 40건이면 동시에 12개 이상의 연결이 필요하다. 풀은 10개이고 connection-timeout은 500ms다. 요청당 DB 왕복 수와 풀 대기 시간은 측정하지 않았다.
- 손실 조건에서는 실패 대신 `202 RETRY_PENDING`으로 접수됐고 모든 workflow가 `RESERVED`로 수렴했다. 접수와 수렴이 coordinator의 설계대로 동작한 결과이며, 손실 비율을 바꿔 한계를 찾지는 않았다.

## 이 결과가 증명하는 것과 아닌 것

- 증명한 것: 이 스택과 이 조건에서 order DB, location 서버, location DB 컨테이너의 `pause`·`stop`·`kill` 중 어떤 경우에도 응답받은 예약이 사라지거나 주문과 창고 상태가 어긋나지 않았다. 메모리 모델로 얻은 [EXP-064](EXP-064-location-fault-convergence.md)의 결론이 실제 서버에서도 같았다.
- 증명하지 못한 것:
  - 조건별 n=1이다. 장애 구간에 시작한 요청 수와 결과는 실행마다 다르다.
  - PostgreSQL을 SIGKILL한 뒤 데이터 디렉터리를 재사용하는 크래시 복구의 정합성. 이번 `kill`은 같은 볼륨으로 재시작했고 커밋된 행이 보존됐지만, fsync 설정과 WAL 손상까지 검증하지는 않았다.
  - 네트워크 분리(양방향 부분 장애), CPU·메모리 압박. 지연·손실은 위 두 조건만 n=1로 했고 크기·비율·대상 조합은 넓히지 않았다. 이 실험은 `docker pause/stop/kill`과 `tc netem`만 썼고 Pumba는 쓰지 않았다([EXP-071](EXP-071-production-like-fault-injection.md)이 Pumba로 반복했다).
  - Kafka 중단. 이 실험은 relay를 켜지 않았다. [EXP-072](EXP-072-kafka-outage-relay.md)가 다뤘다.
  - 장애 구간이 6초로 짧다. lease(30초)보다 긴 장애에서의 동작은 EXP-066의 메모리 모델 결과(복구 약 29초)에만 근거한다.
  - 호스트 자원을 통제하지 않았으므로 처리량·지연 수치는 일반화할 수 없다.
- 장애 구간에 시작한 요청 중 일부는 성공했다(`pause` 23~27건, `stop` 2건, `kill` 1건). 장애가 시작되는 순간과 요청이 겹치는 정도는 제어하지 못했다.

## 하네스 조건(결과 해석에 필요한 것)

- 부하는 14초에 걸쳐 일정 속도로 보내고, 장애 구간에 **시작한 요청 수**를 함께 기록한다. 40건을 0.2초에 모두 보내면 요청이 장애 전에 끝나 장애 구간의 요청이 0건이 되고, 이 경우 "유실 0건"은 아무것도 검증하지 않는다.
- `location_held`는 이 실행이 만든 SKU만 센다. location DB에는 이전 실험의 예약이 남아 있어 전체 수를 세면 섞인다.
- 복구 지연의 원인 후보는 Hikari 풀 회복, lease 만료, 이름 조회 캐시였다. 컨테이너 IP 불변과 IP 접속·부정 TTL 0 개입의 결과로 이름 조회 캐시만 남겼고, 풀 상태나 lease 만료 시각을 직접 재서 나머지 둘을 배제하지는 않았다.

## 코드를 올리지 않은 이유

실행 도구(compose 파일, 감사 스크립트, 장애 주입 스크립트)는 컨테이너 6개와 `docker`·`psql` 명령에 의존하는 로컬 실험용이고 CI에서 안정적으로 돌릴 대상이 아니다. 저장소 밖에 보관하고 이 문서에 구성·파라미터·감사 방법을 모두 적었다. **저장소만으로는 재현할 수 없다.**

## 후속 제안(적용하지 않음)

- DB 접속 JVM의 `networkaddress.cache.negative.ttl`을 낮추는 방안: `java.security` 오버라이드(`-Djava.security.properties`)나 애플리케이션 기동 시 `Security.setProperty`. 이 실험은 전자만 컨테이너에서 검증했고 후자는 검증하지 않았다. 부작용은 이름 조회 실패 시 조회가 자주 반복되는 것이며 측정하지 않았다. 운영 설정 변경이므로 별도 결정(ADR)이 필요하다.
- 조건별 반복을 늘리고 6초보다 긴 장애, 지연·손실의 크기별 비교, 네트워크 분리를 같은 방식으로 추가한다.
