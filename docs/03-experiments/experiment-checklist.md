# 부하 실험 점검표

- 날짜: 2026-11-23([EXP-062](EXP-062-admission-gate-paired-comparison.md)와 [EXP-063](EXP-063-redis-gate-failopen-and-paired-rerun.md)에서 적용했고, 못 지킨 항목은 각 문서의 한계에 적었다)

각 항목은 출처 근거가 있다. 근거는 [ADR-0068](../02-decisions/adr/ADR-0068-external-research-direction-review.md)의 외부 조사다. 하나라도 못 지키면 해당 문서에 "한계"로 적고 그 수치를 절대값·퍼센트 주장에 쓰지 않는다.

## 0. 주장 등급을 먼저 정한다
- A급(방어 가능): 요청당 DB tx 수·행 수·호출 수 같은 결정론적 카운트, 불변식(오버셀 0), 병목 위치의 정성적 식별.
- B급(자릿수 비교): 같은 세션 안에서 3회 이상 반복했고 범위가 겹치지 않는 비율. 하한/상한으로만 쓴다.
- C급(쓰지 않는다): 단일 호스트·1~2회의 절대 처리량, p99, "N% 개선", 서로 다른 세션 비교.

## 1. 환경 기록 (EXP 문서 "환경" 절에 반드시)
- [ ] VM vCPU/메모리(Colima 설정), 호스트 모델, 컨테이너 CPU limit 합계 ≤ VM vCPU − 2 인지. (limit은 quota일 뿐 예약이 아니다.)
- [ ] k6 위치. 가능하면 다른 머신/다른 VM. 불가능하면 `cpuset`으로 코어를 분리하고 그 사실을 한계로 적는다.
- [ ] 이미지/JDK/PG 버전, 커밋 SHA, 스크립트 환경변수 전체, 실행 순서(arm·rate).
- [ ] 샘플러(`docker stats --no-stream` 1초 주기, actuator curl)가 같은 VM에서 도는 비용을 샘플러 끈 1회로 비교했는가.

## 2. 부하 생성기가 병목이 아님을 증명
- [ ] k6 컨테이너 CPU 평균·최대 ≤ 80% (k6 공식 권고: 20% idle). 초과 시 그 실행은 "생성기 포화"로 표시하고 서버 용량으로 해석 금지.
- [ ] `dropped_iterations`는 실패다. `thresholds: { dropped_iterations: ['count<N'] }` 또는 비율 0.1% 미만을 통과 조건으로 둔다. 초과한 비율은 "포화 이후"로 분류.
- [ ] Little 법칙으로 VU 점검: 필요 VU ≈ rate × 응답시간(s). maxVUs / rate < p99 응답시간이면 드롭이 불가피하다.
- [ ] k6 Trend는 요청 시작 시각 기준이고 드롭된 반복은 지연 표본이 없다. 드롭이 있는 실행의 p99는 "완료분 p99"로 명기하고 하한으로만 쓴다.

## 3. 실행 길이와 워밍업
- [ ] 워밍업: 목표 속도의 50% 이상으로 30~60초 이상, 수락 경로와 거절 경로를 모두 지나게 한다(현재 100/s×10s는 JIT·풀·Lua 스크립트 캐시에 부족할 수 있다).
- [ ] 측정 구간: 최소 60~120초(권장 5분). 5초 버킷별 처리량으로 정상상태(앞·뒤 절반 차이 < 5%)를 확인한다.
- [ ] 구간 안에 gate stock-ttl 주기, Hikari 풀 변동, checkpoint/autovacuum 중 어느 것이 들어갔는지 기록(없었다면 "포함하지 않음"이라고 적는다).
- [ ] 실행 직후 settle(비종결 workflow 0) 확인은 유지.

## 4. 반복과 통계
- [ ] 반복 단위는 "요청"이 아니라 "전체 실행"(fresh compose, JVM 재기동, DB 새로 생성). 현재 방식(fresh project)은 맞다.
- [ ] 일반 주장 n ≥ 5, 효과가 30% 미만이면 n ≥ 10~30(CV 15%에서 10% 차이를 80% 검정력으로 보려면 독립 비교 약 35회, 짝지으면 줄어든다).
- [ ] 보고: 중앙값 + [최소, 최대] + n. 평균의 평균·p99의 평균은 금지(Tene: 백분위는 평균 불가). p99는 실행마다 따로 적고 합치려면 HdrHistogram 병합.
- [ ] 신뢰구간: 짝지은 비율의 bootstrap 95% CI. 부호 검정류는 n=5에서 양측 p=0.0625로 0.05를 못 넘는다(n≥6).
- [ ] A/A 대조: 같은 arm을 끼워 넣어 잡음 하한을 잰다. 지금까지 관측된 잡음은 [EXP-060](EXP-060-hot-sku-admission-gate.md) 기준선 1,000/s 3회 383.0~525.0(최대/최소 1.37배), [EXP-062](EXP-062-admission-gate-paired-comparison.md)의 precheck 1,000/s 6회 937~996/s(6%)와 A/A 2,000/s 2회 1,894 대 1,977/s(4.2%)다.

## 5. A/B 설계
- [ ] arm(off / redis / precheck)을 같은 세션·같은 스크립트·같은 rate 목록에서 블록 단위로 섞는다(블록당 무작위 순서 또는 ABBA). rate도 오름차순 고정 금지.
- [ ] 블록 안에서 비율(gate/off)을 구하고 블록들의 중앙값·범위·CI를 보고한다.
- [ ] 비교 지표는 고정 rate의 completed/s가 아니라 "SLO 안에서 지속 가능한 최대 rate"(드롭<0.1%, 거절 경로 p99<기준, 5xx 0). gate arm이 offered load에 붙어 있으면 knee를 못 잰 것이다. rate를 더 올려 knee를 찾는다.
- [ ] 세 번째 arm(Redis 없는 사전 점검)으로 "Redis 효과"와 "일찍 거절하는 효과"를 분리한다.

## 6. 설계상 거절 비율 보고
- [ ] 전체 요청 중 수락/설계상 거절/오류/드롭 비율을 표 첫 열에 쓴다(예: 100 재고·20,000 요청이면 99.5%가 거절).
- [ ] 지연·처리량은 결과별(수락/거절)로 분리해서 쓴다. 혼합 p99는 거절 경로 지연이다.
- [ ] 이득의 상한은 대략 1 / (1 − ρ(1−ε)) (ρ=거절 비율, ε=gate 경로 상대 비용)임을 적고, 운영 ρ를 추정할 수 없으면 일반화하지 않는다.

## 7. 워크로드 대표성
- [ ] SKU 수, 수요 분포(Zipf s), SKU당 재고, 주문당 라인 수를 명시. 단일 SKU 실험은 "메커니즘 확인"으로만 쓴다.
- [ ] 꼬리 SKU에서 gate 오버헤드(캐시 미스 시 location 조회+SET)를 따로 잰다.

## 8. 주장 문장 규칙
- 사용: "이 환경에서 A는 B보다 최소 약 N배(범위 [x, y], n=k)", "요청당 DB tx가 5.75~5.94 → 0.02로 줄었다(EXP-060, 1,000/s, 결정론적 카운트)".
- 금지: "처리량이 X로 늘었다", "N% 개선", "원인은 Y이다"(대조 arm 없이).
