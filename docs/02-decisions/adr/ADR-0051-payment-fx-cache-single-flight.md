# ADR-0051: 결제 환율 조회를 TTL 캐시 + 단일 비행으로 줄인다

- 상태: Accepted — 구현 추적: [#420](https://github.com/Neo1228/ATLAS/issues/420)
- 날짜: 2026-11-20
- 관련 결정: [ADR-0026](ADR-0026-paypal-sandbox-payments.md), [ADR-0030](ADR-0030-paypal-currency-boundary.md), [EXP-041](../03-experiments/EXP-041-payment-external-fx-dependency.md)

## 문제

결제는 PayPal authorization 을 시작할 때 외부 환율 API(BOK ECOS)를 **동기로** 호출하고 캐시가 없었다. 결제 1건이 외부 호출 1회를 만들고, 그 지연이 결제 응답시간에 그대로 더해졌다(EXP-041: 주입 80ms → p50 91.90ms, 450ms → 461.43ms). 외부 장애는 곧 결제 전면 중단이었다.

먼저 "핫 로우 경쟁"을 가설로 세웠지만 측정에서 **틀렸다**. `inventory_pool` 단일 행 UPDATE 는 32 client 에서도 194,219 tps 였다. 병목은 DB 가 아니라 요청 경로의 외부 의존이었다.

## 결정

1. 환율 조회 결과를 **60초 TTL** 로 캐시한다(`atlas.payment.fx.cache-ttl`).
2. 캐시 미스가 동시에 몰리면 **한 번만 외부 호출**하고 나머지는 그 결과를 기다린다(단일 비행). 캐시만으로는 만료 직후 thundering herd 를 막지 못한다.
3. 외부 조회 실패 시 **마지막 정상값을 최대 10분**까지 사용한다(`atlas.payment.fx.max-stale`). 초과하면 예외를 올려 결제를 막는다.
4. 캐시는 프로세스 로컬로 시작한다. 공유 캐시는 replica 수·호출량 측정 후 판단한다.

## 왜 금전 정합성이 깨지지 않는가

- BOK ECOS 731Y001 은 **일 단위 고시**다. 60초 TTL 은 고시 주기보다 훨씬 짧다.
- 결제 금액은 `PaymentAttempt.setFxSnapshot` 으로 **불변** 스냅샷으로 고정된다. 이후 모든 비교(`refundAmountWon`, 캡처 금액 검증)는 저장된 값과만 한다.
- 따라서 캐시는 "어떤 고시값을 스냅샷으로 고를지"에만 영향을 주고, 한번 고정된 결제의 금액을 바꾸지 않는다.

## 실패 경로

| 상황 | 동작 | 근거 |
| --- | --- | --- |
| 캐시 적중 | 외부 호출 없음 | EXP-041: p50 0.00ms |
| 동시 콜드 스타트 | 외부 1회 | 단일 비행 테스트(8 스레드 → 1 호출) |
| 외부 실패, max-stale 이내 | 마지막 값 사용 + WARN | 결제 지속 |
| 외부 실패, max-stale 초과 | 예외 → 결제 차단 | 낡은 환율로 조용히 결제하지 않음 |
| max-stale < ttl 설정 | 기동 실패 | 설정 오류를 조기에 드러냄 |

## 대안과 trade-off

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 캐시 없이 외부 호출 유지 | 측정된 지연이 1:1 로 결제에 더해진다. |
| 캐시만, 단일 비행 없음 | 만료 직후 N개 동시 요청이 N회 외부로 나간다(측정으로 필요 확인). |
| 환율을 DB 테이블에 고정 배치로 적재 | 새 테이블·스케줄러·장애 경로가 늘어난다. 60초 TTL 로 같은 효과를 더 적은 복잡도로 얻는다. |
| Redis 공유 캐시 즉시 도입 | 측정되지 않은 필요에 인프라를 추가한다. replica 간 불일치는 스냅샷 불변성으로 금전 영향이 없다. |
| 외부 실패 시 결제 차단(캐시 없음과 동일) | 외부 장애가 곧 매출 중단이 된다. 10분 staleness 는 명시적 교환이다. |

## 실측: replica 배수 (EXP-041)

프로세스 로컬 캐시의 비용을 실측했다. 호스트에서 JVM·stub·k6 를 모두 실행해 같은 네임스페이스에서 측정했다.

| 조건 | 결제 | FX 외부 호출 |
|---|---:|---:|
| 단일 인스턴스, TTL 내 | 3 | **0** |
| 단일 인스턴스, TTL 만료 후 | 1 | **1** |
| replica 2대, 각 1건 (같은 TTL 창) | 2 | **2** (인스턴스별 1) |

즉 캐시는 단일 인스턴스에서 TTL 당 1회로 접히고, replica 수만큼 곱해진다. 계산 모델이 관측으로 확인됐다.

## 공유 캐시 결정: 보류 (근거 명시)

| 선택지 | 상태 |
|---|---|
| 지금 Redis 도입 | **보류.** 측정된 호출률은 `replica 수 / TTL` 수준이며, 운영 결제율·quota 대비 위협 여부가 아직 판단되지 않았다 |
| PostgreSQL 단일 행 캐시 | **후보.** 새 인프라 없이 공유 가능. 도입 시점에 다시 비교한다 |
| 프로세스 로컬 유지 | **현재 선택.** 측정된 절대값이 작고, replica 간 값 차이는 금전 영향이 없다(스냅샷 불변) |

보류 근거는 "측정이 없어서"가 아니라 "배수는 알려졌고, 운영 quota 와의 비교가 남아서"다. `atlas.payment.fx.external` 지표로 replica 별 호출률을 관측할 수 있으므로, quota 근접이 확인되면 그때 도입한다.

## 한계

- TTL·max-stale 은 측정이 아니라 판단이다(고시 주기 + 결제 실패 허용 시간). 운영 분포로 조정해야 한다.
- 프로세스 로컬 캐시라 replica 간 값이 최대 60초 다를 수 있다. 금전 영향은 없지만, 이를 관측하지 않으면 "왜 다른 금액인가"라는 문의에 답하기 어렵다.
- replica 배수 측정은 호스트 단일 머신, 낮은 결제율(vus=1) 조건이었다. 높은 결제율에서 배수가 유지되는지는 별도 측정이 필요하다.
- 외부 API quota·429 동작은 측정하지 않았다.
