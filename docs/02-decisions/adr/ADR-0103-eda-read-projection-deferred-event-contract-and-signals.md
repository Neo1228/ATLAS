# ADR-0103: 판매자 정산 조회 투영은 넣지 않고(덮는 인덱스는 쓰기 비용 결정으로 남김), 공개 이벤트 계약에 버전을 두며, EDA 전환 신호를 지표로 낸다

- 상태: Accepted(사용자 승인 전 에이전트 제안; 승인 여부는 확인하지 못함)
- 날짜: 2026-11-27
- 관련 결정: [ADR-0067](ADR-0067-event-log-kafka-relay.md)(이벤트 로그·옵트인 relay), [ADR-0087](ADR-0087-consumer-contract-first-delivery-order-and-rebalance.md)(소비자 규약), [ADR-0100](ADR-0100-settlement-ledger-guards.md)(원장 추가 전용·균형), [ADR-0057](ADR-0057-financial-operation-outbox-and-payout-reconciliation.md)(판매자 advisory 락), D-182
- 근거: [EXP-114](../../03-experiments/EXP-114-seller-statement-projection-and-transition-signals.md), 이슈 [#719](https://github.com/Neo1228/ATLAS/issues/719)

## 문제

판매자 잔액(`sellerBalance`)과 환불 분개의 보류 잔액(`reserveBalance`)은 판매자 원장 전체 이력을 합산하고, 정산서 30일 기간 합계의 수수료·보류 부분은 기간과 무관하게 판매자의 모든 항목을 읽는다. 합성 원장(항목 970만 행)에서 판매자 항목 39만 행일 때 잔액 p50 241 ms, 판매자 락을 쥔 환불 분개 트랜잭션 p50 191 ms, 30일 정산서 1회 p50 579 ms였다(EXP-114 A0). 조회 투영(EDA 검토 3.2)을 넣을지 정해야 했다.

## 결정

1. **조회 투영(같은 트랜잭션 A2, 비동기 A3, materialized view A4)은 넣지 않는다.** A2는 원장에 없던 핫 행(같은 판매자 c = 8 capture 처리량 -66.6%)과 교착(판매자 둘의 checkout에서 0.417%, 트리거를 지우면 0)을 만들었다. A4는 새로 고침 16~23 s 동안 오래된 값이라 돈을 정하는 경로(지급 예약, 환불 분개)에 쓸 수 없다. A3는 정확했지만(투영 + 꼬리 = 원장 합산, 늦은 커밋 유실 0) 꼬리 인덱스 때문에 capture p50이 늘었고 worker·cursor·대사를 운영해야 한다.
2. **덮는 인덱스(A1)도 기본으로 넣지 않는다.** 사전 등록한 H4(쓰기 p50 증가 ≤ 10%)가 같은 창 쌍 측정에서 반증됐다: capture c = 1 p50 0.324 → 0.411 ms(+27%), 처리량 2,663.5 → 1,836.7 tps(-31%). 같은 측정에서 읽기는 환불 분개 p50 207.6 → 7.1 ms(100k), 정산서 1회 666.2 → 112.9 ms(100k)로 줄었다. 원인은 새 인덱스가 키 중복 제거(B-tree deduplication)를 받지 못해 이전 인덱스(68 MB)의 약 10배(715 MB)라는 것이다. 이 교환(쓰기 약 0.09 ms 대 판매자 락 안 읽기 약 200 ms)을 받아들일지는 사용자가 정할 일이라 근거와 선택지를 #719에 남긴다.
3. **공개 이벤트 계약에 `schemaVersion`(1)을 둔다.** 필드 추가는 같은 버전, 이름·형식·뜻 변경과 삭제는 버전을 올린다. 소비자는 모르는 버전에서 멈춘다. 계약 시험이 필드 집합·형식·key·중복 제거 헤더를 고정한다. 필드 이름을 바꿔도 기존 시험 8건이 모두 통과했던 것을 재현했다(H9). Kafka relay는 계속 옵트인이고 기본 꺼짐이다.
4. **EDA 전환 신호를 지표로 낸다.** 청구 지연 타이머 `atlas.queue.claim.duration{queue,outcome}`(기본 켜짐, DB 질의 추가 없음)와 큐 표 부풀음·락 대기 게이지(`atlas.observability.database-signals.enabled`, 기본 꺼짐, 통계 뷰만 읽음). 임계값과 검토할 전환은 운영 가이드 "EDA 전환 신호" 표 한 곳에 둔다. 원장 삽입 지연과 핫 SKU 경합은 새 지표를 만들지 않는다(EXP-114 표의 이유).

기본값 규칙: 계약 필드는 추가 필드라 기존 소비자에 영향이 없다. 타이머는 기존 청구 호출을 잴 뿐이다. DB 통계 게이지는 주기 질의가 생기므로 옵트인이다.

## 결과

- 판매자 정산 조회 비용은 지금과 같다. 운영 가이드의 판매자 이력 조회 신호(정산서·환불 라우트 p95 > 50 ms)가 넘으면 A1(쓰기 비용 수용) 또는 A3를 다시 정한다.
- 정산서 독자가 같은 DB의 쓰기 처리량을 크게 줄였다(H3: 독자 4개에서 capture 처리량 -90%). 원인은 EXP-114 H3 원인 절. 판매자 조회가 많아지면 읽기 분리(replica, distributed-readiness 5절)보다 먼저 이 비용이 드러난다.
- 공개 payload에 필드 하나가 늘었다.

## 롤백

- 공개 계약: `schemaVersion` 필드를 빼고 계약 시험 기대값과 참조 소비자 검사를 고친다.
- 신호 지표: `atlas.observability.database-signals.enabled=false`(기본). 청구 타이머는 Micrometer `MeterFilter`로 막는다.
- 스키마·데이터 변경 없음(마이그레이션 없음).

## 재검토 조건

- 판매자 정산서·환불 라우트 p95가 50 ms를 15분 넘게 넘거나, 한 판매자의 항목이 4만 행(EXP-114 10k 판매자)을 넘는 판매자가 생기면 A1을 쓰기 비용과 함께 다시 정한다. 그 전에 쓰기 비용이 작은 변형(INCLUDE 없는 `(seller_id, account_code, recorded_at)`, 계정별 부분 인덱스)을 같은 쌍 측정으로 잰다.
- A1 뒤에도 판매자 하나가 항목 표의 상당 부분(EXP-114 1m 판매자: 40%)이면 A3를 다시 잰다.
- relay를 켜고 외부 소비자가 생기면 `schemaVersion` 2가 필요한 변경 전에 소비자 목록과 이관 기간을 정한다.
