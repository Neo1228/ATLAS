# ADR-0074: shard 가중치는 최근 성공 실행의 평균으로 스크립트가 만든다

- 상태: Accepted(시뮬레이션 근거. 실제 CI 효과는 [EXP-076](../../03-experiments/EXP-076-shard-balance.md)의 마지막 절)
- 날짜: 2026-11-24
- 관련 결정: [ADR-0070](ADR-0070-parallel-backend-ci.md)
- 근거: [Issue #599](https://github.com/Neo1228/ATLAS/issues/599), [EXP-076](../../03-experiments/EXP-076-shard-balance.md), [EXP-069](../../03-experiments/EXP-069-ci-shard-imbalance.md)

## 문제

ADR-0070의 shard 가중치는 한 번의 실측으로 만들었고 갱신은 사람이 기억해야 한다. 그 파일은 4개 shard가 모두 210초로 균형이라고 예측했지만 성공 실행 111회에서 실제 클래스 시간 합은 평균 221/165/203/158초였다. 한 번의 실행에서 비싸게 나온 클래스를 계속 비싸다고 적고, 그 뒤 추가된 클래스는 모르기 때문이다. 클래스 시간 합과 shard job 시간은 `job = 68초 + 0.503 x 합`의 관계라(EXP-076) 이 어긋남은 가장 느린 job을 수 초 늘린다.

## 결정

- 가중치는 Backend CI 최근 성공 실행 30회의 `CLASSTIME` 클래스별 **평균**으로 `scripts/ci/update-test-shard-weights.py`가 만든다. 기본은 보고만 하고 `--write`를 줘야 파일을 쓴다. 보고서는 현재 파일과 새 가중치의 예상 균형을 같은 실행들에서 비교한다. 검증은 가장 새 3분의 1을 그보다 오래된 실행으로 만든 가중치로 잰다(미래 실행을 훈련에 쓰지 않는다).
- 파일을 자동으로 커밋하는 워크플로는 만들지 않는다. 사람이 보고서를 보고 `--write` 한 뒤 일반 PR로 낸다.
- 균형 방식은 지금의 LPT를 그대로 둔다(`TestShardFilter` 변경 없음). 파이썬의 LPT가 실제 배정과 같음을 실행 14회로 확인했다.
- shard 개수는 4개를 유지한다. `--shard-counts 3,4,5,6`으로 다시 계산할 수 있다.
- 비싼 구간 수정이나 테스트가 크게 바뀐 변경이 병합되면 가중치를 다시 만든다. 이 PR의 값은 그 수정 이전의 시간 분포로 만든 것이다.

## 대안과 버린 이유

| 대안 | 버린 이유 |
| --- | --- |
| 중앙값 가중치 | 2~4초와 20~35초를 오가는 클래스는 중앙값이 낮은 쪽이라 shard 합을 13~20초 낮게 잡는다(편향). 무작위 분할과 시간순 분할에서 평균보다 나빴다. |
| 한 번 실측을 계속 사용 | shard 합 예측 오차가 36.2초로 평균 20회의 26.8초보다 크고, 일회성 비싼 구간을 클래스의 성질로 적는다. 다만 앞으로 걷는 검증에서 평균과의 차이는 3~4초로 표준편차보다 작았다. |
| 훈련 실행에 직접 최적화한 배정(국소 탐색) | 최대 shard 합이 4~7초(job 시간 2~4초) 줄지만 실행 간 표준편차 18~25초에 묻히고, 클래스별 shard 번호 목록이라 필터 형식과 shard 개수 고정이 바뀌며, 클래스 시간이 시점에 따라 이동하므로(EXP-076 사실 3) 쉽게 낡는다. |
| 가중치를 갱신하는 워크플로(자동 커밋/PR) | 쓰기 권한 토큰이 필요하고 낡았는지 판단 없이 PR이 쌓인다. 갱신이 드물어(비싼 구간 수정이나 테스트가 크게 바뀐 뒤) 스크립트를 사람이 돌리는 것으로 충분하다. |
| shard 5개 이상 | 모형으로 5번째 shard가 가장 느린 job을 약 19초 줄이고 job 합계를 11% 늘린다. 이 이득은 한 실행의 잡음(표준편차 약 15~18초) 정도라 지금은 늘리지 않는다. 비싼 구간이 수정돼 클래스 시간 합이 줄면 적정 개수는 더 줄어든다. |

## 결과와 한계

- 낡은 파일(최대 shard 합 225~231초, 최대/평균 1.21~1.24) 대신 최근 평균 가중치(같은 구간 검증에서 209~214초, 1.12~1.14)를 쓴다. 효과는 클래스 시간 합 기준 약 12~17초이고 job 시간으로 약 6~8초(0.503을 곱한 모형 추정)다. 실제 CI에서 같은 조건으로 잰 값은 EXP-076 마지막 절에 있다.
- **방식(평균 대 중앙값 대 직전 1회) 사이의 차이는 24시간 표본에서 유의미하게 가르지 못했다.** 이 결정의 근거는 "낡은 가중치를 피하고 갱신을 도구로 만든다"이다.
- 남는 편차(상한 대비 약 27초)는 클래스별 독립 잡음이다. 가중치로 줄일 수 없고, 비싼 구간의 정체를 찾는 작업에서 다룬다.

## 실패 경로와 되돌리기

- 가중치가 틀려도 테스트는 빠지거나 중복되지 않는다. 필터가 모든 클래스를 정확히 한 shard에 배정하고, 가중치에 없는 클래스는 이름 해시로 배정된다(ADR-0070). 틀린 가중치의 비용은 균형 악화뿐이다.
- 되돌리기: 가중치 파일을 이전 커밋 값으로 되돌린다. 스크립트는 저장소 밖 서비스(`gh`)에 의존하며 실패하면 파일을 쓰지 않고 끝난다.
- `gh` API 형식, `CLASSTIME` 로그 줄, job 이름(`Application tests`)이 바뀌면 스크립트가 쓸 수 있는 실행을 찾지 못해 종료한다. `Summarize executed tests` step의 출력 줄은 스크립트가 읽는 계약이다.
- 새 가중치를 쓰는 PR의 shard 구성이 바뀌므로 그 PR 자체의 CI에서 shard별 시간을 확인한다.

## 후속

- 비싼 구간 수정이 병합되면 `--write`로 가중치를 다시 만들고 `--shard-counts`로 shard 개수를 다시 계산한다.
- 갱신을 잊지 않게 하는 장치(주기, 경고)는 만들지 않았다. 문제가 반복되면 보고서의 `현재 파일` 행 최대/평균이 1.2를 넘는 시점을 기준으로 삼는다.
