# ADR-0110: 판매자 반품 권고는 결정 규칙이 판정하고 돈을 움직이지 않으며, 환불은 판매자의 기존 검수 호출만 실행한다

- 상태: Accepted(1단계. 이슈 [#737](https://github.com/Neo1228/ATLAS/issues/737)의 에이전트 결정이며 사용자 승인 여부는 확인하지 못함)
- 날짜: 2026-11-28
- 관련 결정: [ADR-0089](ADR-0089-return-window-and-inspection-deadline.md)(반품 기간·검수 마감), [ADR-0061](ADR-0061-return-restock-source-shipment.md)(반품 줄의 출고 출처), [ADR-0030](ADR-0030-paypal-currency-boundary.md)(환불 금액 경계)
- 근거: [EXP-121](../../03-experiments/EXP-121-seller-return-refund-recommendation.md), D-189

## 문제

판매자는 반품을 수령한 뒤 `PUT .../returns/{returnId}/inspection`으로 줄마다 `PASSED`/`FAILED`를 정하고, `PASSED` 줄이 있으면 같은 호출 안에서 기존 환불 경로가 PayPal 환불까지 실행한다. 그런데 판매자는 구매자가 왜 반품하는지 몰랐고(`order_return`에 사유 컬럼 없음), 반품 기간·이미 환불된 수량·금액을 직접 대조해야 했다. AI 보조를 붙이면 잘못된 승인이 곧 금전 손실이고, 구매자 자유 텍스트는 프롬프트 주입 통로다.

## 결정

1. **사유는 코드와 선택 자유 텍스트로 받는다(V15).** `order_return.reason_code`(값 집합 = `ReturnReason`: `CHANGED_MIND`, `DEFECTIVE`, `DAMAGED_IN_DELIVERY`, `WRONG_ITEM`, `NOT_AS_DESCRIBED`, `OTHER`)와 `reason_note`(500자 이하, 앞뒤 공백 제거)를 nullable로 더한다. 사유 이전 클라이언트와 기존 행을 위해 사유는 선택이고, 텍스트는 사유가 있을 때만 받는다(서비스와 DB 제약이 함께 막는다). 같은 멱등 키의 재요청은 사유와 텍스트까지 같아야 한다.
2. **권고는 `atlas-order`의 결정 규칙(`ReturnRecommendationRules`)이 낸다.** 입력은 DB 사실(요청 시각, 줄별 출고 `delivered_at`, 주문 수량, 이미 환불된 수량, 주문 스냅샷으로 서버가 계산한 줄 환불액)과 판매자가 줄마다 적은 상태(`ReturnItemCondition`)뿐이다. **구매자 자유 텍스트는 규칙의 입력 타입에 없다.** 줄 판정 순서와 표는 아래와 같다.
   - 이미 환불된 수량과 합쳐 주문 수량을 넘거나 계산한 환불액이 0 이하인 줄이 하나라도 있으면 반품 전체 `REJECT`(`DUPLICATE_REFUND`). 지금은 요청 시점 검사가 먼저 막으므로 다른 환불 경로가 생겼을 때의 방어선이다.
   - `NOT_RETURNED` → 그 줄 불통과. 출고 시각을 모르면(출고 출처가 없는 옛 줄) 사람 검토.
   - 요청 시각이 그 줄 출고의 `delivered_at + window`보다 늦으면(경계 포함, ADR-0089와 같은 계산) 불통과. 판매자가 하자를 확인한 줄(`DEFECT_CONFIRMED`)만 사람 검토. `window-enforced=false`로 접수 거절을 꺼도 권고는 기간을 본다.
   - 기간 안: `DEFECT_CONFIRMED`·`UNOPENED`·`OPENED`는 사유와 무관하게 통과. `USED`·`DAMAGED`는 단순 변심이면 불통과, 판매자 책임 주장이나 사유 없음이면 사람 검토(원인을 판단해야 함).
   - 줄을 모아 모두 통과 `APPROVE_FULL`, 통과·불통과 섞임 `APPROVE_PARTIAL`, 모두 불통과 `REJECT`, 판단하지 못한 줄이 있으면 `HUMAN_REVIEW`. 승인 권고의 환불 합계가 `atlas.order.return.recommendation.review-amount-won`(기본 300,000원, 포함)을 넘으면 `HUMAN_REVIEW`(`AMOUNT_ABOVE_REVIEW_LIMIT`).
3. **권고는 읽기 전용이고 승인은 기존 검수 호출이다.** `POST /api/sellers/{sellerId}/orders/{orderId}/returns/{returnId}/recommendation`은 수령했고 검수 결과가 없는 반품에만 답하고(그 밖은 409), 상태·환불 행·정산 예약·PayPal 호출을 만들지 않는다. 응답의 줄별 `suggestedResult`를 판매자가 `PUT .../inspection`에 보내야 돈이 움직이며, 그 호출이 주문 행 잠금 아래에서 수량과 금액을 다시 계산한다. 권고는 잠금 없이 읽으므로 그 사이 상태가 바뀔 수 있고, 돈의 정합성은 검수 호출이 지킨다.
4. **권고를 저장하지 않는다(1단계).** 돈을 움직이는 결정(검수 결과·환불 행)은 이미 저장된다. 권고는 저장된 사실과 판매자가 보낸 상태의 순수 함수라 같은 입력으로 다시 계산된다.
5. **2단계 LLM 검토 층(`ReturnRecommendationReviewer`)은 승인을 사람 검토로 내리거나 설명만 붙인다.** 공유 LLM 클라이언트(`atlas-llm`, ADR-0109)의 `ChatCompletionService`를 쓴다. 모델은 첫 줄에 `KEEP` 또는 `HUMAN_REVIEW`만 쓸 수 있고, 해석 코드는 규칙이 `APPROVE_*`일 때의 `HUMAN_REVIEW`만 반영한다. 그 밖의 값(승인 지시, 형식 위반, 빈 응답)은 버리고 규칙 결과를 쓴다. 승인 쪽으로 옮기는 해석 경로가 코드에 없다. 금액과 줄 결과는 규칙의 값이다. LLM이 꺼져 있거나(기본) 실패하면 규칙 결과만 낸다. 호출은 읽기 트랜잭션 밖에서 한다. 프롬프트에는 사유 코드, 줄 상태, 규칙 결과·근거 코드, 이메일·전화번호를 가린 자유 텍스트만 넣고 buyerRef·주소·결제 식별자는 넣지 않는다. 응답은 `ruleDecision`(규칙 결과), `reviewDowngraded`, `explanation`을 함께 내보내 판매자가 둘을 구분한다.
   - ✓ 결정(가정): LLM 권고를 아직 저장하지 않는다. 기본이 꺼짐이고 실제 모델 평가 전이다. 재검토 조건: 실제 판매자 대상으로 `ATLAS_LLM_ENABLED=true`를 켜기 전에 권고(모델, 규칙 결과, 최종 결과, 설명)를 감사 이벤트로 저장한다.

## 대안과 기각 이유

| 안 | 근거 | 결정 |
|---|---|---|
| LLM이 처음부터 4분류를 판정 | 주입·환각이 곧 승인. EXP-121 C31~C33처럼 텍스트가 승인을 지시하는 사례에서 규칙은 텍스트를 읽지 않으므로 영향이 0이다 | ✗ 기각 |
| 권고를 자동 실행(승인이면 바로 환불) | 판매자 승인 원칙과 충돌. 검수 호출이 이미 승인 경로다 | ✗ 기각 |
| 상태를 저장하는 "제안 승인" 엔드포인트를 새로 둠 | 같은 일을 하는 환불 경로가 둘이 된다(SSOT 위반). 검수 호출에 줄별 결과를 보내는 것으로 충분 | ✗ 기각 |
| 기존 `PASSED`/`FAILED`만 입력으로 받음 | 판매자가 이미 판정을 내린 뒤라 권고할 것이 없다. 상태(미개봉·개봉·사용·파손·하자 확인·미반환)는 판정 전 관찰이다 | ✗ 기각 |
| 사유를 필수로 받음 | 사유 이전 클라이언트와 시험 10곳이 깨진다. 사유가 없으면 사용·파손 줄이 사람 검토로 가므로 안전 쪽으로 기운다 | ✗ 기각 |
| 중복 환불 줄만 불통과(부분 승인 허용) | 이미 나간 돈과 겹치는 반품은 데이터 이상이라 정상 줄까지 사람이 다시 봐야 한다 | ✗ 기각 |
| 결정 1~5 채택 | EXP-121: 라벨 60건에서 거짓 승인 0/17 | ✓ 채택 |

## 결과

- 판매자는 사유·자유 텍스트·줄별 기한·서버 계산 환불액과 근거 코드를 한 번에 본다. 결정은 여전히 판매자의 검수 호출이다.
- 규칙만으로 라벨 60건 중 52건이 맞고 거짓 승인은 0이다. 틀린 8건은 모두 자유 텍스트를 읽어야 정답을 아는 사례다(EXP-121). 이 중 4건(규칙 승인, 정답 사람 검토)이 2단계 LLM 층의 대상이다.
- 사람 검토 이관은 60건 중 19건이다. 판매자 책임 주장과 사용·파손이 겹치면 규칙은 판단하지 않는다.

## 롤백

- 권고 엔드포인트는 읽기 전용이라 앱만 되돌리면 된다. V15 컬럼은 nullable이고 이전 앱이 무시하므로 스키마를 되돌릴 필요가 없다. 되돌린 동안 사유 입력은 버려지지 않고 저장되지 않을 뿐이다(요청 본문의 모르는 필드).

## 재검토 조건

- 판매자가 권고와 다른 검수 결과를 낸 비율을 잴 수 있게 되었는데 승인 권고 뒤 `FAILED`가 10%를 넘으면: 상태 표와 상한을 다시 잰다.
- 다른 환불 경로(배송 뒤 직접 환불, PayPal 분쟁 수용)가 생기면: `DUPLICATE_REFUND`가 방어선이 아니라 실제 경로가 되므로 반품 요청과 같은 주문 행 잠금 아래에서 계산하는지 다시 본다.
- 300,000원 상한은 근거 없는 가정이다. 판매자별 평균 객단가가 생기거나 상한 초과 사람 검토가 하루 이관의 절반을 넘으면 다시 정한다.
- 실제 모델로 켤 때: EXP-121과 같은 60건을 실제 모델로 다시 재고(거짓 승인 0/17 유지, 정답 승인 24건의 잘못된 강등 수), 감사 이벤트 저장을 함께 넣는다.
