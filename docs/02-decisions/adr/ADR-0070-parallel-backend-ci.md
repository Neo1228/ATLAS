# ADR-0070: Backend CI를 병렬 shard로 나누고 문서 전용 변경은 Java 검사를 건너뛴다

- 상태: Accepted(구현·실측 완료)
- 날짜: 2026-11-23
- 관련 결정: [EXP-030](../../03-experiments/EXP-030-ci-build-duration.md)
- 근거: [Issue #501](https://github.com/Neo1228/ATLAS/issues/501)

## 문제

Backend CI가 한 job에서 직렬로 돌아 최근 성공 26회 기준 중앙값 366초, 최대 513초다. 필수 체크가 `strict`라 스택 PR은 병합할 때마다 뒤 PR이 이 시간을 다시 기다린다. 문서만 바꾼 PR도 같은 Java 검사를 돈다. 문서 검사는 7~11초라 병목이 아니다.

## 결정

- `changes`(변경 감지), `verify`(정적 검사와 다른 모듈 테스트), `app-tests`(application 테스트 4 shard), `backend`(판정) 4단계로 나눈다. 필수 체크 이름 `Java 25 and PostgreSQL integration checks`는 판정 job이 그대로 제공한다.
- shard는 JUnit `PostDiscoveryFilter`가 클래스 단위로 나눈다. 배정은 기록된 실측 시간을 가중치로 쓰는 LPT 방식이다. 가중치에 없는 새 클래스는 이름 해시로 배정하고, shard 지정이 잘못되면 실패한다.
- `docs/`와 Markdown만 바뀐 PR은 `changes` job이 판정해 Java 검사를 건너뛴다. `paths-ignore`는 필수 체크를 대기 상태로 남기므로 쓰지 않는다.

## 대안과 버린 이유

| 대안 | 버린 이유 |
| --- | --- |
| 클래스 이름 해시 분할 | 측정한 클래스 시간으로 시뮬레이션하면 4분할 최대 172초로 이상값(113초)의 1.5배다. |
| `paths-ignore`로 문서 PR 건너뛰기 | 필수 체크가 영원히 대기 상태로 남아 병합할 수 없다. |
| shard 5개 이상 | runner 준비 시간(약 33초)과 추가 이득(시뮬레이션 약 40초)이 비슷하다. |
| Spring context 공유·컨테이너 재사용으로 테스트 자체를 줄이기 | 효과가 더 클 수 있으나 테스트 53개 클래스의 설정을 건드리는 별도 작업이다. 이번에는 하지 않았다. |

## 결과(GitHub runner, 같은 PR 브랜치의 3회 실행)

| 실행 | 가중치 | 전체 wall(큐 대기 포함) | application shard job 시간 |
| --- | --- | --- | --- |
| 1 | 로컬(8 vCPU) 실측 | 251초 | 148, 170, 188, 236초 |
| 2 | 로컬 실측(같은 구성 재실행) | 217초 | 141, 161, 194, 204초 |
| 3 | runner 실측으로 교체 | 221초 | 145, 154, 169, 208초 |

- 기존 중앙값 366초(job 시간 기준)에 비해 전체 대기 시간이 217~251초로 줄었다. 중앙값끼리 비교하면 약 37% 감소이나 새 구조는 3회뿐이라 범위로만 읽는다. 기존 수치는 job 시간이고 새 수치는 큐 대기를 포함한 wall이라 새 쪽이 불리하게 측정됐다.
- 모든 실행에서 shard별 테스트 수는 123/141/86/163이고 합계 513건(기존 507 + 필터 단위 테스트 6)이며 실패는 0이다. 로컬에서 4개 shard를 따로 실행해도 같은 결과였고 중복 실행된 클래스는 0이다.
- 판정 job은 2~3초이고, 정적 검사·다른 모듈 테스트(verify)는 33~51초다. 가장 느린 shard가 전체 시간을 결정한다.

## 틀렸던 가설

가중치를 8 vCPU Mac의 로컬 실측으로 만들었더니 shard 편차가 1.4배였다. 원인을 "runner(4 vCPU)와 CPU가 달라 클래스별 상대 비용이 어긋남"으로 가정하고, runner 실측값으로 가중치를 다시 만들었다. 시뮬레이션은 최대 shard가 240초에서 215초로 줄고 편차가 사라진다고 예측했다. **실측은 예측과 달랐다.** 최대 shard는 204초에서 208초로 그대로이고 편차도 145~208초로 남았다.

즉 "클래스 시간은 어느 shard에 있든 같다"는 가정이 틀렸다. 가장 가능성이 큰 원인은 같은 shard 안의 클래스가 Spring 컨텍스트나 컨테이너를 재사용해 비용이 달라지는 것이다. 이 원인은 검증하지 않았다. 가중치 조정의 추가 효과가 작다는 사실만 확인했으므로 여기서 멈췄다.

## 병합 후 확인(2026-11-23)

- 장애 수렴 PR(#500)이 새 CI로 처음 실행됐다. 전체 wall 182초, shard 테스트 합계 521건(107+173+128+113)이 통과했다. 가중치에 없던 새 테스트 클래스(`LocationFaultConvergenceIntegrationTest`)도 이름 해시로 배정되어 실행됐다.
- 기대값 520건과 1건 달랐다. 원인은 같은 시기에 병합된 다른 PR(#503)이 `@Test` 1건을 추가한 것이다. 기준을 507이 아닌 508로 보면 508 + 7 + 6 = 521건으로 맞는다. 누락·중복은 없다.
- 문서 전용 변경이 Java 검사를 건너뛰는 경로는 이 문서를 바꾸는 PR로 확인한다. 앞선 실행들은 워크플로와 Java 파일을 포함한 PR이라 항상 코드 변경으로 판정되어 이 경로를 검증하지 못했다.

## 한계

- 3회 실행의 범위이며 runner 간 잡음을 통계적으로 분리하지 못했다.
- 총 runner 시간은 늘었다. shard마다 Gradle 설정과 컨테이너 기동이 중복된다. 공개 저장소라 비용은 없지만 동시 runner 한도를 쓴다.
- 가중치 파일은 클래스가 크게 바뀌면 `scripts/ci/update-test-shard-weights.py`로 갱신해야 균형이 유지된다. 갱신하지 않아도 모든 테스트는 정확히 한 번 실행된다.
- 가장 느린 shard의 원인을 줄이는 방법(컨텍스트 공유)은 후속 과제다.

## 재현

```sh
ATLAS_TEST_SHARD=1/4 ./gradlew :application-module:test
python3 scripts/ci/update-test-shard-weights.py --run <Backend CI run id>
```
