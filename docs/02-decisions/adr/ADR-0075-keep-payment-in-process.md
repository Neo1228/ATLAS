# ADR-0075: 결제를 독립 서비스로 분리하지 않고 모듈 경계로 유지한다

- 상태: Accepted
- 날짜: 2026-11-25
- 관련 결정: [ADR-0026](ADR-0026-paypal-sandbox-payments.md), [ADR-0038](ADR-0038-durable-payment-recovery-workflow.md), [ADR-0046](ADR-0046-order-payment-transactional-outbox.md)
- 근거: [EXP-050](../../03-experiments/EXP-050-toxiproxy-postgres-fault-probe.md), [EXP-068](../../03-experiments/EXP-068-stage-evidence-map.md)

## 문제

처음 계획의 5단계는 결제 시스템에 별도 상태 저장소를 주고 타임아웃, 지연 성공, 중복 통지를 재현해 결과가 불명한 상황에서도 중복 청구와 잘못된 출고를 막는 것이었다. 지금 결제는 같은 애플리케이션과 같은 PostgreSQL 안에 있고 외부 결제 시스템은 실제 PayPal Sandbox다. 독립 결제 서비스를 만들 것인가?

## 결정

만들지 않는다. 결제를 `atlas-payment` 모듈로 두고 경계는 지금처럼 코드로 강제한다. 아래 재검토 조건 중 하나가 측정으로 확인되면 다시 판단한다.

근거는 결합을 센 결과다(2026-11-25 main `95519599`).

| 측정 | 값 |
| --- | --- |
| 결제 모듈(Java 87개 파일)이 다른 모듈을 import하는 횟수 | 0 |
| 결제 모듈을 import하는 모듈 | application(16개 클래스, import 47회), order(5개 클래스, import 14회) |
| 결제 테이블 | 11개 |
| 다른 모듈의 SQL이 결제 테이블을 직접 읽는 곳 | settlement의 PayPal 대사 저장소 1곳(테이블 3개, SQL로 직접 접근) |
| 경계 강제 | `ModuleBoundaryTest`가 결제 모듈의 허용 의존을 자기 자신, Java, 영속성, Jackson으로 제한 |

- 결제는 이미 나가는 의존이 없는 잎(leaf) 모듈이고, 들어오는 호출은 서비스 인터페이스로만 들어온다. 분리했을 때 바뀔 호출 지점은 order의 5개 클래스와 application의 16개 클래스다.
- 주문과 결제의 일관성은 이미 서비스 사이의 경계를 가정한 방식으로 풀려 있다. 결제 의도를 PostgreSQL에 먼저 남기고, provider를 호출하고, 주문 쪽에 결과를 적용하는 순서의 복구 작업이다([ADR-0046](ADR-0046-order-payment-transactional-outbox.md)). 같은 DB 트랜잭션 하나에 의존하지 않는다.
- 결과가 불명한 상황은 이미 실제 Sandbox로 확인했다. capture 응답을 12초 지연시켜(클라이언트 read timeout 10초 초과) 응답을 유실시키면 ATLAS는 `PAYMENT_UNKNOWN`이 되고 PayPal에는 capture가 1건 있었다. 복구 worker를 켠 조건에서 3/3이 수동 개입 없이 `PAID`로 수렴했고 capture와 settlement journal이 각각 1건이었다([EXP-050](../../03-experiments/EXP-050-toxiproxy-postgres-fault-probe.md), 조건별 n=3).

## 대안과 버린 이유

| 대안 | 버린 이유 |
| --- | --- |
| 결제를 별도 프로세스와 별도 DB로 분리한다 | 풀려는 문제가 확인되지 않았다. 결제가 병목이라는 측정, 결제만 독립 배포해야 하는 요구, 결제 장애가 주문을 막는 경로가 모두 없다. 분리하면 서비스 사이 인증, 버전 호환, 분산 추적, 배포 순서가 새 운영 비용으로 생긴다 |
| 가상 결제 시스템을 만들어 독립 서비스처럼 쓴다 | 가상 시스템의 응답 규칙이 실제 PayPal과 다르면 5단계 근거가 가짜 가정에 기댄다. 실제 Sandbox를 쓰는 편이 같은 장애를 더 정확히 재현한다 |
| 분리 가능성만 코드로 확인한다(경계 강제) | **채택.** 이미 `ModuleBoundaryTest`로 강제하고 있다 |

## 결과와 한계

- 5단계의 "독립 결제 서비스"는 만들지 않은 것으로 남는다. 문서와 README는 이를 "부분"으로 표기하고 이유를 이 결정으로 가리킨다.
- 한계: 이 판단은 단일 팀, 단일 DB, 현재 부하에서의 판단이다. 결제만 따로 늘려야 하는 부하는 측정하지 않았다. 결합을 센 것은 `import`와 SQL 문자열 검색이며 리플렉션이나 설정 문자열을 통한 결합은 세지 못했다. settlement의 대사 저장소가 결제 테이블을 읽는 1곳은 분리 시 먼저 풀어야 하는 결합이다.
- 성능 비용(결제 호출이 프로세스 안인지 밖인지에 따른 지연 차이)은 측정하지 않았다.

## 실패 경로와 되돌리기

- 이 결정은 코드를 바꾸지 않는다. 되돌릴 것이 없다.
- 재검토 조건이 충족돼 분리하게 되면 order의 5개 클래스와 application의 16개 클래스를 서비스 호출로 바꾸고, settlement의 대사 저장소를 결제 쪽 조회 계약으로 바꾸는 것이 첫 작업이다.

## 후속

- 재검토 조건: (1) 결제 경로의 지연이나 장애가 주문 처리량을 제한한다는 측정, (2) 결제만 독립 배포·확장해야 하는 요구, (3) 결제 DB를 분리해야 하는 규제나 보안 요구 중 하나.
- 재검토 시 먼저 settlement 대사 저장소의 결제 테이블 직접 접근을 조회 계약으로 바꿀 수 있는지 확인한다.
