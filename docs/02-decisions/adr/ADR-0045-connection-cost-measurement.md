# ADR-0045: 커넥션 비용은 점유율이 아니라 획득 횟수로 측정한다

- **상태:** 채택 (Accepted)
- **일자:** 2026-11-19
- **관련:** [#373](https://github.com/Neo1228/ATLAS/issues/373), [#375](https://github.com/Neo1228/ATLAS/issues/375),
  [#376](https://github.com/Neo1228/ATLAS/issues/376)
- **결정 로그:** [D-104](../../00-governance/decision-log.md#d-104)

## 배경

접속 풀은 "몇 개를 동시에 쓸 수 있나"로만 이야기되기 쉽습니다. 그래서 풀 지표를 볼 때
`active`, `idle`, 대기열 길이를 보는 습관이 생깁니다. 이 프로젝트도 그렇게 판단해
**잘못된 변경을 배포하고 되돌렸습니다.** 그 기록을 남깁니다.

### 무엇을 했나

640 VU 부하 중 PostgreSQL 세션 상태를 5회 샘플링했습니다(연결 49개 고정).

| 샘플 | `idle in transaction` | `active` | `idle` | 유휴 비율 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 34 | 4 | 11 | 69% |
| 2 | 23 | 5 | 21 | 47% |
| 3 | 24 | 8 | 17 | 49% |
| 4 | 38 | 3 | 8 | 78% |
| 5 | 33 | 7 | 9 | 67% |

평균 **62%** 가 `idle in transaction` 이었습니다. 원인은 목록 조회의
`@Transactional(readOnly = true)` 였고, 쿼리 4개 사이에 앱이 매핑을 하는 동안 커넥션이
반납되지 않았습니다. 그래서 트랜잭션을 제거했습니다([#373](https://github.com/Neo1228/ATLAS/issues/373), PR #374).

유휴 비율은 **62% → 28%** 로 개선됐습니다.

### 무엇이 잘못됐나

Hikari 지표를 20초 창에서 차분해 보니 반대 방향이었습니다.

| 구성 | 커넥션 획득 / HTTP 요청 |
| --- | ---: |
| ① 트랜잭션 O + 쿼리 4개 (원래) | **3.09** |
| ② 트랜잭션 X + 쿼리 4개 (배포한 변경) | **6.43** |
| ③ 트랜잭션 O + 쿼리 3개 (병합 실험) | 3.31 |

트랜잭션을 빼면 쿼리 4개가 **각각** 커넥션을 빌리고 반납합니다. 획득 1회당 풀 대기가
약 38 ms 였으므로 요청당 대기 비용은:

```text
① 3.09 × 38 ms = 117 ms
② 6.43 × 38 ms = 244 ms        (+127 ms/요청)
```

처리량은 개선되지 않았습니다(292–296 → 247–300 it/s). 즉 **대리 지표를 최적화해
실제 비용을 악화시켰습니다.** 변경은 되돌렸습니다(PR #377).

## 결정

커넥션 비용을 판단할 때 다음을 따른다.

1. **1차 지표는 `획득 횟수 × 획득 대기 시간`** 이다. `active`/`idle`/`idle in transaction`
   비율은 진단 보조 지표이며, 그 자체를 목표로 삼지 않는다.
2. **트랜잭션 경계는 "빌린 획득 수"를 결정한다.** 한 트랜잭션 안의 여러 쿼리는 획득
   하나를 공유한다. 쿼리 수를 줄여도 획득 수는 줄지 않는다.
3. **쿼리 병합은 보유 시간만 줄이며, 그 이득이 행 작업 증가를 넘을 때만 채택한다.**
   측정 결과 이 프로젝트의 목록 경로에서는 넘지 못했다(아래 표).
4. 풀 크기 조정은 `풀러 서버 연결 상한 ≥ replica 수 × replica 당 pool` 을 만족하는
   범위에서만 검토한다. 이 범위를 넘기면 "더 많은 연결"이 "더 긴 대기"가 된다.

### 쿼리 병합 실험 (모두 미채택)

| 방식 | 행 작업 | 결과 |
| --- | ---: | --- |
| 상관 서브쿼리로 SKU·채널·카테고리 집계 | 1.30–4.4 ms | 보유 14 → 29 ms, 대기 38 → 104 ms **악화** |
| 단일 조인으로 페이지 + SKU | 3.0–72 ms | **악화** |
| `UNION ALL` 로 채널 + 카테고리 | 0.22 ms | 획득 횟수 불변, 처리량 무변화 **이득 없음** |

`UNION ALL` 이 행 작업을 거의 늘리지 않았는데도 이득이 없었다는 점이 핵심입니다.
병합으로 줄일 수 있는 것은 보유 시간뿐이고, 병목은 보유가 아니라 **획득 대기**이기
때문입니다.

## 결과

- 커넥션 비용을 재는 표준 창을 정했습니다: **20초 차분, `acquire_seconds_count` /
  `http_server_requests_seconds_count`**.
- 회귀 방지: 목록 조회 진입점 3개가 `@Transactional` 을 가져야 한다는 계약을 단위
  테스트로 고정했습니다.
- 재발 방지: 이 ADR 의 1차 지표를 인용하지 않는 "유휴 비율 개선" 주장은 근거로 쓰지
  않습니다.

## 남은 한계

요청당 117 ms 의 풀 대기는 그대로 남아 있습니다. 이 값은 DB 가 아니라 풀 큐에서
사라지며, 다음 선택지는 모두 별도 판단이 필요합니다.

| 선택지 | 왜 아직 안 했나 |
| --- | --- |
| pool 확대 | 총합 상한 52 에 걸리고, 상한을 올린 실험에서 동시 세션 증가로 처리량이 **떨어졌다** |
| 스레드 축소 | 대기열이 앱 앞으로 이동할 뿐 처리량은 그대로다 |
| 읽기 모델·캐시 | 커넥션을 잡지 않고 응답하는 유일한 방향이지만, 정합성·무효화 정책 설계가 선행되어야 한다 |

마지막 항목이 측정이 가리키는 방향입니다. 요청당 DB 작업은 약 0.6 ms 인데 커넥션을
14 ms 쥐고 있으므로, 그 차이를 다른 요청이 쓸 수 있게 만드는 것이 다음 단계입니다.
