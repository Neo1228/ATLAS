# ADR-0044: 부하 시나리오는 실제 구매 여정과 공개 전환율로 구성한다

- 상태: Proposed
- 날짜: 2026-11-19
- 추적: [#346](https://github.com/Neo1228/ATLAS/issues/346)

## 맥락

EXP-033/035는 `catalog-read-capacity.js`로 읽기 경로만 측정했습니다. 이 시나리오는 1 iteration에 공개 GET 6개를 실행합니다. 유용했지만 세 가지가 빠져 있었습니다.

1. **쓰기 경로 부재.** 장바구니 변경, 체크아웃 예약, read-after-write 검증이 없습니다. 실제 이커머스의 비용과 실패 모드는 이 소수 쓰기에서 나옵니다.
2. **비현실적 분포.** 시드가 균등 분포라 핫 셀러·핫 상품이 없습니다. 프로모션에서 발생하는 락 경쟁과 핫 파티션이 드러나지 않습니다.
3. **resume 미고려.** 재방문 사용자가 기존 장바구니를 이어받는 동작을 측정하지 않았습니다.

또한 측정 중 세 가지 실행 결함이 드러났습니다.

- 장바구니 API는 인증이 필요해 인증 없는 시나리오는 100% 실패했습니다.
- 첫 방문자는 장바구니가 없어 `404 CART_NOT_FOUND`가 정상인데 실패로 집계했습니다.
- 프로브가 시나리오마다 `down --volumes`를 실행해 2M 행 데이터셋을 지웠고, 그 다음 측정이 빈 카탈로그에서 돌았습니다.

## 결정

1. **여정 시나리오를 기본으로 쓴다**(`load-tests/buyer-journey-capacity.js`). 읽기가 다수이고 쓰기는 공개 벤치마크 비율을 따릅니다.
   - 장바구니 추가: 세션의 **6%** (Dynamic Yield 12개월 벤치마크 6.04%, 2차 요약)
   - 체크아웃 시도: 장바구니 추가의 25%
2. **인증된 구매자**를 `setup()`에서 1회 등록하고 VU별로 재사용합니다. 반복마다 가입하면 가입 비용을 측정하게 됩니다.
3. **read-after-write를 명시적으로 검증**합니다. 쓰기 직후 장바구니를 다시 읽어 반영 여부를 `journey_cart_read_after_write_ok`로 기록합니다. 캐시·read replica 도입 시 가장 먼저 깨지는 성질이기 때문입니다.
4. **빈 장바구니 404를 정상 상태로 처리**합니다. 401/403/5xx만 실패입니다.
5. **핫키 편중을 파라미터화**합니다(`HOT_SELLER_SHARE`). 기본 0이지만 프로모션 재현 시 사용합니다.
6. **대용량 데이터셋은 named volume에 두고 재사용**합니다. `LOAD_KEEP_DATA=1`이면 `down`이 볼륨을 지우지 않습니다.

## 근거

- 전환율: 세션의 6%만 장바구니에 담습니다. 1:1로 쓰기를 섞으면 실제보다 쓰기를 16배 과대평가합니다.
- read-after-write: GitHub은 replica로 read를 30%까지 돌리면서 지연 작업을 lag 기반으로 대기시켰습니다(freno). Aurora는 1,000→10,000 writes/s에서 replica lag이 2.62→5.38 ms였습니다. 두 사례 모두 **쓰기 직후 읽기**를 replica로 보내면 안 된다는 전제를 공유합니다.
- 핫키: 균등 분포는 프로모션 트래픽을 대표하지 못합니다. EXP-035에서 균등 분포만으로는 락 경쟁이 드러나지 않았습니다.

## 기각한 대안

| 대안 | 기각 이유 |
| --- | --- |
| 읽기 시나리오 유지 | 쓰기·read-after-write·resume를 전혀 측정하지 못함 |
| 쓰기 50% 시나리오 | 공개 전환율과 8배 이상 차이. 큐·락 병목을 과장 |
| 반복마다 구매자 가입 | 측정 대상이 가입 흐름으로 바뀜 |
| 시나리오마다 데이터 재시드 | 2M 행 재시드가 측정 창을 오염시키고 시간을 낭비 |
| 404를 실패로 유지 | 정상 첫 방문을 장애로 보고 |

## 결과와 한계

- 전환율은 **제3자 벤치마크 요약**이며 ATLAS 자체 데이터가 아닙니다. 자체 로그가 생기면 교체해야 합니다.
- 체크아웃은 결제 provider가 `disabled`인 로컬 구성이라 실제 승인까지 가지 않습니다. 예약·재고 경로까지만 측정합니다.
- 인증 토큰은 실제 발급 경로를 쓰지만, 이메일 인증은 Mailpit에 의존합니다. 메일 지연이 setup 시간에 포함됩니다.
- 핫키 편중은 파라미터이며 기본값은 균등입니다. 프로모션 재현은 별도 실행으로 남깁니다.

## 운영 규칙

- 드롭이 0이 아닌 지점을 용량이라 부르지 않습니다.
- 인증 실패(401/403)가 1%를 넘으면 측정을 중단합니다. 시나리오가 아니라 인증 설정 문제이기 때문입니다.
- 대용량 데이터셋 측정에서는 `LOAD_KEEP_DATA=1`을 명시합니다.
