# 고부하·대용량에서의 시스템 디자인 검토

**상태:** 설계 검토 · 측정 근거 기반 · 단계별 도입

**관련:** [ADR-0045](adr/ADR-0045-connection-cost-measurement.md),
[scaling-bottleneck-map.md](scaling-bottleneck-map.md),
[distributed-readiness.md](distributed-readiness.md)

## 이 문서의 목적

측정으로 확인한 병목을 **어떤 순서로, 무엇으로** 푸는지 정리합니다. 스펙 증설은
선택지에서 제외했습니다. 이유는 측정이 그것을 부정했기 때문입니다(아래 "증설이
통하지 않은 이유").

## 측정된 사실 (요약)

| 항목 | 값 | 출처 |
| --- | ---: | --- |
| 목록 요청 1건 서버 지연 | 264 ms | Actuator `/api/products` |
| 그중 DB 쿼리 실행 | 0.67 ms (0.3%) | `pg_stat_statements`, buffer 1,132 |
| 그중 커넥션 획득 대기 | 117 ms (44%) | Hikari `acquire` × 획득 횟수 |
| 커넥션 획득 / HTTP 요청 | 3.09 (트랜잭션 유지 시) | Hikari 차분 |
| 요청당 응답 크기 | 91 KiB → gzip 6.6 KiB | 실제 응답 측정 |
| PostgreSQL CPU | 8코어 중 1.6 (20%) | `docker stats` |
| 앱 CPU | 2코어 중 1.6–1.9 (80–95%) | `docker stats` |

핵심은 **DB 가 병목이 아니라는 점**입니다. DB 연산은 요청당 0.67 ms 이고 CPU 도
20% 입니다. 지연은 응답을 만들고, 커넥션 큐를 통과하고, 바이트를 내보내는
경로에서 발생합니다.

## 증설이 통하지 않은 이유

측정으로 세 가지를 확인했습니다.

1. **pool 확대** — pool 10 → 16, 풀러 상한 80 으로 올려 측정했더니 처리량이
   떨어졌습니다. 동시 세션이 늘면 각 쿼리가 느려지고, 풀러가 서버 연결을
   재사용하지 못해 `sv_tested` 가 누적됐습니다.
2. **앱 코어 확대** — replica 당 2 → 4 코어로 올려도 272 → 292 it/s 로 변화가
   없었습니다. 커넥션 수가 병렬성의 상한이라 CPU 가 남아도 쓰이지 않습니다.
3. **고정 노드 스펙** — [ADR-0042](adr/ADR-0042-fixed-node-capacity-methodology.md)
   에서 노드 스펙을 고정하고 replica 만 늘리는 방법론을 이미 채택했습니다.

즉 병목은 자원량이 아니라 **직렬화 지점**입니다.

## 설계 원칙

측정에서 도출한 원칙입니다. 이후 모든 최적화는 이 순서로 판단합니다.

1. **요청 경로에서 커넥션을 덜 잡는다.** 커넥션은 희소 자원이고, 잡고 있는
   시간의 95% 는 앱 계산입니다. 잡는 횟수와 시간을 먼저 줄입니다.
2. **응답 바이트를 줄인다.** 전송은 CPU·소켓·네트워크를 모두 씁니다. 압축과
   중복 제거가 여기 해당합니다.
3. **읽기는 DB 를 지나지 않게 한다.** 같은 데이터를 수천 번 읽는 경로는
   캐시·읽기 모델로 옮깁니다. 단, 정합성 요구가 낮은 곳부터.
4. **쓰기 경로는 정합성을 유지한다.** 주문·결제·재고는 캐시하지 않습니다.
5. **스펙은 마지막 수단이다.** 위 1–4 를 소진한 뒤에도 벽이면 그때 자원을 늘립니다.

## 단계별 계획

### 1단계 — 즉시 가능, 위험 낮음 (완료/진행)

| 항목 | 측정 효과 | 상태 |
| --- | --- | --- |
| 만료 sweep 이 부분 인덱스를 쓰도록 정렬 수정 | buffer 9,960 → 21 | 완료 (#372) |
| 커넥션 풀 예산 health 노출 | 조용한 실패 제거 | 완료 (#370) |
| 목록 트랜잭션 유지(획득 3.09 회복) | 요청당 대기 127 ms 제거 | 완료 (#377) |
| 응답 gzip 압축 | 91 KiB → 6.6 KiB | 진행 (#382) |

### 2단계 — 인증 경로에서 커넥션 획득 제거

인증된 모든 요청이 JWT 검증에서 DB 를 봅니다(`isAccessTokenFamilyActive`).
요청당 획득 3.09 중 1회가 여기입니다.

#### 설계 선택지와 판단

| 방안 | 정합성 | 위험 |
| --- | --- | --- |
| 활성 여부 TTL 캐시 | 폐기 지연 TTL | 상태 변경 경로마다 무효화 필요 |
| 폐기 epoch claim | 정확 | DB 조회는 여전히 필요 |
| 폐기 목록(deny list) 캐시 | 목록 반영 지연 | 워밍 전 통과 가능 |

**측정으로 확인한 제약:** 이 프로젝트의 테스트는 DB 를 직접 수정해 즉시 폐기를
검증합니다(`jdbc.update` 로 상태 변경). 즉 캐시 무효화가 **모든 변경 경로**를
덮어야 하는데, 현재는 리포지토리를 직접 호출하는 경로가 있어 보장할 수 없습니다.

**따라서 순서를 바꿉니다.**

1. 먼저 계정·세션 상태 변경을 **단일 서비스 경계**로 모은다.
2. 그 경계에서만 무효화 이벤트를 발행한다.
3. 그 다음 캐시를 도입한다.

이 순서를 지키지 않으면 보안 회귀 위험이 이득보다 큽니다(실제로 시도했다가
즉시 폐기 테스트 2건이 실패해 되돌렸습니다).

### 3단계 — 읽기 모델(읽기 전용 뷰)

목록은 같은 상품 집합을 세 쿼리가 반복 방문합니다(buffer 1,132 중 목록 503,
SKU 324, 채널/카테고리 305). 세 쿼리를 합치는 것은 행 작업이 늘어 실패했지만
(측정: 1.30–4.4 ms), **미리 조인해 둔 읽기 모델**은 다릅니다.

**실측 후 구현했습니다(PR #390).** 2M 상품에서 100건 페이지:

| 방식 | 시간 | buffer | 쿼리 |
| --- | ---: | ---: | ---: |
| 원본 3개 테이블 | 0.67 ms | **1,132** | 3 |
| 읽기 모델 | **0.37 ms** | **103** | **1** |

```text
적용:  product_listing_projection (채널·카테고리 집계, V45)
       -> 목록은 이 표에서만 읽는다 (buffer 103, 쿼리 1회)
       -> 상세·주문 가능 판정은 원본을 계속 본다
```

- 갱신: 카탈로그 쓰기 트랜잭션에서 같은 트랜잭션으로 갱신합니다. 트리거를 쓰지 않는
  이유는 애플리케이션 동작이 DB 에 숨는 것을 피하기 위해서입니다.
- 정합성: 목록은 준실시간이면 충분합니다. 상세·주문 가능 판정은 원본을 봅니다.
- **구현 중 발견한 함정**: `@ElementCollection` 은 flush 시점에 반영됩니다. flush 전에
  투영을 갱신하면 이전 채널 상태가 들어갑니다. 실제로 채널을 켰는데 목록에 반영되지
  않는 것을 통합 테스트로 확인하고, 쓰기 경로를 `saveAndFlush` 로 바꿨습니다.
  이 회귀를 테스트로 고정했습니다.
- 이득의 정직한 범위: DB 실행이 0.67 → 0.37 ms 이지만 커넥션 보유는 14 ms 이므로
  **처리량이 오른다고 주장하지 않습니다.** 가치는 확장 여지입니다 — 목록이 상품 전체를
  재스캔하지 않고 페이지에 필요한 페이지만 읽으므로, `shared_buffers` 가 작은 환경에서
  캐시 적합률이 오르고 상품 수 증가에도 비용이 선형으로 늘지 않습니다.

이 단계가 **쿼리 횟수를 원본 테이블 수와 분리하는** 방향입니다. 다음 후보는 SKU 를
투영에 포함해 2 → 1 로 더 줄이는 것입니다.

### 4단계 — 캐시 계층

읽기 모델로도 부족하면 캐시를 둡니다.

- 위치: 앱 앞(프록시) 또는 앱 내부. 측정상 앱 CPU 가 포화이므로 **앱 앞**이 낫습니다.
- 무효화: 상품 변경 이벤트 기반. TTL 은 안전망으로만.
- 주의: 이 프로젝트는 이미 "캐시 도입 전에 무효화 경로를 단일화한다"는 교훈을
  얻었습니다(2단계).

### 5단계 — 그래도 부족할 때

- 읽기 replica 로 목록 조회를 분리(쓰기와 읽기의 커넥션 예산을 따로 관리).
- 그 다음에야 수직 확장을 검토합니다.

## 대규모 트래픽·데이터에서의 고려

측정 환경(2M 상품, 4M SKU)에서 확인한 것과, 더 큰 규모에서 달라질 지점입니다.

| 규모 | 지금 확인된 것 | 더 커지면 |
| --- | --- | --- |
| 상품 2M | 목록 정렬 인덱스로 0.32 ms | 100M 이면 인덱스 깊이 증가, 커서 페이지네이션 유지 필요 |
| SKU 4M | 배치 조회 0.24 ms, buffer 324 | 샤딩 또는 SKU 집계 사전 계산 |
| 주문 1만 | sweep buffer 21 | 파티셔닝(월 단위), 오래된 파티션 분리 |
| 동시 640 | 커넥션 큐 117 ms | 풀러·replica 예산을 함께 설계 |
| 응답 91 KiB | gzip 6.6 KiB | 필드 선택(sparse fieldsets) 또는 페이지 크기 축소 |

**극한 동시성에서의 원칙:** 커넥션 풀은 큐입니다. 큐의 대기 시간은
`획득 횟수 × 평균 대기`이고, 평균 대기는 Little's law 로 포화 근처에서 급격히
증가합니다. 그래서 "동시 요청이 많다"는 것은 "커넥션을 오래 잡는 요청이 많다"와
같은 문제로 다뤄야 합니다.

## 이 문서가 주장하지 않는 것

- 운영 규모의 SLA. 모든 수치는 단일 호스트 로컬 측정입니다.
- 처리량 배수. 세션 후반 측정은 호스트 과부하(load average 15.9/11코어)로
  절대값을 신뢰할 수 없어, 상대 비교도 같은 시점끼리만 유효합니다.
- 3·4·5단계의 효과. 아직 구현하지 않았으므로 측정된 적이 없습니다.
